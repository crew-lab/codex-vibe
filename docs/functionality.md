# Behavior

The supervisor is a local MCP coordinator for Mistral Vibe runs through the `vibe-app-server` protocol: one app-server process per run, driven as a client over newline-delimited JSON-RPC on stdio. Its five tools are `vibe_review_start`, `vibe_edit_start`, `vibe_status`, `vibe_result`, and `vibe_close`. Review and edit starts require a short-lived private dispatch grant: `authorization_id` binds the exact request to current policy and authorizes one start, while `attempt_id` uniquely identifies that dispatch attempt. The coordinator obtains these values with `vibe-supervisor task authorize`; the start tool rejects missing, expired, replayed, or mismatched grants. Runs remain one-shot and restart, timeout, failure, or cancellation never replays a task. The only accepted Vibe version is 3.0.2, including the default and the exact app-server pin. Run records, events and results name the engine as `backend: app-server`.

The supervisor, not Vibe's defaults, decides what the model may do. It starts the server with a supervisor-written session configuration, reads the effective configuration back before the first turn and fails the run on any mismatch, answers every approval request itself, and audits the run's history for any tool effect it did not approve. [Security](security.md#enforcement-points) lists each point. The model's tool catalogue cannot be narrowed: `write_file`, `edit`, the shell tool and `run_typescript` are listed to the model, in reviews too, and are refused when called. The model sees these tools and cannot use them; each refused call is recorded as a `tool_denied` event and the run continues.

The capacity guarantee belongs to one owning server/storage instance. The server reserves its single slot before asynchronous preparation and rejects another start with a capacity error; there is no waiting record or hidden worker. Separate isolated MCP connections can each own an instance. A second process cannot manage the same storage while the owner lock is held.

The owner lock is crash recovery, not a lease. When its owner process has exited, or its PID now belongs to a process started after the lock was written, the next server to start takes the lock over and marks that storage's interrupted runs failed. An operator never needs to delete a lock for that case. `VSUP_OWNER_LOCKED` with a live owner means another supervisor really holds the storage: stop that process, or give the connection its own storage with `--isolated` or `VIBE_SUPERVISOR_HOME`. For an unsafe or malformed lock, inspect the file in `details.lock_path`; remove it by hand only after confirming that no `vibe-supervisor` process uses that data directory.

## Readiness and admission

Every delegation should begin with `vibe_status` in workspace mode on the connection that will run the task. The check rereads the selected configuration, runs the same admission validators a start runs, reports this server's version and instance, the policy revision, boot-setting drift, the active slot and executable resolution, and lists structured blockers. It creates no run, worktree or model call. An eligible check returns a 10-minute receipt bound to this server instance, the policy revision, the operation, the canonical workspace and, for an edit, the `base_ref` and the commit it resolves to. A start that carries the receipt is rejected before launch if any of these drifted. See [workspace readiness](reference.md#workspace-readiness).

A start, with or without a receipt, reserves the slot, then rereads and validates the selected configuration before it creates a record. Allowlist and `excluded_globs` changes therefore apply to the next check or start without a restart (the run records the exclusions it was admitted with); an allowed root that disappears from disk denies only workspaces under it; changes to boot-bound settings make readiness report `restart_required` and starts fail with `VSUP_RESTART_REQUIRED`; a missing or unsafe file fails closed. The admitted `policy_revision` is saved with the run. See [policy authority](reference.md#policy-authority).

## Run lifecycle

Admission, the slot, the integrity snapshot or detached worktree, and settlement belong to the run manager and are the same for both operations. The engine adds these steps:

1. **Before spawn:** the pin check hashes the installed Vibe files against the candidate's manifest (see [compatibility](compatibility.md#the-pin-and-its-manifest)), and the credential is resolved from `MISTRAL_API_KEY` in the supervisor environment or, on macOS, the Vibe Keychain entry. Either failing refuses the start before any process exists.
2. **Spawn:** `vibe-app-server` starts from the exact real path the pin check hashed (symlinks resolved once, in the check), with no arguments, piped standard streams, its own process group, the filtered child environment, the supervisor's `VIBE_*` settings, and a private `HOME`, `VIBE_HOME` and `TMPDIR` inside the run directory. The worker's standard output is consumed only by the protocol client, which bounds every line and the total; the process wrapper counts the bytes against the same budget but keeps no second copy. A small reaper process, in its own group, kills the worker's group if the supervisor disappears or the run deadline plus a margin passes.
3. **Handshake and read-back:** `initialize` (declaring that the client answers approvals; the result's server version must equal the pin), `initialized`, `session/start` with the profile, wait until the session is ready, read the runtime and effective configuration back, turn thinking off, read back again. The denylist compared per profile tool is the fixed list plus the run's `excluded_globs` from every containing root, anchored at that root. `config/read` must report a hook count and a skill count of exactly 0; a missing or null count is a mismatch, not a pass. Any mismatch fails the run before the first turn with `VSUP_BACKEND_ERROR` and `details.reason: readback_mismatch`.
4. **Turn:** `turn/start` carries the task as one text block over standard input, so the task is absent from OS-visible arguments. The supervisor handles every notification that arrived before the response before it adopts the response's event id, so none is dropped as stale. The start call returns when Vibe accepts the turn, with the run `running`. For a run whose workspace is a Git repository, the prompt starts with a bounded file listing (see [Review](#review)).
5. **During the turn:** notifications drive status. Each statistics update refreshes `usage` (tokens, and an estimated cost in USD that is not authoritative), at most about once a second, because the server writes no run export and the supervisor rebuilds usage and cost from the session statistics and Vibe's pricing formula. A counter that goes backwards outside a handoff fails the run (`details.reason: usage_counter_regressed`) instead of being clamped to zero, and a cost ceiling with no price for the active model fails the run (`details.reason: price_unavailable`), before the first turn when the prices are already missing at startup. Each `callback/call` is an approval request; see [security](security.md#approval-handler).
6. **Handoff:** when Vibe compacts or clears the session mid-turn it announces a new session id (`session/compacted`, `session/contextCleared`). The supervisor accepts that only when no effect is unfinished and no callback is open or unanswered; otherwise the run fails with `details.reason: session_handoff_unsafe`. It then adopts the new id and watermark, remembers a fingerprint of every effect it saw settle before the handoff, pages the new session's whole history (an effect first seen there must be approved like any other, and a known effect must be unchanged, else `historical_effect_changed`), reads the runtime and effective configuration back again with the startup comparison (thinking off included), and keeps counting usage: if the new session's counters reset, the old session's totals are carried and the new counters add to them; if they kept growing, they continue. Token and cost ceilings apply to the totals across the handoff. The result gains a warning and the run a `session_handoff` diagnostic; nothing is replayed and no callback or grant is carried over. A failed re-validation fails the run and every later approval is denied.
7. **End:** the supervisor reads the final statistics and pages the whole turn history once more, so an effect it missed live is found before the outcome is decided. The audit also runs after a budget or deadline stop that Vibe did not honor in time (the interrupt grace expired), as long as the connection is alive, so an unapproved effect is found even then; a cancel does not run it. An effect still `running`, `blocked` or otherwise unfinished when the turn ends fails the run (`details.reason: unfinished_effect`) because its outcome cannot be verified; at the deadline the run already fails as a timeout. The final assistant message becomes the summary. Reasoning entries are dropped on receipt and never persisted.
8. **Stop:** the supervisor closes standard input, which lets Vibe clean up (a termination signal skips its cleanup), waits briefly, kills the process group if needed, verifies termination, then deletes the private directories. A stop on cancel or deadline first sends `turn/interrupt` for the current turn and waits a short grace period. Every stop request (cancel, close, forced termination, deadline, budget stop) revokes the approval handler first, so a callback that arrives afterwards is answered deny without consulting the policy.

## Review

A review requires a canonical workspace beneath an explicitly configured allowlist. The starter allowlist is empty. Before launch, the supervisor snapshots source integrity (see Review snapshot cost below). Vibe's model receives `read_file` only as a usable tool. There is no search or listing tool, so when the workspace is a Git repository the supervisor puts a bounded listing at the start of the prompt: the output of `git ls-files -z --cached --others --exclude-standard` (fixed arguments, no shell, run in the workspace with the supervisor's hardened Git settings, a 10 second timeout and an 8 MiB output cap), as relative paths, sorted, one per line. Paths the approval handler would deny are left out: anything with a `.git`, `.vibe`, `.agents` or `.vibeignore` component and secret-file names (`.env*`, `.envrc*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`) and anything matching the [`excluded_globs`] of any allowed root that contains the workspace, each anchored at its own root,(reference.md#excluded-paths), as are names with control characters or a replacement character, so a file name cannot add lines to the prompt. The listing holds at most 1000 files and 32 KiB; past either limit it ends with an explicit line saying how many files were not shown. Only names are listed, never content, and listing a file does not approve it: every read still passes the approval handler. Outside a Git repository, or if Git fails or exceeds its bounds, the listing is left out (with a `file_listing_unavailable` diagnostic unless the directory is simply not a repository) and the worker reads only paths it is given or can guess. Validated `context_files` follow the listing as approved context paths, so a review task should still name the files that matter. Write tools are visible and refused as described above. The final result records whether source integrity remained verified, changed, or could not be established. `completed` means the worker ended; the coordinator must inspect the stop reason, warnings, integrity and final answer.

## Edit

An edit requires the root of a Git repository and a named base ref. The supervisor creates a detached worktree and launches the one-shot task there. The prompt carries the same bounded file listing as a review, taken from the worktree, so the worker can find files it has not been told about; reading and writing stay subject to the approval handler. It exports a patch, file inventory, and bounded transcript/artifacts. It never applies, stages, commits, merges, or pushes the patch. The coordinator reviews a fresh export and verifies it in a separate copy before deciding whether to integrate the change.

The export and the cleanup checks read a private copy of the worktree index, so index flags in the user's repository cannot hide a change: `core.ignoreStat` and split index are turned off for every supervisor Git command, assume-unchanged bits are cleared, and skip-worktree bits are cleared for every file present on disk (an absent sparse-checkout entry is not reported as deleted). The copy is rewritten once before the diffs so unchanged files are hashed once rather than by every command. Neither the source repository's index nor the worktree's own index is modified.

## Settlement and close

Settlement records one final state. The active slot and owned handle are released only after backend close verifies termination. If close fails or times out, the run stays inspectable, its handle and slot remain owned, and the close response reports `worker_termination_unverified` with `VSUP_BACKEND_ERROR`; a second run cannot take that slot. Deadline, no-progress, output overflow, cancellation, provider error, shutdown and late process callbacks cannot reopen a settled run or replace its result. Deadlines and output limits are bounded. The reaper stops the worker's process group when the supervisor disappears or the run deadline plus its margin passes.

Outcomes come from the turn status, its stop reason and error code, and the limits the supervisor itself detected, which take precedence.

| Observed | State | `stop_reason` or error |
|---|---|---|
| Turn ended normally | `completed` | `end_turn`; a warning if no final message exists |
| Vibe's iteration limit, or the supervisor's model-call backstop | `completed` | `turn_limit`, with an incomplete-result warning |
| `limits.max_tokens` crossed | `completed` | `token_limit`, with the warning |
| `limits.max_cost_usd` crossed | `completed` | `price_limit`, with the warning |
| The model declined (error code `refusal`) | `completed` | `refusal`, with a warning that the result is not a review or an edit |
| `vibe_close` or cancel | `cancelled` | `cancelled` |
| Run deadline, or no progress | `failed` | `VSUP_TIMEOUT`, `VSUP_NO_PROGRESS` |
| Provider rejected the key | `failed` | `VSUP_AUTH_REQUIRED` |
| Rate limit | `failed` | `VSUP_RATE_LIMITED`, retryable |
| Context or response too long, or stop reason `length` | `failed` | `VSUP_OUTPUT_LIMIT` |
| Unapproved allowed effect (including one whose input differs from what was approved), unknown history entry, event gap, unsafe session handoff, usage counter going backwards, cost ceiling without a price, unparseable message | `failed` | `VSUP_BACKEND_ERROR`, `details.reason` names the cause |
| A limit stop whose final history audit could not run or finish | `failed` | the audit's own error, else `VSUP_BACKEND_ERROR` with `details.reason: audit_unavailable`; never a clean `completed` |
| Server exited or its stream closed | `failed` | `VSUP_BACKEND_CRASHED` |
| Any other error code | `failed` | `VSUP_BACKEND_ERROR` |

A protocol failure recorded earlier (a malformed or unrecognized message, an event gap, a counter fault, an approval the handler could not process) is not overwritten by a later cancel or deadline: the run fails with that error, its message says the run was also cancelled or reached its deadline, and `details.also` lists the stop requests. A plain deadline or cancel with no earlier protocol failure keeps its own outcome.

The settled outcome is kept as the record's `execution_state` when close moves `state` to `closed`, so a closed run still shows whether it completed, failed or was cancelled; a record written without that field reports `unknown` in exports. The record's `started_at` is the first time the run was observed running. See [workflow acceptance](workflow-acceptance.md#execution-lifecycle-and-reasoning-observations).

A limit stop means execution ended at its budget, not that the task succeeded. The supervisor does not retry, continue, or raise the budget. A stop reason Vibe reports that the supervisor does not know is recorded as `completed` with that text and the incomplete-result warning; read it before trusting the answer.

Closing a live run cancels its process group and accounts for worktree creation that is already in flight. Worktree deletion requires the expected canonical run-owned path, validated Git registration, a fresh export matching the saved artifact, and an inventory showing the worktree is pristine. Dirty or uncertain worktrees are retained with an explicit path and reason so the coordinator can review the exported patch. Cleanup is admitted by the root recorded when the run started, not by the current allowlist. Removing a root does not stop a run already admitted there: it runs to its normal end, stays readable and closable, and its verified pristine worktree can still be removed; a dirty or uncertain one is retained exactly as before. Saved PIDs alone never authorize termination, and saved mutable worktree metadata alone never authorizes deletion.

A retained worktree stays registered in the source repository under `.git/worktrees/`. If you run `git worktree prune` or delete the directory yourself, verified cleanup refuses it permanently, because the registration it checks no longer exists, and the run directory is kept. Recover manually: read the exported patch from the run's artifacts, call `vibe_close` without cleanup (or use `vibe-supervisor runs cleanup`, which lists each retained worktree with the exact `git -C <source> worktree remove <path>` command, each path single-quoted for a POSIX shell), then remove or prune the worktree yourself with Git. The supervisor never force-deletes retained data.

Git operations are bounded separately: queries such as `rev-parse` and `ls-files` have a 30 s bound, while worktree creation, patch export and verified cleanup have a 5 minute bound so large repositories can be checked out. The exported patch is capped by `limits.max_artifact_bytes`. Exceeding a bound fails with `VSUP_TIMEOUT` or `VSUP_OUTPUT_LIMIT` and `details.operation`, including during worktree creation and base ref resolution. A missing `git` executable stays `VSUP_GIT_REQUIRED`; a worktree directory that no longer exists is `VSUP_ARTIFACT_ERROR` with `details.kind: workspace_missing`.

### Review snapshot cost

The integrity snapshot hashes the content of every file Git can see (tracked, plus untracked files not ignored) and only stats everything else, such as ignored trees like `node_modules`, skipping `.git`. It runs at launch and again at settle. Large ignored trees cost stat time at both ends. The snapshot is capped at 200,000 files and 2 GiB of hashed content; past either cap integrity is reported as `unverified` rather than failing the review. Keep large generated trees out of the reviewed workspace, or accept `unverified`.

On server shutdown, the supervisor allows a primary 10-second graceful drain and then retries termination through each live owned handle. Individual cancel and forced-termination attempts are bounded, but there is no fixed overall exit guarantee while termination remains unverified. Unresolved workers retain their handle, slot, worktree and owner lock; pending initialization and in-flight Git/worktree writes also remain accounted for under that lock. The lock is released only after all owned work is accounted for.

When `serve --stdio --isolated` receives `vibe_status`, `vibe_result` or `vibe_close` for a run outside its currently selected session directory, it searches the same private `mcp-sessions` namespace for that UUID. It routes only when exactly one safe run directory matches; the existing manager validates its saved record during recovery. The owning lock is acquired before that manager loads the store; live owners, unsafe paths, duplicate UUIDs and namespaces over the scan limit fail closed. The temporary manager uses the current server's boot-bound settings, applies the same frozen-admission cleanup rule, and is shut down after the operation. New runs always stay in the current session. This lookup does not search other config roots or identify which desktop connection originally created a run.

## Restart and saved data

On startup, active records from an interrupted one-shot run are made inspectable and marked failed with an interruption diagnostic. Before the server accepts work, recovery also deletes each such run's private directories (`child-home`, `vibe-home` and `tmp`), because a crash can leave Vibe's throwaway session store there. The old worker may still be alive when the server restarts: its reaper only notices the dead supervisor within a few seconds and then terminates the group. Recovery therefore waits, once for all runs and at most 6 seconds, before it deletes a directory, unless the run's recorded deadline plus the reaper margin has long passed or no private directory exists; it never signals a process to speed this up. If a directory cannot be deleted, the saved result carries a warning that private Vibe state remains in the run directory, and the retention sweep is not relied on to remove it. The isolated UUID lookup applies the same recovery when it temporarily opens a unique older session. Startup and lookup do not launch Vibe, load a session, replay a task, restore a grant, or signal a PID from a saved record. 2.0 makes no migration or cleanup contract for data saved by 1.x or by an older ACP installation; use the corresponding older executable for that data.

Runs, events and artifacts are persisted privately and bounded by configured limits and retention. The supervisor uses atomic writes, owner locking, fresh path validation and explicit child environment filtering. The credential lives only in the worker's environment, never in a task, event or artifact, and raw provider output and secrets are filtered from saved artifacts.

Reasoning stays off disk by construction rather than by a switch, because Vibe has none. Session logging is off, so Vibe's session store is a throwaway directory under the run's private `TMPDIR`; thinking is turned off; reasoning entries received over the wire are dropped before anything is written; the supervisor never reads the store; and the private directories are deleted at close and by restart recovery. Whether thinking off stops the model from generating reasoning is a target observation, not a local guarantee. What the supervisor can see is counted: at the end of the turn a `reasoning_observation` diagnostic records how many structured reasoning entries were dropped from the stream (`streamed_entries`) and from the audited history (`history_entries`, null without an audit), and whether that audit completed without a fatal error (`history_audited`); counts only, never content.

## Events

Besides `message` (the final answer) and `diagnostic`, a run records these events, each with bounded, redacted fields:

| Event | Fields | Meaning |
|---|---|---|
| `tool_call` | `name` (`read_file`, `write_file`, `edit`), `tool` (Vibe's wire name), `kind`, `outcome: executed`, `entry_id`, `path` | An approved, executed call on the profile. |
| `tool_denied` | `tool`, `outcome`, `reason`, `entry_id`, `path` | A call that did not run. `outcome` is `permission_denied_by_handler` when the supervisor's handler answered deny (`reason` is its reason, such as `tool_not_in_profile`, `path_outside_workspace`, `path_secret`, `path_excluded` (a match of a containing root's `excluded_globs`), `outside_allowed_write_paths` (an edit's write outside its declared `allowed_write_paths`) or `decision_deadline`), or `permission_denied_by_policy` when Vibe itself denied it before any approval request (for example a denylisted path, which includes a merged exclusion), in which case `reason` repeats the outcome. |
| `timeout` | `timeout_seconds` | The run exceeded its configured timeout and is failed with `VSUP_TIMEOUT`. |
| `review_integrity` | `status` (`verified`, `changed` or `unverified`), `write_tool_observed`, `changed_paths`, `changed_paths_total`, `reason` | The end-of-run comparison of the source workspace with its launch snapshot, recorded for a review when the status is not `verified` or a write tool was seen. Severity is error only when the source changed and a write tool was observed. |

The supervisor counts these outcomes as it records them and saves the counts with the run as `usage.tool_calls` (`executed`, `denied_by_handler`, `denied_by_policy`), beside the token and model-call numbers and the ceilings in force ([reference](reference.md#usage-ceilings-and-tool-call-counts)). The counts are the supervisor's audited outcomes, not Vibe's own tool statistics. The handler's decisions are also saved per run as the [approval ledger](workflow-acceptance.md#approval-ledger-and-pin-identity).

`vibe_status` shows a `tool_denied` event as `<tool>: <reason>`. The wire names are `file_system.read_file`, `file_system.write_file` and `file_system.search_replace`. A denied write in a review is expected policy, not a failure; it shows that the worker tried a refused action. Three consecutive denials of shell or network tools with no executed call between them stop the run as failed (`details.reason: repeated_unsafe_denials`); a tool counts as shell or network when a word of its name, split at any non-alphanumeric character, is one of `bash`, `shell`, `terminal`, `command`, `exec`, `network`, `http`, `https`, `web`, `fetch`, `url`, `download`, `curl` or `browser`, so `terminal.run_command`, `web.fetch` and `web_search` count and `file_system.search_replace` does not. Supervisor `diagnostic` events carry a `reason`, listed in [compatibility](compatibility.md#diagnostic-reasons).

## Configuration and preparation

Select a config with `--config`; otherwise resolution uses `VIBE_SUPERVISOR_HOME`, then the platform default root. Explicit invalid or missing configs fail without fallback. That selection is made once, before `--isolated` switches to a private session directory, and stays the policy source for the life of the connection; the session's copy of `config.toml` is an audit record only. Once serving, a missing selected file fails closed even where startup could have used defaults. Removed keys such as `backend`, `max_concurrent_runs`, idle-session TTL and ACP executable paths are rejected, and `paths.vibe_pin_manifest` is required for runs. A missing `paths.vibe_pin_manifest` is the one problem the commands that repair it tolerate: `pin-manifest`, `allow`, `doctor`, `runs` and `serve` read the file without that key (every other check still applies), so the missing path never blocks its own repair. `serve` starts, but every readiness check and start rereads the file strictly and fails with `VSUP_CONFIG_INVALID` naming `paths.vibe_pin_manifest` and the repair; after the path is set and the manifest written, restart the server, because the path is boot-bound. The config, doctor provenance, data directory and already-open client handshake are separate facts.

Select the existing immutable committed base and pass it as `base_ref`; preserve unrelated uncommitted source changes. Uncommitted bytes are not an edit base.

The supervisor's path checks, session configuration, approval handler and Vibe tool configuration are application policy. They are not a kernel or process sandbox. A worker's account permissions and any content included in its allowed workspace remain relevant.

## Managed configuration isolation

Each worker receives an owned loopback `vibe_base_url` serving only a disabled managed policy; remote admin configuration is excluded ([ADR 0005](adr/0005-target-conformance-repairs.md)). The endpoint is validated through effective read-back before a turn and closed during cleanup. The inference provider endpoint and five MCP operations are unchanged. Nullable harness-selection provenance is accepted; actual unified-harness identity remains required.

## Bundled Vibe skills

Pinned Vibe 3.0.2 bundled plugin skills are permitted by owner decision ([ADR 0006](adr/0006-bundled-vibe-skills.md)): `vibe:create-plugin`, `vibe:skill-creator`, `vibe:vibe`, `vibe:worktree`. The runtime read-back requires plugin source, builtin scope and no registry reference, and rejects unknown or duplicate names; the `config/read` skill count above counts root user and project skills, which stay disabled, so it must still be 0. User/project/registry skills remain disabled. Skills are guidance; their instructions do not authorize tools, paths, shell or network access. The exact review/edit file-tool profiles and approval handler remain unchanged.

## Artifact acceptance and reproducible validation

The server always registers exactly five tools. Edit start may freeze an [acceptance contract](workflow-acceptance.md); automated checks evaluate exact exported bytes separately from execution and coordinator assessment. Close accepts append-only assessment corrections. Read-only `runs verify` and `runs export` produce sanitized reports and optional patch/projected-event artifacts, and an export adds the run's approval ledger and pin identity when it has them. `runs usefulness` counts accepted and rejected edit runs from those assessments ([workflow acceptance](workflow-acceptance.md#measuring-usefulness)); reviews are not assessable.

[Version-matched preparation](preparation.md) is now a dispatch gate: workspace eligibility alone is insufficient. Native readiness reports candidate identity, preparation state and optional expected-candidate mismatch. Runtime pin verification remains independent at launch. Model observations and detailed usage are reported where exposed; unknown identities, costs and phase boundaries stay unknown. [Validation preparation](validation-workspace.md) creates independent owned copies and pinned offline dependencies without running project checks or integrating output.
