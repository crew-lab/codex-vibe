# Functionality

Codex Vibe exposes a local Model Context Protocol (MCP) server that delegates code review and editing tasks to Mistral Vibe. The supervisor manages workspace access, worker processes, run state, and result artifacts. A client starts a run, waits for it inside a tool call, and retrieves the outcome.

## Review and editing

**Review runs** read an allowed workspace using Vibe's `read_file` and `grep` tools. They produce a public response and recorded events. The supervisor compares the source workspace before and after the run. A change during a review does not fail the run: it adds a warning to the result that findings may not match the current files, and artifacts are still written. The review profile does not enable editing, shell, or network tools. Optional `context_files` identify approved context paths for the task.

The programmatic backend does not put the task on the Vibe command line. The supervisor writes it to an owner-only (0600) `task-prompt.txt` in the private run directory and passes only that path to the launcher shim in `VIBE_SUPERVISOR_PROMPT_FILE`. The shim removes the variable, verifies the file (absolute path inside the run directory, regular non-symlink file owned by the user, no group or world access, at most 4 MiB, UTF-8), deletes it, and supplies `--prompt` to Vibe through its in-process `sys.argv`, so the task is not visible in `ps`. Any failed check aborts the launch. ACP sends the task over the protocol and is unchanged. The real Vibe run of this path is unverified; the task is still held in process memory and in Vibe's own redacted session records.

**Edit runs** require a Git repository. The supervisor creates a detached worktree from `base_ref` (default: `HEAD`) and enables `read_file`, `grep`, `write_file`, and `edit` there. The worker edits that worktree, leaving the source checkout unchanged. Exported changes are relative to the chosen base; callers should not assume uncommitted source changes are copied into the worker.

Edits produce a patch for inspection. The supervisor does not apply patches to the source checkout, commit changes, merge branches, or push to a remote. `allow_shell: true` is rejected because a certified operating-system sandbox is not available.

## MCP tools

The server runs over stdio, with protocol frames on stdout and diagnostics on stderr. Tool inputs use strict schemas: unknown fields are rejected. Run IDs are UUIDs returned by the start tools.

| Tool | Function and principal inputs |
|---|---|
| `vibe_review_start` | Start a review with `task` and `cwd`; optionally provide `context_files`, `backend`, `max_turns`, `timeout_seconds`, and `wait_seconds`. |
| `vibe_edit_start` | Start an edit with `task` and `cwd`; optionally provide `base_ref`, `backend`, `max_turns`, `timeout_seconds`, and `wait_seconds`. Keep `allow_shell` false. |
| `vibe_status` | Read state and bounded events for `run_id`. Use `after_seq` to fetch subsequent events, `max_events` (default 10) to limit the response, and `wait_seconds` (0 to 300) to block until an event, state change, pending request, or a state needing action. Once the run is `completed`, `failed` or `cancelled` the reply also embeds the compact result as `result` (the `vibe_result` compact shape with `next_action`); an unsettled run has none. |
| `vibe_continue` | Send a follow-up `message` to a run whose ACP session supports continuation. |
| `vibe_respond` | Answer the current `request_id`: select an offered `option_id` for a permission request, or accept, decline, or cancel an elicitation request. |
| `vibe_result` | Retrieve the summary and artifact references for `run_id` (a settled `vibe_status` already embeds the compact form, so call this for `detail: "full"` or the transcript); `detail` is `compact` (default) or `full` (`summary` is deprecated and returns the full shape with a `deprecation` field); optionally set `include_transcript`. |
| `vibe_cancel` | Request cancellation and terminate the managed worker. |
| `vibe_close` | Close a run; optionally request verified worktree removal with `cleanup_worktree`. |

See [protocol.md](protocol.md) and `src/mcp/schemas.ts` for the protocol and exact input constraints.

## Typical workflow

1. Configure the workspace allowlist, build the project, and start the MCP server.
2. Call a start tool. For example, this is a review tool's input:

   ```json
   {
     "task": "Review the authentication module for correctness and report findings.",
     "cwd": "/absolute/path/to/allowed/repository",
     "backend": "programmatic"
   }
   ```

3. Save the returned run ID. Without `wait_seconds` a start returns at once; with it (for example 120 to 300) the start call waits until the run needs action and then includes the compact result if the run has finished. Otherwise call `vibe_status` with `wait_seconds` repeatedly instead of polling turn by turn; the call that sees the run settle already returns the compact result.
4. For an ACP run waiting for permission or input, inspect the current request before calling `vibe_respond`. Unknown, expired, or unsafe responses fail closed.
5. Read the `result` embedded in `vibe_status` (or in the start reply) when work completes, fails, or is cancelled; fetch `vibe_result` only for `detail: "full"` or the transcript. Inspect `stop_reason`, warnings, the summary, and any available edit patch. A `completed` run whose `stop_reason` is not `end_turn` stopped early; the supervisor derives the summary from the stop reason when the backend gave none (turn limit, token limit, refusal, cancelled turn, or an unknown reason) and adds a warning naming the stop reason. A backend-supplied summary is kept. On a continuation, the summary, `stop_reason` and stop-reason warning always reflect the latest turn, while other warnings such as review integrity carry over.
6. Close the run. Worktree removal is optional and is refused if the saved patch no longer matches the worktree or residual files cannot be safely accounted for. The result says which happened: see "Closing and worktree cleanup".

## Run lifecycle and recovery

Runs enter a queue, start a worker, and advance through backend initialization to execution. ACP runs may pause in `waiting_permission` or `waiting_input`. Normal outcomes are `completed`, `failed`, or `cancelled`; closing releases worker resources and records `closed`.

The default capacity is two active runs and eight queued runs. Configured turn counts, deadlines, output limits, and idle lifetime bound work. The `timeout_seconds` deadline counts from the moment a run launches, not from when it was queued; queued runs have no deadline timer. State, sequenced events, and public transcripts are persisted in private run directories. A data-directory owner lock prevents two supervisors from managing the same storage concurrently.

One supervisor owns one data directory. The lock file `supervisor.lock` records the owner's PID, a token and the time it was taken. A second supervisor on the same directory refuses to start with `VSUP_INVALID_STATE`, naming the lock path and owner PID in the message and in `details` (`lock_path`, `owner_pid`); the remedy is to stop the other process or to give each Codex session its own `VIBE_SUPERVISOR_HOME`. A lock is taken over only when its owner is provably gone: the PID no longer exists, or the PID is alive but its process start time (computed once as now minus the elapsed time from `ps -o etime=`, only when a lock already exists, so no time zone is involved) is more than 5 seconds later than the lock's timestamp, which means the PID was reused. If the start time cannot be read the lock is treated as live, and the supervisor never signals the PID. The takeover runs under a short-lived `supervisor.lock.recovery` guard; a guard older than 30 seconds is stale and is claimed once by renaming it to a unique name; only the acquirer whose rename succeeded proceeds, a claimed file that turns out to be another acquirer's fresh guard is put back, and a guard that was not created or claimed by the caller is never removed. An empty or unparsable lock younger than 2 seconds is re-read every 250 ms up to four times, because its owner may still be writing it; after that it is reported as malformed and left for manual inspection. `doctor` reports the holder in its `lock` check and never removes the lock.

After a restart, the supervisor reads saved records and never starts a process, loads a session, hashes a workspace or exports a patch while doing so. A run that was `queued` or `starting` was never submitted and becomes `cancelled` with `VSUP_CANCELLED`. Any other unfinished run becomes `recoverable`: without an error when it has a saved ACP session and the backend advertised `loadSession`, and with `VSUP_SESSION_NOT_RESUMABLE` otherwise (programmatic runs, or no saved session). A pending permission or input request cannot survive a restart, so it is cleared and recorded as `VSUP_REQUEST_EXPIRED`. These transitions write `meta.json` and a minimal `result.json` (no integrity record, no artifacts) and hold no run slot, so a large backlog of recovered runs costs nothing until one is continued. `vibe_continue` handles `completed`, `ready` and `recoverable` runs the same way: it needs a free run slot (`VSUP_LIMIT_EXCEEDED` otherwise), lazily loads the saved session with `session/load` (replayed updates are suppressed) within 30 seconds, moves the run to `running`, restarts its `timeout_seconds` deadline from that moment and sends the new message. If the session cannot be loaded, because the backend cannot resume it, its process exits or the load does not answer in time, the process is terminated, the slot is released, the call fails with `VSUP_SESSION_NOT_RESUMABLE` and a `recoverable` run records that error; a load that does not answer within 30 seconds says so ("Vibe did not finish loading the session within 30 seconds.") instead of reporting the load as unsupported; a late result from the abandoned load cannot change the run. A recovered run that finishes goes through the normal end-of-run path and the idle lifetime and cap. The original task is never automatically resubmitted and pending requests are never restored; a recovered session needs explicit continuation.

If the live session of a `completed` ACP run turns out dead when `vibe_continue` arrives (its process exited while idle), the supervisor drops that handle and reconnects with the same lazy `session/load` within the same call, so the continuation reaches `running` and finishes normally. Without `loadSession` support the call fails fast with `VSUP_SESSION_NOT_RESUMABLE` and releases the slot instead of waiting for `VSUP_TIMEOUT`.

After an ACP turn completes, its session stays live for `worker_idle_ttl_seconds`, and at most `max_concurrent_runs` completed sessions are kept live at once; the least recently completed idle session is closed first (recorded as an `idle_evicted` or `idle_expired` event) while the run stays `completed`. Completed runs found after a restart are not reloaded at startup; `vibe_continue` lazily reloads the saved session, which needs a free run slot. Closing or cancelling a run never turns a completed run into `failed` because of the backend process exiting afterwards. A backend-reported state change that is invalid for the run's current state is ignored and recorded as a `diagnostic` warning event with `reason` `ignored_backend_state_transition`, the reported and current states, and a redacted, bounded message. Programmatic runs cannot resume an interactive session; saved records remain available for inspection.

A review snapshots the source workspace at launch, keeping a manifest in memory, and compares the workspace with it when the run ends. The launch snapshot runs while the backend is selected, and Vibe is never started before it resolves. The manifest records, for every entry except the root `.git`, its kind, size, modification time in nanoseconds, inode, mode and symlink target (directories only by presence), scanned with 32 concurrent stat calls. Content is hashed (SHA-256) only for files Git can see (tracked, or untracked and not ignored, from `git ls-files --cached --others --exclude-standard`); a root that is not a Git work tree is compared by stat only. At the end of the run an added or removed path, or one whose stat changed, is reported as changed, except that a Git-visible file whose stat changed but whose mode and content hash are unchanged (a touch or same-content rewrite) counts as unchanged. A write to an ignored path (such as `node_modules/`) is detected only through stat, so a write that preserves size, mtime and inode (for example restoring the timestamp afterwards) is a blind spot; Git-visible files are hashed, so they have no such blind spot. The 200,000-entry cap counts all entries, and the 2 GB cap counts hashed bytes only. The result carries an `integrity` object: `status` is `verified` (nothing changed), `changed` (with `changed_paths`, up to 50 relative added, removed or modified paths, and `changed_paths_total`) or `unverified`, plus `write_tool_observed`, which is true when the run's own `tool_call` or `tool_call_update` events show a write-capable call (kind edit, delete or move, or a `write_file` or `edit` title or name). A changed workspace is a warning, not a failure, and the run state is unchanged. A continuation drops the previous turn's integrity record (and its integrity warnings) when it starts, so every settled turn, including one that is cancelled or times out, is assessed again against the launch snapshot. With a write tool observed the warning is "Possible read-only boundary violation: the review worker issued a write-capable tool call and the source workspace changed. Inspect the changed paths before trusting the review." Without one it is "The source workspace changed during this read-only review. The changes may be your own edits or a read-only boundary violation; inspect the changed paths before trusting the review." If a snapshot cannot be taken (more than 200,000 files, more than 2 GB, or an unreadable entry) the review still proceeds with status `unverified` and the warning "The source workspace could not be snapshotted (too large or unreadable); review integrity was NOT checked, so a read-only boundary violation would go undetected." Anything other than `verified`, or a verified run with a write tool observed, also appends a `review_integrity` supervisor event carrying the integrity object, with severity `error` when the workspace changed and a write tool was observed and `warning` otherwise. The manifest is not persisted (only a digest of it, `workspace_snapshot_sha256`, is), so a run recovered after a restart can report `changed` without paths, including after a mere touch. Every path that moves a run to `failed` (backend-reported failure, artifact finalization failure, deadline, output limits, launch errors) releases the worker process and session handle once; a failed run never keeps a live worker.

### Closing and worktree cleanup

An edit run's `worktree` record is written only after `git worktree add` succeeded; until then the requested `base_ref` travels in memory, so a run whose worktree could not be created has no worktree to retain and ordinary retention can remove it. Creation failures are `VSUP_WORKTREE_CREATE_FAILED` with the tail of git's stderr (redacted, at most 1 KiB) in `details.stderr_tail` and the failed git operation in `details.operation`: an unknown `base_ref`, a directory that is not a repository, a target path that already exists. `VSUP_GIT_REQUIRED` is reserved for a missing git binary. A queued edit run cancelled before launch finalizes like any other run (its `result.json` lists the transcript and event log and no patch).

`vibe_close` always ends with the run `closed`; a refused cleanup, or a step that fails after the run began `closing` (for example the backend's close), never leaves it half-closed: the run still reaches `closed` and the response carries the failure as `error` while a `diagnostic` event with `reason` `close_failed` records it. The response carries `worktree_removed`. With `cleanup_worktree: true` the supervisor first exports the worktree through the normal artifact path when the run has no saved `diff.patch` (for example a `starting` run found after a supervisor crash that had already created its worktree), and then removes it only when a fresh export of it matches the saved `diff.patch` digest, the path is a registered supervisor-created worktree, and no ignored files remain. When it refuses, `worktree_removed` is `false`, `worktree_retained_reason` says why (bounded to 400 characters) and a `diagnostic` event with `reason` `worktree_retained` records the same text; the worktree stays on disk and in the record. After a restart the digest is taken from the `diff.patch` artifact saved in the run directory (its path must be `artifacts/diff.patch` under that run, and the file is hashed again before it is trusted), so a tampered patch still refuses. Closing a `closed` run again with `cleanup_worktree: true` retries only the removal, for example after deleting the ignored files that blocked it; `runs cleanup <run-id>` reports the same fields, but acts only on a `failed`, `cancelled` or `closed` run: for any other state, such as `completed` or `recoverable`, which may still be continued, it returns `worktree_removed: false` with a `worktree_retained_reason` naming the state and touches nothing. Closes of one run are queued: a second `vibe_close` while the first is still in progress waits for it and then reports the real outcome, retrying the removal when it asked for `cleanup_worktree`. `vibe_cancel` on a closing run changes nothing. A run found `closing` after a supervisor crash becomes `closed` at startup. The retention sweep (`runs cleanup` without an ID) treats a record whose worktree path no longer exists as having no worktree.

### How a run ends

Every end of a run goes through one routine that always runs in the same order: close the transcript turn, assess review integrity, write the artifacts and `result.json`, record the state, then release the backend session (or schedule idle expiry after `completed`), and finally release the run slot and wake waiting callers. The slot release and waiter notification happen even when an earlier step throws, so a failed step cannot leak a slot or block the queue. This applies to backend-reported completion, failure and cancellation, `vibe_cancel`, the deadline, output limits, a policy violation, launch errors, and shutdown (which records `recoverable`, or `cancelled` with `VSUP_CANCELLED` for runs still queued).

When the supervisor itself decides the outcome (timeout, output limit, policy violation, user cancellation) that outcome is recorded before the backend is asked to stop, and it wins over a `cancelled`, `failed` or even `completed` state the backend then reports while stopping, and the deadline's `timeout` event is recorded before the backend is asked to stop. `result.json` and `meta.json` therefore agree on the final state. Review integrity is recorded for every review run that launched and took (or failed to take) a launch snapshot, including failed and cancelled runs; a queued review that never launched has none, and shutdown, which only suspends the run, does not assess it. A run that already `completed` is never moved to `failed` by a later backend report; such a report only releases the session. If artifact finalization fails, a completed turn becomes `failed`; for every outcome a minimal `result.json` with an "artifacts could not be finalized" warning is still attempted.

### Honest failure reporting

An ACP process that exits with status 0 before the prompt response arrived does not complete the run: it fails with `VSUP_BACKEND_CRASHED` ("Vibe ACP exited before the turn finished"), including for a recovered session after it became ready. Only the prompt response yields `completed`; a process that exits 0 while idle changes nothing. The programmatic backend still reports `end_turn` (it has nothing better), but an empty or whitespace-only final message adds the warning "Vibe produced no final message." and the summary falls back to the generic completion text, the same as when the backend gave none.

When the backend is chosen explicitly there is no availability probe: the same version, executable and interpreter errors come from the real start (`VSUP_VIBE_VERSION_UNSUPPORTED` from ACP's `initialize` or the launcher shim's stderr message, with `detected_version` but no `details.candidates`). Only `auto` probes. Every launch failure appends a `diagnostic` supervisor event (`reason` `launch_failed`, a redacted `message` of at most 500 characters) before the run settles as `failed`. When no backend can be selected the error says why instead of a generic unavailability: `VSUP_VIBE_VERSION_UNSUPPORTED` names the detected and the supported version when a probe saw another one; `VSUP_VIBE_NOT_FOUND` or `VSUP_VIBE_ACP_NOT_FOUND` only when every probed executable itself does not exist; a launcher whose interpreter is missing (its shebang interpreter, or `python3` for `#!/usr/bin/env python3`) is reported as `VSUP_BACKEND_UNAVAILABLE` naming the interpreter; otherwise `VSUP_BACKEND_UNAVAILABLE`. All three carry `details.candidates`, one entry per probed backend with its `reason`, and `detected_version` or a redacted `stderr_tail` when known. A start that fails before its session is ready (spawn, initialization, wrong mode or trust state) forgets the cached successful probe, so the next run probes again instead of failing until the 10 minute cache expires.

`vibe_status` events normally carry only `seq`, `type` and tool-call `title`, `kind` and `status`. Supervisor events of type `diagnostic`, `review_integrity`, `timeout` and `permission_denied_by_policy` also carry `text`, the event's own `text`, else `message`, else `reason`, redacted and at most 400 characters, so a failing run explains itself without reading `events.ndjson`. Events from Vibe or ACP never carry `text`, and no other event data is returned. A failed `test-acp` or `doctor` ACP check prints the probe's redacted stderr tail (at most 1 KiB, also `stderr_tail` in the JSON). A connection error that happens after the ACP session is ready is `VSUP_ACP_PROTOCOL_ERROR`; before that it is `VSUP_ACP_INIT_FAILED`, and an authentication failure (401, unauthorized, missing API key) is `VSUP_AUTH_REQUIRED` in both phases.

### Storage errors

Events are buffered in memory per run and appended to `events.ndjson` in one write, with at most one `fsync` per 100 ms. The in-memory events that `vibe_status` returns are always current, but a crash can lose up to the last 100 ms of events; the file always holds a valid, ordered prefix and a torn final record is dropped on the next load. Pending events are flushed and synced before every run-state save, before a pending request becomes visible, before artifacts are finalized, before a `vibe_result` read, and on shutdown, so a saved state is never ahead of the events that preceded it. The run directory is verified once per run and the events file is opened without following links and must be a regular file. The `max_event_bytes` limit counts buffered bytes, so it still fails the run with `VSUP_OUTPUT_LIMIT`. A failed flush degrades the run exactly like a failed state save and is retried every second while events remain buffered.

Startup reads only each run's `meta.json`. A run's events and transcript load on first use (`vibe_status`, `vibe_result`, `vibe_continue`, finalizing a run, or appending an event), once per run even for concurrent calls, so a data directory with many large logs starts quickly. A torn final event record is truncated at that point.

Retention runs automatically: once shortly after the server begins serving stdio (never before initialization finishes) and then every 24 hours. It removes terminal runs older than `retention.days` that have no worktree, keeping failed runs while `preserve_failed_runs` is true, and also `completed` runs older than `retention.days` whose backend session is not live, closing them first. A run with a worktree, a live session, a held run slot, or a pending request is never removed. `runs cleanup` performs the terminal-only sweep on demand.

Filesystem faults while saving run state, events or artifacts (`ENOSPC`, `EACCES`, `EPERM`, `EROFS`, `EIO`, `EDQUOT`, `EMFILE`) surface as `VSUP_STORAGE_ERROR` with `details.code` (the errno) and `details.directory` (the parent directory of the failed path); file content is never included. Each errno has its own message (disk full, quota exceeded, permission denied, read-only file system, I/O error); `EMFILE` says the process ran out of file descriptors and advises raising the open-file limit. The first save when a run starts propagates the error to the caller and no run is created. Later state changes keep the in-memory state, which is what actually happened, instead of reverting it: the run is marked storage-degraded, `vibe_status` returns a `warnings` entry naming the errno and directory until both a run-state save and an event append have succeeded since the last failure, and the run still releases its slot so other runs continue. Failures to record an event never reject the backend session that produced it.

The server process logs one redacted line to stderr for an unhandled promise rejection and continues. For an uncaught exception it logs one line, shuts the supervisor down within five seconds, and exits with status 1. Errors reaching a tool that are not supervisor errors are returned to the client as `VSUP_INTERNAL` without detail, and their redacted cause (error code or name and message, bounded to 500 characters) is written to stderr. Background tasks (deadline timers, idle expiry, queue launches, backend callbacks) log their failures the same way and, when they belong to a run, add a `diagnostic` event with `reason` `background_failure`.

## Backends

| Capability | Programmatic (default) | ACP (opt-in) |
|---|---|---|
| Review and isolated edits | Yes | Yes |
| Public response and event capture | Yes | Yes |
| Follow-up in the same session | No | Yes, when the session is available |
| Interactive permission/input responses | No | Yes, subject to supervisor policy |
| Session loading after restart | No | Conditional on advertised support and validated saved state |

Both adapters are pinned to Mistral Vibe **2.25.8** and use a private launch profile and runtime shim. Unsupported versions fail closed. ACP negotiates protocol version 1 and verifies the requested mode and workspace trust state. Selecting a backend does not establish provider authentication or guarantee successful model inference.

## Results and retained data

Compact results (the default) include state, a public summary, the review `integrity` object, up to 50 changed-file paths with a total, warnings, a diff stat, the patch inline when it is at most 4000 bytes and the whole payload fits `max_mcp_result_chars` (otherwise `patch_path` and `patch_bytes`), and artifact `name` and `path`. `detail: "full"` adds workspace paths and, per artifact, the SHA-256 digest, byte count, and media type.

- All finalized runs can expose a public `transcript.md` and sequenced `events.ndjson`.
- Edit runs additionally export `diff.patch`, `diff.stat`, and `changed-files.json`, including supported binary and untracked changes.
- MCP response size (`max_mcp_result_chars`, default 8000, and `mcp_result_format`) and transcript/event/artifact limits keep returned and retained data bounded. A failed or unfinished run may have incomplete artifacts.
- Known secret patterns are redacted and reasoning/thought fields are excluded from persisted public output. Filtering does not guarantee detection of every secret format.
- Retention defaults to seven days with failed runs preserved and runs automatically (see above). Private Vibe histories are retained for recovery and handled by supervisor cleanup.

## Boundaries and release status

The supervisor enforces application-level permissions, environment filtering, workspace validation, private homes, and bounded process termination. These controls do not provide a kernel sandbox or network firewall. Shell and network tools are disabled; enabled local file tools can send permitted source content to the configured model provider.

This is a local release candidate. Automated protocol fixtures, unit/integration tests, packaging smoke tests, and local compatibility probes have passed. Hosted inference, authenticated real-session tool inventory, a real hosted ACP soak, and Codex desktop integration remain unverified. Plugin manifests are scaffolds rather than evidence of successful installation.

For details, read [security.md](security.md), [compatibility.md](compatibility.md), [acceptance.md](acceptance.md), and [plugin-scaffold.md](plugin-scaffold.md).

## Workspace permission profiles

File tools use a literal recursive workspace grant with a `never` fallback and secret/reserved-path denials. Supervisor-generated agent definitions in each private VIBE_HOME preserve these rules after Vibe selects Plan or Accept Edits. They do not inherit user or project agents. Reviews enable only read/search; edits add write/edit in the detached worktree, with no global write permission.

## Opt-in per-connection storage

`serve --stdio --isolated` starts each MCP server with a fresh private configuration snapshot and persistent run directory. Register it using `configure-codex --user --isolated`. This allows independent clients to connect without competing for the default storage owner lock. The default remains shared storage. Configuration refresh, run ownership, retention, and explicit recovery requirements are described in [configuration](configuration.md#independent-mcp-clients).
