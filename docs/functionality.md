# Behavior

The supervisor is a local MCP coordinator for one-shot Mistral Vibe 2.26.1 runs through the `vibe-app-server` protocol: one app-server process per run, driven as a client over newline-delimited JSON-RPC on stdio. Its tools are `vibe_review_start`, `vibe_edit_start`, `vibe_status`, `vibe_result`, and `vibe_close`. A run accepts one task and fixed turn, deadline, event, transcript, token, price and artifact limits. There is no interactive permission response, continuation, queue, ACP session, idle-session retention, or automatic recovery. Run records, events and results name the engine as `backend: app-server`.

The supervisor, not Vibe's defaults, decides what the model may do. It starts the server with a supervisor-written session configuration, reads the effective configuration back before the first turn and fails the run on any mismatch, answers every approval request itself, and audits the run's history for any tool effect it did not approve. [Security](security.md#enforcement-points) lists each point. The model's tool catalogue cannot be narrowed: `write_file`, `edit`, the shell tool and `run_typescript` are listed to the model, in reviews too, and are refused when called. The model sees these tools and cannot use them; each refused call is recorded as a `tool_denied` event and the run continues.

The capacity guarantee belongs to one owning server/storage instance. The server reserves its single slot before asynchronous preparation and rejects another start with a capacity error; there is no waiting record or hidden worker. Separate isolated MCP connections can each own an instance. A second process cannot manage the same storage while the owner lock is held.

The owner lock is crash recovery, not a lease. When its owner process has exited, or its PID now belongs to a process started after the lock was written, the next server to start takes the lock over and marks that storage's interrupted runs failed. An operator never needs to delete a lock for that case. `VSUP_OWNER_LOCKED` with a live owner means another supervisor really holds the storage: stop that process, or give the connection its own storage with `--isolated` or `VIBE_SUPERVISOR_HOME`. For an unsafe or malformed lock, inspect the file in `details.lock_path`; remove it by hand only after confirming that no `vibe-supervisor` process uses that data directory.

## Readiness and admission

Every delegation should begin with `vibe_status` in workspace mode on the connection that will run the task. The check rereads the selected configuration, runs the same admission validators a start runs, reports this server's version and instance, the policy revision, boot-setting drift, the active slot and executable resolution, and lists structured blockers. It creates no run, worktree or model call. An eligible check returns a 10-minute receipt bound to this server instance, the policy revision, the operation, the canonical workspace and, for an edit, the `base_ref` and the commit it resolves to. A start that carries the receipt is rejected before launch if any of these drifted. See [workspace readiness](reference.md#workspace-readiness).

A start, with or without a receipt, reserves the slot, then rereads and validates the selected configuration before it creates a record. Allowlist changes therefore apply to the next check or start without a restart; an allowed root that disappears from disk denies only workspaces under it; changes to boot-bound settings make readiness report `restart_required` and starts fail with `VSUP_RESTART_REQUIRED`; a missing or unsafe file fails closed. The admitted `policy_revision` is saved with the run. See [policy authority](reference.md#policy-authority).

## Run lifecycle

Admission, the slot, the integrity snapshot or detached worktree, and settlement belong to the run manager and are the same for both operations. The engine adds these steps:

1. **Before spawn:** the pin check hashes the installed Vibe files against the candidate's manifest (see [compatibility](compatibility.md#the-pin-and-its-manifest)), and the credential is resolved from `MISTRAL_API_KEY` in the supervisor environment or, on macOS, the Vibe Keychain entry. Either failing refuses the start before any process exists.
2. **Spawn:** `vibe-app-server` starts with no arguments, piped standard streams, its own process group, the filtered child environment, the supervisor's `VIBE_*` settings, and a private `HOME`, `VIBE_HOME` and `TMPDIR` inside the run directory. A small reaper process, in its own group, kills the worker's group if the supervisor disappears or the run deadline plus a margin passes.
3. **Handshake and read-back:** `initialize` (declaring that the client answers approvals; the result's server version must equal the pin), `initialized`, `session/start` with the profile, wait until the session is ready, read the runtime and effective configuration back, turn thinking off, read back again. Any mismatch fails the run before the first turn with `VSUP_BACKEND_ERROR` and `details.reason: readback_mismatch`.
4. **Turn:** `turn/start` carries the task as one text block over standard input, so the task is absent from OS-visible arguments. The start call returns when Vibe accepts the turn, with the run `running`. For a run whose workspace is a Git repository, the prompt starts with a bounded file listing (see [Review](#review)).
5. **During the turn:** notifications drive status. Each statistics update refreshes `usage` (tokens, and an estimated cost in USD that is not authoritative), at most about once a second, because the server writes no run export and the supervisor rebuilds usage and cost from the session statistics and Vibe's pricing formula. A counter that goes backwards outside a handoff fails the run (`details.reason: usage_counter_regressed`) instead of being clamped to zero, and a cost ceiling with no price for the active model fails the run (`details.reason: price_unavailable`), before the first turn when the prices are already missing at startup. Each `callback/call` is an approval request; see [security](security.md#approval-handler).
6. **Handoff:** when Vibe compacts or clears the session mid-turn it announces a new session id (`session/compacted`, `session/contextCleared`). The supervisor accepts that only when no effect is unfinished and no callback is open or unanswered; otherwise the run fails with `details.reason: session_handoff_unsafe`. It then adopts the new id and watermark, remembers a fingerprint of every effect it saw settle before the handoff, pages the new session's whole history (an effect first seen there must be approved like any other, and a known effect must be unchanged, else `historical_effect_changed`), reads the runtime and effective configuration back again with the startup comparison (thinking off included), and keeps counting usage: if the new session's counters reset, the old session's totals are carried and the new counters add to them; if they kept growing, they continue. Token and cost ceilings apply to the totals across the handoff. The result gains a warning and the run a `session_handoff` diagnostic; nothing is replayed and no callback or grant is carried over. A failed re-validation fails the run and every later approval is denied.
7. **End:** the supervisor reads the final statistics and pages the whole turn history once more, so an effect it missed live is found before the outcome is decided. The final assistant message becomes the summary. Reasoning entries are dropped on receipt and never persisted.
8. **Stop:** the supervisor closes standard input, which lets Vibe clean up (a termination signal skips its cleanup), waits briefly, kills the process group if needed, verifies termination, then deletes the private directories. A stop on cancel or deadline first sends `turn/interrupt` for the current turn and waits a short grace period.

## Review

A review requires a canonical workspace beneath an explicitly configured allowlist. The starter allowlist is empty. Before launch, the supervisor snapshots source integrity (see Review snapshot cost below). Vibe's model receives `read_file` only as a usable tool. There is no search or listing tool, so when the workspace is a Git repository the supervisor puts a bounded listing at the start of the prompt: the output of `git ls-files -z --cached --others --exclude-standard` (fixed arguments, no shell, run in the workspace with the supervisor's hardened Git settings, a 10 second timeout and an 8 MiB output cap), as relative paths, sorted, one per line. Paths the approval handler would deny are left out: anything with a `.git`, `.vibe`, `.agents` or `.vibeignore` component and secret-file names (`.env*`, `.envrc*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`), as are names with control characters or a replacement character, so a file name cannot add lines to the prompt. The listing holds at most 1000 files and 32 KiB; past either limit it ends with an explicit line saying how many files were not shown. Only names are listed, never content, and listing a file does not approve it: every read still passes the approval handler. Outside a Git repository, or if Git fails or exceeds its bounds, the listing is left out (with a `file_listing_unavailable` diagnostic unless the directory is simply not a repository) and the worker reads only paths it is given or can guess. Validated `context_files` follow the listing as approved context paths, so a review task should still name the files that matter. Write tools are visible and refused as described above. The final result records whether source integrity remained verified, changed, or could not be established. `completed` means the worker ended; the coordinator must inspect the stop reason, warnings, integrity and final answer.

## Edit

An edit requires the root of a Git repository and a named base ref. The supervisor creates a detached worktree and launches the one-shot task there. The prompt carries the same bounded file listing as a review, taken from the worktree, so the worker can find files it has not been told about; reading and writing stay subject to the approval handler. It exports a patch, file inventory, and bounded transcript/artifacts. It never applies, stages, commits, merges, or pushes the patch. The coordinator reviews a fresh export and verifies it in a separate copy before deciding whether to integrate the change.

The export and the cleanup checks read a private copy of the worktree index, so index flags in the user's repository cannot hide a change: `core.ignoreStat` and split index are turned off for every supervisor Git command, assume-unchanged bits are cleared, and skip-worktree bits are cleared for every file present on disk (an absent sparse-checkout entry is not reported as deleted). The copy is rewritten once before the diffs so unchanged files are hashed once rather than by every command. Neither the source repository's index nor the worktree's own index is modified.

## Settlement and close

Settlement records one final state. The active slot and owned handle are released only after backend close verifies termination. If close fails or times out, the run stays inspectable, its handle and slot remain owned, and the close response reports `worker_termination_unverified` with `VSUP_BACKEND_ERROR`; a second run cannot take that slot. Deadline, no-progress, output overflow, cancellation, provider error, shutdown and late process callbacks cannot reopen a settled run or replace its result. Deadlines and output limits are bounded. The reaper stops the worker's process group when the supervisor disappears or the run deadline plus its margin passes.

Outcomes come from the turn status, its stop reason and error code, and the limits the supervisor itself detected, which take precedence.

| Observed | State | `stop_reason` or error |
|---|---|---|
| Turn ended normally | `completed` | `end_turn`; a warning if no final message exists |
| Vibe's iteration limit, or the supervisor's model-call backstop | `completed` | `turn_limit`, with an incomplete-result warning |
| `limits.max_tokens` crossed | `completed` | `token_limit`, with the warning |
| `limits.max_cost_usd` crossed | `completed` | `price_limit`, with the warning |
| The model declined (error code `refusal`) | `completed` | `refusal`, with a warning that the result is not a review or an edit |
| `vibe_close` or cancel | `cancelled` | `cancelled` |
| Run deadline, or no progress | `failed` | `VSUP_TIMEOUT`, `VSUP_NO_PROGRESS` |
| Provider rejected the key | `failed` | `VSUP_AUTH_REQUIRED` |
| Rate limit | `failed` | `VSUP_RATE_LIMITED`, retryable |
| Context or response too long, or stop reason `length` | `failed` | `VSUP_OUTPUT_LIMIT` |
| Unapproved allowed effect (including one whose input differs from what was approved), unknown history entry, event gap, unsafe session handoff, usage counter going backwards, cost ceiling without a price, unparseable message | `failed` | `VSUP_BACKEND_ERROR`, `details.reason` names the cause |
| Server exited or its stream closed | `failed` | `VSUP_BACKEND_CRASHED` |
| Any other error code | `failed` | `VSUP_BACKEND_ERROR` |

A limit stop means execution ended at its budget, not that the task succeeded. The supervisor does not retry, continue, or raise the budget. A stop reason Vibe reports that the supervisor does not know is recorded as `completed` with that text and the incomplete-result warning; read it before trusting the answer.

Closing a live run cancels its process group and accounts for worktree creation that is already in flight. Worktree deletion requires the expected canonical run-owned path, validated Git registration, a fresh export matching the saved artifact, and an inventory showing the worktree is pristine. Dirty or uncertain worktrees are retained with an explicit path and reason so the coordinator can review the exported patch. Cleanup is admitted by the root recorded when the run started, not by the current allowlist. Removing a root does not stop a run already admitted there: it runs to its normal end, stays readable and closable, and its verified pristine worktree can still be removed; a dirty or uncertain one is retained exactly as before. Saved PIDs alone never authorize termination, and saved mutable worktree metadata alone never authorizes deletion.

A retained worktree stays registered in the source repository under `.git/worktrees/`. If you run `git worktree prune` or delete the directory yourself, verified cleanup refuses it permanently, because the registration it checks no longer exists, and the run directory is kept. Recover manually: read the exported patch from the run's artifacts, call `vibe_close` without cleanup (or use `vibe-supervisor runs cleanup`, which lists each retained worktree with the exact `git -C <source> worktree remove <path>` command, each path single-quoted for a POSIX shell), then remove or prune the worktree yourself with Git. The supervisor never force-deletes retained data.

Git operations are bounded separately: queries such as `rev-parse` and `ls-files` have a 30 s bound, while worktree creation, patch export and verified cleanup have a 5 minute bound so large repositories can be checked out. The exported patch is capped by `limits.max_artifact_bytes`. Exceeding a bound fails with `VSUP_TIMEOUT` or `VSUP_OUTPUT_LIMIT` and `details.operation`, including during worktree creation and base ref resolution. A missing `git` executable stays `VSUP_GIT_REQUIRED`; a worktree directory that no longer exists is `VSUP_ARTIFACT_ERROR` with `details.kind: workspace_missing`.

### Review snapshot cost

The integrity snapshot hashes the content of every file Git can see (tracked, plus untracked files not ignored) and only stats everything else, such as ignored trees like `node_modules`, skipping `.git`. It runs at launch and again at settle. Large ignored trees cost stat time at both ends. The snapshot is capped at 200,000 files and 2 GiB of hashed content; past either cap integrity is reported as `unverified` rather than failing the review. Keep large generated trees out of the reviewed workspace, or accept `unverified`.

On server shutdown, the supervisor allows a primary 10-second graceful drain and then retries termination through each live owned handle. Individual cancel and forced-termination attempts are bounded, but there is no fixed overall exit guarantee while termination remains unverified. Unresolved workers retain their handle, slot, worktree and owner lock; pending initialization and in-flight Git/worktree writes also remain accounted for under that lock. The lock is released only after all owned work is accounted for.

When `serve --stdio --isolated` receives `vibe_status`, `vibe_result` or `vibe_close` for a run outside its currently selected session directory, it searches the same private `mcp-sessions` namespace for that UUID. It routes only when exactly one safe run directory matches; the existing manager validates its saved record during recovery. The owning lock is acquired before that manager loads the store; live owners, unsafe paths, duplicate UUIDs and namespaces over the scan limit fail closed. The temporary manager uses the current server's boot-bound settings, applies the same frozen-admission cleanup rule, and is shut down after the operation. New runs always stay in the current session. This lookup does not search other config roots or identify which desktop connection originally created a run.

## Restart and saved data

On startup, active records from an interrupted one-shot run are made inspectable and marked failed with an interruption diagnostic. Before the server accepts work, recovery also deletes each such run's private directories (`child-home`, `vibe-home` and `tmp`), because a crash can leave Vibe's throwaway session store there. If a directory cannot be deleted, the saved result carries a warning that private Vibe state remains in the run directory, and the retention sweep is not relied on to remove it. The isolated UUID lookup applies the same recovery when it temporarily opens a unique older session. Startup and lookup do not launch Vibe, load a session, replay a task, restore a grant, or signal a PID from a saved record. 2.0 makes no migration or cleanup contract for data saved by 1.x or by an older ACP installation; use the corresponding older executable for that data.

Runs, events and artifacts are persisted privately and bounded by configured limits and retention. The supervisor uses atomic writes, owner locking, fresh path validation and explicit child environment filtering. The credential lives only in the worker's environment, never in a task, event or artifact, and raw provider output and secrets are filtered from saved artifacts.

Reasoning stays off disk by construction rather than by a switch, because Vibe has none. Session logging is off, so Vibe's session store is a throwaway directory under the run's private `TMPDIR`; thinking is turned off; reasoning entries received over the wire are dropped before anything is written; the supervisor never reads the store; and the private directories are deleted at close and by restart recovery. Whether thinking off stops the model from generating reasoning is a target observation, not a local guarantee.

## Events

Besides `message` (the final answer) and `diagnostic`, a run records these events, each with bounded, redacted fields:

| Event | Fields | Meaning |
|---|---|---|
| `tool_call` | `name` (`read_file`, `write_file`, `edit`), `tool` (Vibe's wire name), `kind`, `outcome: executed`, `entry_id`, `path` | An approved, executed call on the profile. |
| `tool_denied` | `tool`, `outcome`, `reason`, `entry_id`, `path` | A call that did not run. `outcome` is `permission_denied_by_handler` when the supervisor's handler answered deny (`reason` is its reason, such as `tool_not_in_profile`, `path_outside_workspace`, `path_secret` or `decision_deadline`), or `permission_denied_by_policy` when Vibe itself denied it before any approval request (for example a denylisted path), in which case `reason` repeats the outcome. |
| `timeout` | `timeout_seconds` | The run exceeded its configured timeout and is failed with `VSUP_TIMEOUT`. |
| `review_integrity` | `status` (`verified`, `changed` or `unverified`), `write_tool_observed`, `changed_paths`, `changed_paths_total`, `reason` | The end-of-run comparison of the source workspace with its launch snapshot, recorded for a review when the status is not `verified` or a write tool was seen. Severity is error only when the source changed and a write tool was observed. |

`vibe_status` shows a `tool_denied` event as `<tool>: <reason>`. The wire names are `file_system.read_file`, `file_system.write_file` and `file_system.search_replace`. A denied write in a review is expected policy, not a failure; it shows that the worker tried a refused action. Supervisor `diagnostic` events carry a `reason`, listed in [compatibility](compatibility.md#diagnostic-reasons).

## Configuration and preparation

Select a config with `--config`; otherwise resolution uses `VIBE_SUPERVISOR_HOME`, then the platform default root. Explicit invalid or missing configs fail without fallback. That selection is made once, before `--isolated` switches to a private session directory, and stays the policy source for the life of the connection; the session's copy of `config.toml` is an audit record only. Once serving, a missing selected file fails closed even where startup could have used defaults. Removed keys such as `backend`, `max_concurrent_runs`, idle-session TTL and ACP executable paths are rejected, and `paths.vibe_pin_manifest` is required. The config, doctor provenance, data directory and already-open client handshake are separate facts.

Commit or stash the reviewed state before delegating and pass its ref as `base_ref`; uncommitted source bytes are not an edit base.

The supervisor's path checks, session configuration, approval handler and Vibe tool configuration are application policy. They are not a kernel or process sandbox. A worker's account permissions and any content included in its allowed workspace remain relevant.
