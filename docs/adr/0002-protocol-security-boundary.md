# ADR 0002: Enforce Vibe profiles at process, config, and workspace boundaries

- Status: accepted for the fallback ACP integration
- Date: 2026-10-03

## Context

Vibe is an independently executing agent with its own config layers, tool runtime, approval logic, authentication lookup, and logs. A Git worktree provides version-control isolation; it does not stop a process from reading or writing other host paths. The supervisor must bound Vibe before it accepts output, and must not treat a natural-language instruction, an ACP mode label, or the worktree itself as a sandbox.

Source inspection and a bounded ACP protocol probe were performed against Vibe 2.25.8. The ACP entrypoint loads both user and project harness sources. Project config/hooks and project-discovered tools, agents, plugins, and skills are eligible when the working directory is trusted. Environment fields merge above project/user config, but agent profile overrides merge above those environment fields. MCP server lists merge by name. ACP `session/new` defaults to `accept-edits` in a fresh home. These details rule out a design that merely sends `mcpServers: []`, asks for Plan mode in text, or relies on one lower-priority config override.

## Decision

Every supervisor run receives a fresh owner-only `HOME` and `VIBE_HOME`, both in its private run directory, and a minimal child environment built from an allowlist. Preserve authentication only as private process input: pass an existing nonempty `MISTRAL_API_KEY` only when present in the parent environment; otherwise the pinned shim performs a bounded, exact-argv macOS Keychain lookup after version and signature validation, using the original HOME only for that `security` subprocess and removing it before Vibe starts (see `docs/compatibility.md`). Do not copy the user's Vibe config, local `.env`, tokens, plugins, tools, hooks, skills, or agents. Do not return the credential through any MCP or ACP surface.

Launch ACP from the requested repository root so Vibe's workspace root is that checkout, with an empty ACP `additionalDirectories` array and `mcpServers: []`. Do not mark the checkout trusted. Require ACP's workspace trust metadata to remain `untrusted`; reject a trusted state. The isolated trust store makes pre-existing user trust unavailable to this process and keeps the project harness inactive while allowing the session's file tools to resolve within the opened working directory. Never call the trust decision extension. Reject runs when the requested root contains Vibe configuration, plugins, hooks, custom tools, or agent profiles that could become active through an unexpected Vibe version or trust transition; do not silently accept those files as inert.

For read-only inspection, configure the isolated environment to enable exactly `read_file` and `grep`, select `plan` as `default_agent`, and set enabled agents to exactly `["plan"]`. Set each file reader's permission to `never` and its allowlist to the exact canonical workspace root plus `<root>/**`; without a matching allowlist, `never` also blocks ordinary in-workspace reads. Set denylist rules first for known secret-file patterns, with separate root-level and recursive patterns for `.env`, `.env.*`, `.envrc`, and `.envrc.*`. The installed matcher does not let `<root>/**/.env` cover a root-level `.env`. ACP 2.25.8 resolves symlink targets before its file permission boundary and path-pattern checks. The MCP server must still validate every normalized event and never grant an unknown permission request. The advertised mode is a status signal and defense in depth; the exact tool inventory and path checks are the security controls.

Do not enable shell, write/edit, subagent, web, skill, connector, or MCP tools in a read-only profile. For implementation work, create a separate explicit profile and run it only against a dedicated worktree with narrowly enabled editing tools; do not extend the read-only profile implicitly. Never claim the worktree confines filesystem access. On macOS, use `sandbox-exec` as a supplementary OS boundary only when a tested policy is available; otherwise describe the Vibe path checks as application-level controls, not kernel isolation. If the supervisor cannot prove process isolation, effective tool inventory, trust state, or expected backend before sending work, fail closed.

The supervisor does not expose Vibe's full ACP wire messages or raw logs by default. ACP logging is explicitly disabled. A pinned runtime launcher for exactly Vibe 2.25.8 sets a restrictive umask, suppresses INFO prompt logging, and filters reasoning/thought and known credential values before Vibe's session append/overwrite/metadata persistence. It signature-checks the installed logger and fails before work on drift; a detached-process watchdog kills its own worker process group if the supervisor disappears or the run lifetime expires. This protects the verified session persistence path, but cannot claim complete sanitization of every possible Vibe diagnostic or undiscovered persistence path. Keep ERROR stderr streaming-redacted, apply run retention to the isolated home, redact credential-like values, and never expose hidden reasoning. Treat project text, model responses, logs, and tool outputs as untrusted data.

## ACP compatibility choice

Use stable ACP v1 behavior. Detect advertised capabilities; do not infer support from method names or draft protocol versions. Vibe 2.25.8 advertises `loadSession: true` and session `close`, `list`, and `fork`. The backend continues a live session and uses `session/load` for restart recovery only when Vibe advertises `loadSession`. Recovery validates the run directory and private HOME/VIBE_HOME against the supervisor's data root, and checks saved mode, version, workspace, session ID, and untrusted workspace metadata. It suppresses update replay during load and never resubmits the original task. No `resume` capability is advertised. Pending requests are not restored. Vibe 2.25.8 sends only a tool-call ID in an ACP permission callback; correlate it with merged prior tool-call updates by ID. Its initial update carries `title`, `kind`, `locations`, and `rawInput` but may not carry a `name`; do not require that absent field. If the ID or safe action/path is missing, offer deny/cancel only. Core policy evaluates normalized requests; the adapter only selects an offered one-time choice and never `allow_always`. Form elicitation is advertised only for schemas within the adapter's bounded JSON Schema subset; URL/secret-like fields, unsupported schema forms, oversized schemas, and concurrent requests are declined. Never collect credentials through ACP elicitation.

Vibe 2.25.8 supports both legacy and a rollout-gated unified harness. The pinned runtime launcher explicitly forces `--legacy-harness` for ACP and programmatic launches; unified is not a supported profile. Exact Vibe version and logger-signature checks fail closed before work on drift, rather than inheriting rollout-selected behavior. Do not rely on experimental/smart approval modes for enforcement.

## Authentication and logging implications

The user's existing Vibe `.env` is intentionally unavailable when `VIBE_HOME` is isolated. Inheriting `MISTRAL_API_KEY` keeps API-key auth usable without copying a secret file. Because the private HOME hides the user's Keychain from Vibe's own lookup, the shim resolves the credential itself as described in `docs/compatibility.md`, and only on macOS. Vibe's macOS Keychain lookup uses service `ai.mistral.vibe` and environment-variable name as account, then may search legacy service `vibe`; the key is accessible to the launched process and sent to its configured provider, but is never a tool argument or supervisor result. Vibe's Keychain helper can migrate a discovered legacy entry, so this lookup has a potential Keychain write side effect. The supervisor must not claim that Vibe authentication is completely read-only. If policy forbids that side effect, use only an explicitly supplied API key in the child environment or disable Keychain lookup and fail when it is absent.

`vibe/acp/acp_logger.py` writes full ACP JSON messages under `Path.home()/.vibe/logs/acp` when `VIBE_ACP_LOGGING_ENABLED` is enabled. It does not use `VIBE_HOME`. Fresh `HOME` plus explicit logging disable keeps it out of the user's home. Vibe's other logs live under VIBE_HOME. `vibe-acp --help` is not a harmless probe in this version: `main()` bootstraps VIBE_HOME, initializes harness files and file logging, and only then parses arguments.

## Consequences

- User and project Vibe setup is deliberately not inherited; user-specific model and plugin settings need explicit, reviewed mapping into the isolated run profile.
- A trusted project profile is not part of the supported security model. Project Vibe extension files make a run fail closed until separately analyzed and approved for a future design.
- Vibe file-path permission logic is defense in depth. Without a working OS sandbox, arbitrary code execution inside Vibe would still have the user's process rights; therefore shell and custom executable tools stay disabled.
- The safe read-only profile can inspect files and search text. It cannot edit code, run tests, execute shell commands, invoke MCP services, or use Vibe web tools.
- An ACP server restart can be recovered through advertised `session/load`; replayed history updates are suppressed while loading. In-memory pending permissions/elicitation are abandoned during recovery and must never be restored as approvals.

## Verification record

The current adapter's `probe()` ran ACP `initialize` in isolated HOME/VIBE_HOME and passed with protocol v1 and exact version 2.25.8; it did not require credentials or send session/prompt. Separate scratch checks called `session/new` with no key (expected missing-key failure) and with a non-secret placeholder (local session created, no prompt), verified untrusted workspace and default `accept-edits`, then verified Plan-only mode with the constrained agent environment. A Python 3.12 fixture against the installed logger verified reasoning and secret canaries are removed from append, overwrite, and metadata files while ordinary fields survive. A scratch check called the installed `read_file`/`grep` permission resolver with an exact-root plus recursive allowlist, secret denylist, `NEVER` fallback, outside path, and symlink: ordinary in-root paths returned `ALWAYS`, while outside, linked-outside, and root `.env` returned `NEVER`. The current release verification passed all 49 tests across 7 files; fake-subprocess integration covers session load without task replay, live continuation, correlated permission/form requests, cancellation, startup failures, redaction, and a 100-turn soak. `npm run typecheck -- --pretty false`, targeted ESLint, and `npm run build` also passed. The real installed logger fixture and real ACP initialize probe passed independently. Hosted authentication, a real hosted model turn, and real-session tool inventory remain unverified; the fake fixture does not substitute for those checks.
