# Security model

The supervisor limits access through canonical allowed roots, strict private data directories, minimal child environments, managed process groups, bounded streams, redaction, and explicit run-state transitions. Edits execute in detached worktrees. Export verifies the patch and changed-file records before cleanup; changed or ignored content causes cleanup to refuse.

On hosts that deny process-group signaling, shutdown falls back to signaling the supervisor's direct child only. In that case the direct child is managed, but cleanup of its process group/grandchildren remains unverified and must not be reported as fully confirmed.

These are application controls. There is no kernel sandbox, syscall filter, network namespace, or guarantee against vulnerabilities in Vibe, Node, Git, plugins, or the host. Treat delegated work as code execution with the permissions of the local account. Keep shell/network disabled unless a deliberate profile allows them. Do not place credentials in task text or workspace files. The programmatic task is handed to the launcher shim through a private 0600 file that is deleted before Vibe starts, so it does not appear in the OS-visible process arguments (real Vibe verification of this path is pending).

The browser-login credential is resolved inside the pinned launcher shim, never in the Node supervisor. Only real runs (`start` and `recover`) pass the original HOME in `VIBE_SUPERVISOR_ORIGINAL_HOME`; probes never do (`createVibeChildProfile`'s `forwardOriginalHome` option), so probes make no Keychain lookup; the shim validates the Vibe version and signatures first, takes an explicit nonempty `MISTRAL_API_KEY` as authoritative (empty counts as absent), and otherwise runs `/usr/bin/security find-generic-password -a MISTRAL_API_KEY -s <service> -w` for `ai.mistral.vibe` then `vibe` with only `HOME` and `PATH`, a 5 second timeout, an 8 KiB output cap, and discarded stderr. The original-HOME variable is removed before Vibe starts; the credential lives only in the Vibe process environment, and the shim's stderr and native history filtering replace the exact value. This is an application control, not a sandbox, and the real Keychain path is unverified.

Streamed message text passes through a bounded streaming redactor. A line longer than its pending limit (64 KiB) is no longer discarded: the pending buffer is redacted and all but the last 4096 characters are emitted, and the tail stays pending so a secret straddling the cut is still caught (provided it is shorter than that tail). An unfinished PEM private-key block is never cut; one larger than the limit is emitted as a single `[REDACTED]` and its remaining lines are dropped up to the end marker, after which later content flows normally. Besides bearer tokens, common key prefixes, `key=value` pairs and authorization headers, the patterns cover prose such as `API key: <value>` or `API key is <value>` (the value must look like a token of 16 or more characters, so "API key is required" is untouched), `x-api-key` headers and `*_API_KEY=<value>` assignments such as `MISTRAL_API_KEY`, because a credential resolved inside the launcher shim is unknown to the supervisor's sentinel list and could otherwise surface in a backend error message. Pattern redaction is best effort.

Persisted events and JSON are sanitized recursively; reasoning/private thought fields are omitted. Raw protocol streams are consumed internally and must not be logged. Patch files are not rewritten for redaction because that corrupts diffs: likely credential-bearing patches fail export and preserve the worktree for inspection.

Permission rejections follow the ACP specification: a policy or user denial is sent as the selected reject option so the agent continues the turn with the tool refused, while `cancelled` is sent only when the supervisor cancels or closes the run with a request pending. The same applies to a request the supervisor cannot evaluate (no correlated, normalized tool action and path) and to a request that arrives while another is pending: the supervisor selects an offered `reject_once`, else `reject_always`, and falls back to `cancelled` only when no reject option is offered; it never selects an allow option, and the `permission_denied` event records whether the outcome was `rejected` or `cancelled`. `allow_always` and unoffered options are refused, and a cancelled run never reports a completed turn afterwards.
