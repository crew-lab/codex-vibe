# Security model

The supervisor applies workspace, process, persistence, and output controls around Vibe. These controls are **not an operating-system sandbox**. A worker runs with the local account's process permissions, and allowed workspace content is sent to Mistral. Treat delegation as code execution with your account's access.

## Workspace and tool scope

- The canonical workspace allowlist is explicit and starts empty. Invalid, unsafe, glob-containing, symlinked, and out-of-root paths fail closed.
- The selected configuration file is the only policy authority. It is reread and validated (regular file up to 1 MiB, no symlink, no symlinked parents, owned by the current user, not group- or world-writable, strict schema, unique in-scope roots) before each readiness check and start. Failure denies; a root whose directory no longer exists is dropped from the effective allowlist and denies only itself, while a symlinked or over-broad root still invalidates the file; nothing falls back to an earlier read, a session snapshot or defaults. Roots come only from that owner-controlled file, never from task input, project files, worker output or a readiness receipt. Boot-bound settings are never adopted mid-connection; a change blocks starts with `VSUP_RESTART_REQUIRED`.
- A removed root denies later starts. An already admitted run is not mutated or killed by the change and ends normally. Its worktree cleanup is admitted by the canonical root recorded at admission, and still requires the run-owned path, Git registration, a fresh export equal to the saved artifact and a pristine worktree; nothing else is relaxed.
- Readiness receipts are HMAC-SHA-256 tokens under a random per-process key with a 10-minute expiry. They bind instance, policy revision, operation, canonical workspace and edit base; an admitted edit's worktree is created at the checked commit, and only narrow admission: a start still rereads and revalidates everything. A receipt grants no access, is not user authorization and says nothing about provider authentication. It is not single-use: within its 10 minutes it can admit more than one start, each of which still rereads and revalidates; check readiness again before each start.
- Reviews can use only `read_file`; edits add `write_file` and `edit`, in a detached supervisor-created Git worktree. Shell, network, subagents, background processes, connector, MCP, user/project skills and project-provided agents are disabled. Pinned bundled plugin skill entries are permitted by ADR 0006.
- **The model-visible catalogue still lists tools that are refused.** The protocol cannot narrow it: `write_file`, `edit`, the shell tool and `run_typescript` are listed to the model in every run, reviews included. They are refused when called, by configuration and by the approval handler, not hidden. A review's model can see and try the write tools, and every such attempt is denied and recorded as a `tool_denied` event. The unchanged-source check after a review stays the proof that nothing was written.
- Untrusted project state: the session does not trust the workspace and registers no workspace roots, so Vibe loads no project configuration, agents or hooks. `.vibe`, unsafe `.agents` and unsafe `.vibeignore` inputs are refused at admission, and the profile denies those paths and secret files anyway.
- Edit cleanup checks the expected run-owned canonical path, source/base Git registration, a fresh export matching the saved artifact, and a pristine worktree. Dirty or uncertain worktrees remain with an explicit path and reason for review. Saved metadata or PIDs alone do not authorize deletion or process termination.

## What is not isolated

- The worker runs as your user. Within the allowlisted workspace it reads what you can read, and an edit writes inside its worktree with your permissions. Nothing stops the Vibe process at the kernel level; the limits above are enforced by the supervisor's session configuration, approval handler and event audit, not by the operating system.
- Everything the worker reads is sent to Mistral, including files you did not mean to share if they are inside the workspace.
- Vibe's provider client receives the credential it needs, in the worker's environment. The supervisor keeps it out of tasks, logs and artifacts, not out of Vibe.
- A review of untrusted input means the task names files whose content you do not control: a dependency, a pull request from someone else, generated output. That content can try to steer the worker. Treat the answer as data from that source, verify it, and never let it decide what the coordinator runs, merges or trusts. The tool limits make such a review safe to run; they do not make its answer true.

## Managed configuration service

Vibe 2.26.1 refreshes a remote admin layer at session open when a provider key is present, independently of experiments and telemetry. Supervisor replaces only `vibe_base_url` with a per-worker owned HTTP listener on an ephemeral IPv4 loopback port. It responds to GET `/api/v1/code/managed-config` with `{"state":"disabled"}`; other methods, paths, query strings and bodies are refused. It never forwards requests, records headers or bodies, or emits credentials. This deliberately excludes remote organization-managed policy from the private worker; do not use this profile where such remote policy is required. See ADR 0005.

The loopback URL is set before launch and required in effective-configuration read-back before a turn. Bind failure prevents launch; read-back drift prevents a turn. The listener closes during success, cancellation and failed-start cleanup, after worker termination is verified; an unverified worker retains its owned endpoint until cleanup can safely finish. No provider inference URL is changed. The listener has connection/header/time bounds, no persistence and no credential logging. The same local account can access loopback; this remains application policy, not a firewall or OS sandbox. Unexpected networking by Vibe remains a target conformance gate.

## Enforcement points

Every run is a client of `vibe-app-server` (one process per run). Controls are preventive where Vibe's own configuration or the approval answer stops a call, and detective where the supervisor can only notice a call after the fact and interrupt. The design makes every disclosure path preventive and uses detection to catch drift.

1. **Session configuration.** The session request sets the worker workspace as `cwd`, a supervisor-written agent profile, `enabledTools` (the profile) and `disabledTools` (`ask_user_question`, `exit_plan_mode`, `cron`), the turn limit, `autoApprove` false, `trustWorkspace` false, no workspace roots and no MCP servers. The `VIBE_*` process environment turns off subagents, background processes, managed shell, connectors, telemetry, update checks, the model catalogue, experiments and session logging, disables root user/project skills while permitting the pinned bundled plugin catalogue, sets no MCP servers and bypass permissions off, fixes `default_agent` and `enabled_agents` to the supervisor's agent, and keeps logging at error level. Thinking is turned off through the protocol before the first turn.
2. **Agent profile.** A private profile file sets `permission = "ask"` and a denylist for each profile tool. The denylist covers the `.git`, `.vibe` and `.agents` directories and `.vibeignore` at any depth, and secret files (`.env*`, `.envrc*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`) at any depth. `ask` is deliberate: an allowlist match, or the default `always` of `read_file`, would skip the approval handler. A denylist match is denied by Vibe before any approval request.
3. **Startup read-back.** After `session/start` the supervisor reads the runtime and the effective configuration and requires: the exact profile tools; only permitted bundled skills; no MCP sources, connectors or hooks; no issues; bypass off; the unified harness; the expected `cwd`; every setting above; `ask` and the exact denylist on each profile tool; and thinking off on the active model. A missing expected field or any difference fails the run before the first turn (`readback_mismatch`). Unknown extra fields are ignored.
4. **Approval handler.** See below.
5. **Event validator.** See below.
6. **Post-run checks.** A review's launch and end snapshots decide integrity; an edit's patch export, secret refusal and verified cleanup are unchanged. A final paged pass over the turn's history re-runs the validator, and compares every effect settled before a session handoff with its earlier fingerprint.
7. **Process control.** The worker has its own process group. A reaper process kills that group if the supervisor disappears or the deadline plus a margin passes. A graceful stop closes standard input; the supervisor then verifies termination. If termination cannot be verified, the reaper is left running and the handle is kept so the stop can be retried, also when the failure happens while a run is starting. Every stop request (cancel, close, forced termination, deadline, budget stop) revokes the approval handler first, so a callback that arrives after it is denied.

### Approval handler

Vibe sends each approval request to the supervisor and never decides it for the profile's tools, because the profile asks for every call. The handler answers only `approve` or `deny`; it never sends a session or permanent approval, and never cancels the turn.

- It approves only when the callback is an approval for a tool in the profile (review: `file_system.read_file`; edit: also `file_system.write_file` and `file_system.search_replace`), the effect kind matches the tool, a file path is present, and the path passes the judgement below. Anything else is denied, including malformed or unexpected requests.
- **Path judgement.** A relative path resolves against the worker workspace, as Vibe does, never against the supervisor's working directory. The path is resolved with `realpath`. A path that does not exist yet (a new file in an edit) is judged by the real path of its nearest existing ancestor plus the remaining components, which must contain no `..` and no symlink. The result must lie inside the real path of the worker workspace and not be the workspace itself, must contain no `.git`, `.vibe`, `.agents` or `.vibeignore` component and no secret-file name (compared case-insensitively, on both the resolved and the written path), and must not start with `~`, contain a NUL, or exceed 4096 characters.
- **5-second deadline.** The server never times out a pending approval, so the supervisor does: a decision not reached within 5 seconds is answered deny. A repeated callback id, a full decision ledger, or an internal error is also deny.
- A callback that names no effect to link to is denied, as is a callback whose session id is not the active session, and a second callback for an effect that already has a decision. After a failed handoff re-validation or any fatal event the handler is revoked and denies everything.
- Each decision is recorded and bound to exactly one effect: callback id, effect entry id, session id, turn id, tool, the path, the reason, and a SHA-256 fingerprint of the canonical input that the callback showed (the path; for a write also the content; for an edit every change with `replaceAll` normalized, whether sent as a batch or as a single edit; for any other tool the whole input). Read offsets and limits are not part of the fingerprint, because they change neither what is read nor what is written. The event validator uses this record.

The check and Vibe's own file operation are separate steps. The path judgement narrows what the worker is asked to do; it does not make the process incapable of anything else.

### Event validator

Every history entry the server sends is classified. Reasoning entries are dropped on receipt.

- A tool effect that Vibe denied (failed with `tool_denied`, not executed) is expected. It is recorded as `tool_denied`, as a handler denial when the supervisor's handler answered it, or as a policy denial when Vibe denied it first (for example a denylisted path). The run continues.
- **An allowed or executed effect that the handler did not approve is fatal.** Approved means exactly decision `execute`, approval type `ask` and source `user`, linked to a handler `approve` for the same tool and callback, and the tool must be in the profile. Missing or null metadata counts as unapproved. This applies to the profile's own tools too: Vibe has allow paths that skip the callback, and the handler never grants for the session, so a legitimate allow always pairs with an approval. The run is interrupted and fails with `VSUP_BACKEND_ERROR` naming the tool.
- **A cancelled or skipped effect that carries an execute decision is checked like an executed one.** Vibe may have started it before the cancel, so it must still link to a handler approval; otherwise it is fatal (`unapproved_effect`). An effect still unfinished when the turn ends is fatal too (`unfinished_effect`), because what it did cannot be verified.
- **An effect must match its approval exactly.** An executed effect is fatal (`unapproved_effect`) unless its recorded approval was for the same effect id, the same tool, the same turn and a session of this run, and the fingerprint of the effect's own input equals the fingerprint of the input the callback showed. A later effect whose path, content or edit changes differ, an effect that names a callback approved for another effect, and an effect whose input is patched or re-sent differently after the approval are all fatal. An effect input the supervisor cannot fingerprint never matches. The check runs again on every update of the entry and in the final history pass.
- **A session handoff is checked, not trusted.** `session/compacted` and `session/contextCleared` are accepted only when the id they replace is the active session, they carry a watermark, no event gap is open, no effect is unfinished and no callback is open or unanswered (`session_handoff_unsafe`). Every effect settled before it is fingerprinted from what was approved and observed; in the new session's history such an effect must be identical (`historical_effect_changed`), and any other settled effect must be approved against the new session, so nothing is lost or counted twice and nothing hides behind the reset. The runtime and effective configuration are then read back again with the startup comparison before the run continues. Usage counters are carried across the reset and the ceilings apply to the totals. A counter that moves backwards in any other place is fatal, a cost ceiling with no model price is fatal, and neither is treated as zero or as never tripping. If Vibe does not keep thinking off across a handoff, the run fails at that read-back.
- **An unknown history entry kind is fatal**, because it could hide a call. So are an unknown effect status, a malformed notification, a failed history patch, retained-entry limits exceeded, and history paging that does not progress.
- **A gap in event ids fails closed.** Ids at or below the session snapshot are ignored and the next id is accepted; a larger one means events were skipped. The supervisor interrupts the turn, replaces its state from a fresh session read and audits it, then fails the run (`details.reason: watermark_gap`). The gap, like any other protocol failure, outranks a cancel or deadline that arrives afterwards; the later stop is recorded in the error, not substituted for it.
- An unknown notification method is ignored and counted; it is reported as an `ignored_notifications` diagnostic.

The final history pass also runs when a budget or deadline stop was not honored in time and the connection is still alive, so a hidden effect is found there too. A budget stop whose pass cannot run or finish is reported as a failure, never as a clean `completed` result.

The validator is detective. By the time it sees an effect Vibe has already decided it, so it can stop a run and record the breach but cannot undo it.

## Process, configuration, and persistence

Every run uses private `HOME`, `VIBE_HOME` and `TMPDIR` inside its run directory, a child environment assembled from an explicit allowlist, and the task delivered over the protocol, not in OS-visible arguments. User and project tools, hooks, skills, MCP servers and trust records are not inherited. `VIBE_HOME` starts empty apart from the supervisor's profile file.

Vibe is pinned to exactly 2.26.1. Before each spawn the supervisor verifies the installed files against a per-candidate manifest, and after the handshake it requires the server to report the pinned version. Drift fails closed, and the worker is spawned from the real path the check hashed rather than from a symlink that could be repointed afterwards. The pin check covers only the files listed by the installed `mistral_vibe` distribution's `RECORD`, including the `vibe-app-server` script, and rejects unlisted files in the directories that record covers. It does not cover Vibe's dependencies, `.pth` files, the Python interpreter, or compiled `__pycache__` bytecode. It runs before the process starts, so it checks the installation at that moment, not the code that later loads, and the manifest records whatever was installed when it was generated: it detects change, not a malicious original. See [compatibility](compatibility.md#the-pin-and-its-manifest).

**Known limitation of the pin (2.0.0).** A matching pin does not prove that the code which runs is the code that was hashed. The check reaches only the files `RECORD` lists; the Python interpreter, Vibe's dependencies, `.pth` files and compiled bytecode are outside it, and the files can change between the check and the moment Python loads them. Treat the pin as drift detection for the installed Vibe package, not as an integrity or sandbox guarantee. This is accepted for 2.0.0 and is not closed by any other control here: the application policy is not a kernel sandbox either. The source audit is limited to Vibe 2.26.1 as read from its tagged source; fake-server fixtures do not certify hosted inference, authenticated effective configuration, or native clients.

The credential is resolved by the supervisor from `MISTRAL_API_KEY` in its own environment or, on macOS, from the Vibe Keychain entry through a bounded `/usr/bin/security` call, and reaches the worker only as `MISTRAL_API_KEY` in the child environment. It is not resolved into a task, event, log or artifact, and persisted output and server stderr are redacted against it. Redaction is best effort and cannot guarantee sanitization of every possible third-party diagnostic. No credential belongs in task text, source files, logs, reports, or artifacts.

Reasoning stays off disk: session logging is off, so Vibe's session store is a throwaway directory in the run's private `TMPDIR`; thinking is off; reasoning entries are dropped before persistence; the supervisor never reads the store. The store can hold reasoning and unredacted tool output, so it must not outlive the run: the supervisor deletes the private directories at close, and restart recovery deletes them for an interrupted run before the server accepts work. If deletion fails, the run carries a warning and a `private_state_retained` diagnostic.

Process ownership is released only after backend close verifies termination. A failed or timed-out close keeps the live handle, active slot, worktree and owner lock for inspection and bounded retries through that handle. Shutdown has no fixed overall exit guarantee while any owned worker remains unresolved. The supervisor never signals a PID from saved state.

An isolated server can route status, result and close by UUID across sibling session directories only within its selected private `mcp-sessions` namespace. It validates the namespace and target paths, rejects duplicate matches, and acquires the target directory's owner lock before manager recovery. A live owner or unsafe/ambiguous path fails closed. The temporary manager receives the active server's boot settings and selected policy source; the route does not read historical config snapshots to expand workspace access.

Events, transcripts, results, and artifacts have bounded sizes and private permissions. Writes are atomic where supported. Child workers have bounded deadlines and output, and the reaper covers a dead supervisor. Owner locking prevents a second manager from claiming the same storage. A restart makes interrupted one-shot runs inspectable and failed; it never loads a session, replays the task, restores a grant, or signals a saved PID.

The supervisor streams output through bounded redaction and recursively removes reasoning and private fields from persisted JSON. Patch content is not rewritten because that would corrupt diffs; export refuses high-confidence credential patterns in added lines and preserves the worktree for inspection. These checks are defense in depth, not a guarantee against unknown secret formats.

## Protocol and logs

The MCP interface is stdio with strict schemas and exactly five tools. It has no interactive grants, continuation, or pending-input protocol. Standard output is reserved for MCP frames; diagnostics go to standard error. Never persist raw provider logs or reasoning. The app-server link is a private stdio pipe to a child process: bounded line size and total inbound bytes, strict parameters on what the supervisor sends, tolerance for unknown fields on what it reads, and a malformed frame fails the run.

## Verification limits

Local fixtures, doctor and pin checks do not prove hosted inference or authenticated behavior. Actual rc.5 no-inference conformance observed the effective `ask` permission/denylist configuration, as recorded in compatibility; it did not prove hosted handler enforcement, nested `run_typescript` gating, thinking generation effects, native Codex behavior or clean-account installation. The gates are listed in [compatibility](compatibility.md#unverified-gates) and stay unverified until their evidence is recorded there. Historical evidence is version-bound and kept in the source repository, not in the package.

## Development dependency advisories

The current lockfile pins Vitest 4.0.18 and its development dependency tree. GitHub advisories [GHSA-5xrq-8626-4rwp](https://github.com/advisories/GHSA-5xrq-8626-4rwp) and [GHSA-82fw-gwwq-j7x9](https://github.com/advisories/GHSA-82fw-gwwq-j7x9) include this Vitest version in their affected ranges. The first concerns the Vitest UI/API or Windows UI/browser mode; the second concerns an exposed mocker plugin on a Vite HMR WebSocket. This repository's release command uses `vitest run`, does not start the UI/browser mode, and does not use Vitest as a runtime dependency. This narrows the known exposure for the documented workflow; it does not remove the advisories or replace a current online dependency audit. The offline npm audit cache did not contain advisory metadata, so its empty result is not evidence of a clean audit. The app-server change makes no dependency upgrade.

## Bundled Vibe skills (2.0.0-rc.2, owner decision)

Pinned Vibe 2.26.1 bundled plugin skills are permitted: `vibe:create-plugin`, `vibe:skill-creator`, `vibe:vibe`, `vibe:worktree`. Read-back requires plugin source, builtin scope and no registry reference, and rejects unknown or duplicate names. User/project/registry skills remain disabled. Skills are guidance; their instructions do not authorize tools, paths, shell or network access. The exact review/edit file-tool profiles and approval handler remain unchanged. Earlier statements of an empty skill catalogue are superseded by ADR 0006.
