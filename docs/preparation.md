# Current Vibe qualification

The current implementation admits stable Vibe versions at or above 3.0.2 and exposes five one-shot MCP tools. Version eligibility is not target qualification: each actual installed version and manifest must pass the version-matched candidate preparation checks. Each start requires a locally registered, single-use dispatch authorization and attempt. See [ADR 0010](adr/0010-dispatch-attempt-authorization.md). Continuation is deferred. The previous six-tool archive and its evidence remain historical; they do not qualify this changed source. Existing hosted evidence remains limited to the exact archive and Vibe installation it records.

Grant registration is administrative and starts no worker. It may run while a server owns its session directory. A preparation PASS is still required for ordinary inference; it does not authorize a task or prove hosted acceptance.

# Version-matched preparation kit

Each candidate ships a separate preparation-kit-VERSION directory with the conformance procedure, exact no-inference script, candidate identity and checksums. Keep this directory with its candidate archive.

Packaging captures the candidate identity immediately after `npm pack`, before regenerating the external SBOM. Its final gate installs that exact archive into a temporary private prefix using the populated offline npm cache and disabled lifecycle scripts, then compares the installed candidate identity, package version and conformance-script hash with the kit and verifies every kit checksum. Packaging announces success only after that gate passes; its delivery checksum manifest includes all kit files. The temporary installation is removed on success or failure. The external SBOM remains a separate delivery artifact: generating it later must not change the archive-to-kit binding.

Run `vibe-supervisor prepare check --kit /absolute/preparation-kit-VERSION --config /absolute/config.toml` using the installed candidate. It verifies kit/script/candidate hashes, then runs the review and edit initialization checks once with a fixed fake key and refusing network observer. It never sends turn/start or uses real provider credentials. A deterministic failure stops the check; do not blindly retry the unchanged candidate.

When `backend = "antigravity"`, `vibe-supervisor prepare check` verifies the configured Antigravity executable (`paths.antigravity`, defaulting to `agy`), requiring a supported pinned version (`agy 1.4.0`, `1.4.3`, `1.4.4`, `1.4.7`, `1.4.8`, `1.4.9`) and recording its binary SHA-256 digest. It generates isolated review and edit environments with private `HOME`/`TMPDIR`, validates unified permission rules in `settings.json`, and verifies the `supervisor-policy-gate` configuration in `hooks.json`. It runs zero-inference slash-command read-backs (`/config`, `/hooks`, `/permissions`, `/skills`) against a refusing loopback proxy, verifying that only pinned built-in skills with provenance are reported and user/project skills are empty, and executes synthetic `PreToolUse` hook evaluations covering allowed workspace access, excluded globs, reserved directories, secret patterns, and off-profile tools. It then runs the [agy probes](#antigravity-probes) through agy itself, with the same fake key and a scripted loopback model in place of a provider: the hook is invoked and its deny honoured, a hook that times out, exits non-zero or prints unparseable output denies, agy's stream tool events match the audit parser, agy sends its inference traffic through the refusing proxy, and project configuration planted above the workspace is not loaded. Each must pass, or the receipt fails; the report records them under `agy_probes`. The backend must also be enabled with `experimental.antigravity = true`. The resulting receipt and sanitized report are saved in the supervisor data directory, binding candidate distribution bytes, the verified `agy` binary SHA-256 digest, Node version, platform/architecture and policy.

A private receipt and sanitized report are saved beside the selected pin manifest. Evidence binds candidate distribution bytes, pin manifest, Node version, platform/architecture and policy except workspace roots. Changing only task roots can reuse evidence; version/runtime/policy changes invalidate it. After a Vibe CLI upgrade, review and regenerate the manifest with `pin-manifest --force`, then run the kit again; the old manifest and receipt never silently authorize changed installed files. Missing, failed, changed or stale evidence blocks ordinary AppServer dispatch. Fixture tests inject their own preparation evidence provider; there is no production environment bypass. The receipt is rewritten as failed before the check launches, so an interrupted check never leaves an earlier PASS current.

Readiness reports workspace_eligible separately from eligible, candidate identity and preparation status. An optional expected_candidate SHA-256 detects connection drift. Existing runtime pin validation still runs at dispatch; an initialization-only receipt does not prove hosted inference, effective hosted permission enforcement, thinking behavior, disconnect soak, fresh-account installation or Intel support.

Review report.json/diagnostics and conformance findings before hosted testing. Hosted work retains its separately bounded allowance. A preparation failure is infrastructure evidence and must not trigger the fallback implementer or replay the original task.

## Antigravity recovery checks

The scripted read is selected from the request's declared function schema. JSON Schema fields take precedence over an empty legacy `parameters` object. An unknown path property or any additional required argument is inconclusive; the driver never invents an `AbsolutePath` fallback. Fake protocol tests exercise both hook-registration locations so a deny/failure hook cannot silently leave the original policy hook active elsewhere.

When `[experimental] antigravity_skip_permissions = true`, the agy probes run with `--dangerously-skip-permissions`, as workers would, and the report records `agy_permission_layer: "bypassed"`; otherwise `"enforced"`. The setting is part of the receipt's policy, so changing it needs a new check. Effective permission readback must match the supervisor's global allow/deny rules exactly, with no additional project/shared rules, malformed entries or duplicate scopes. Skills: the `/skills` read-back may list only the pinned built-in catalogue in [ADR 0008](adr/0008-antigravity-execution-backend.md), each entry with `builtin: true` and a unique pinned name; a `scope` value alone is not provenance, and any other entry fails closed. A local version outside the explicit supported list remains unsupported even if metadata-only diagnostics succeed. Diagnose those differences and review a changed candidate; do not edit preparation expectations to manufacture PASS.

## Antigravity probes

For a candidate configured with `backend = "antigravity"`. The probes are no-inference: they never use a real Google credential or sign-in.

`prepare check` runs them through the pinned `agy` itself after the existing read-backs and synthetic hook cases, and records them under `agy_probes` in its saved report. Each run gets a private `HOME` and `TMPDIR`, the supervisor-written settings, the fixed fake key `GEMINI_API_KEY`, and `HTTPS_PROXY` pointing at the refusing loopback proxy (`NO_PROXY` covers loopback only):

1. **Scripted model.** A loopback listener stands in for the model and agy is pointed at it through `GOOGLE_GEMINI_BASE_URL`, `GEMINI_API_BASE_URL` and `CODE_ASSIST_ENDPOINT`. It answers the first `generateContent` request with one call to `read_file` or `view_file` (matching the declared tool schema and parameter keys) on a probe file in the workspace holding a random nonce, and every later request with `done` and zero usage. The nonce appearing in a later request means the read ran. `agy_probes.scripted_model` lists the paths agy requested and the functions it declared. If agy honours none of the variables, every probe below is `inconclusive` with reason `scripted_model_unreached`, the receipt fails, and another no-inference driver is needed before these gates can move.
2. **Hook invoked, deny honoured**. A control run with the supervisor's policy hook must end `executed` with a hook-ledger entry; the same probe with a hook that always answers `{"decision":"deny"}` must end `denied` with the hook invoked. `hook_payload_fields` records the top-level fields agy sent the hook.
3. **Hook failures deny**. Three hooks, each registered with a 2-second timeout: one sleeps 30 seconds and then answers allow, one answers allow and exits 3, one prints text that is not JSON. Each must end `denied` with the hook invoked; any `executed` fails the receipt.
4. **Stream tool shape**. For the control and deny-all runs the report records the field names and the `event`, `type`, `step_type`, `state` and `status` values of agy's stream-json tool events, never their values otherwise, and the backend's audit parser must count exactly one executed probe call in the first and none in the second.
5. **Proxy honoured**. One run without the scripted endpoint: agy must send at least one request through the proxy, and at least one recorded host must classify as inference (any `googleapis.com` host except `play.googleapis.com`, including `generativelanguage` and Code Assist `cloudcode-pa`, or a known provider). The proxy answers 403, so nothing reaches Google. If agy ignored the proxy, its request went to Google directly with the fake key, which Google rejects; record that.
6. **Project configuration not loaded**. The workspace is placed two levels under a directory with `.git`, and both the Git root and the intermediate directory carry `.gemini/settings.json`, `.gemini/config.json`, `.gemini/config/hooks.json`, `.agents/hooks.json`, `.agents/mcp_config.json`, `.agents/skills`, `.agents/rules`, `.agents/workflows`, `.agent/skills`, `.agent/rules`, `.agent/workflows`, `GEMINI.md` and `AGENTS.md`, each with a unique `vsup-planted-…` marker. The probe tests two defense layers: first, that supervisor admission (`assertNoProjectAntigravityExtensions`) refuses an unisolated subfolder inside this layout with the `WorkspacePathError` naming the planted ancestor configuration (any other error, or acceptance, yields `project_config_admission_not_refused`); second, that when the workspace has its own proven Git boundary (`.git`), a control probe and five zero-inference read-backs run without loading ancestor configurations (`loaded` empty: no marker in a read-back or in any request to the scripted model, no planted hook or MCP command run, and `/config` still strict).
