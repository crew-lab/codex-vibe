# Dispatch authorization and one-shot stability

The current implementation uses exactly Vibe 3.0.2 and five one-shot MCP tools. Each start requires a locally registered, single-use dispatch authorization and attempt. See [ADR 0010](adr/0010-dispatch-attempt-authorization.md). Continuation is deferred. The previous six-tool archive and its evidence remain historical; they do not qualify this changed source. Hosted inference remains paused.

# Patch acceptance and reporting

Edit requests may supply an optional strict `acceptance_contract` before dispatch:

```json
{"schema_version":1,"allowed_changed_paths":["src/app/page.tsx"],"required_changed_paths":["src/app/page.tsx"],"checks":[{"id":"heading","kind":"text_contains","path":"src/app/page.tsx","value":"Release notes"}],"required_validations":["build"]}
```

Supported assertions are `file_exists`, `file_absent`, `text_contains`, `text_not_contains`, and `file_sha256`. Paths are exact repository-relative names, not globs. The normalized contract is hashed and frozen before launch. Exact checks inspect the committed base plus exported patch using a private Git index; worker summaries and subsequent worktree edits are not evidence. Checks never execute project code. Private bounded file snapshots allow re-verification after worktree cleanup. Missing, unsafe or changed inputs produce `incomplete`, never PASS.

Same-session corrections ([ADR 0009](adr/0009-vibe-3-supervised-corrections.md)) are not available: every run is one-shot and the catalogue has five tools. Records from the earlier correction experiment stay readable in state `awaiting_validation`; an assessment of one must name its `candidate_revision` and both hashes, and closing it after an accepted assessment of the latest revision marks it completed.

Execution state, automated verification, and coordinator assessment are separate. Normal `completed/end_turn` is required for automated PASS. Existing callers without a contract receive `not_requested`. `vibe_close` accepts an optional `assessment` containing decision, reason, patch_sha256, contract_sha256 and validations. Acceptance requires matching artifact hashes, a fresh automated PASS and passed coordinator validations for every required ID. Assessments append; corrections after closure preserve earlier decisions and do not restart inference. Coordinator validations are reported evidence, not independently executed by Supervisor.

```text
vibe-supervisor runs verify RUN_UUID --out /private/report-parent/new-report
vibe-supervisor runs export RUN_UUID --out /private/report-parent/new-report --include patch,events --validation /private/validation.json
```

The output parent must already be canonical, owner-private and writable. Destinations must not exist. Read-only lookup supports direct and isolated session records without borrowing live owner locks. Bundles include report.json, checks.json, diagnostics.json, REPORT.md and SHA256SUMS, and approvals.json when the run saved its [approval ledger](#approval-ledger-and-pin-identity). Optional patch export preserves exact bytes or refuses inclusion when credential detection triggers. Optional events expose only projected diagnostic fields; raw transcripts, tool arguments, receipts, histories and reasoning are excluded. Private paths are replaced in public reports. Exports do not integrate patches, run project commands, infer missing model identities, or assert hosted acceptance.

Validation manifests use schema_version 1, the exported patch_sha256 and unique validations with id/status (`passed`, `failed`, `incomplete`), optional evidence_sha256 and reference. Treat exports containing project patches as private project material.

Runtime observations record the reported session model, alias and thinking setting at startup and each verified handoff. Report version 2 keeps runtime labels separate from an explicitly selected requested model; this backend has no explicit model selection, so the requested model is unavailable. Requested thinking is `off` only when the saved runtime observation records the supervisor session configuration; older records without that field report the request as unavailable. Thinking status is `matched`, `drift` or `unavailable` against that saved request. Reports leave provider and underlying weights unknown. Usage preserves prompt/completion/cache tokens and model calls when available. Price availability and source are explicit; missing prices and cost remain unavailable, while a reported zero price produces an available zero estimate. This is a reported estimate only and does not establish a free provider entitlement or guarantee that no charge was incurred. Runtime/read identifies where a price value was observed, not whether the provider configured it; a zero may be a default for an unconfigured tariff. Do not use zero as proof of free usage or to satisfy monetary-limited dispatch until usable tariff provenance is explicitly established for that candidate. Legacy records with a saved cost preserve that estimate but do not infer a price source. Model calls are distinct from tool calls and Supervisor turn limits; the run's own audited tool outcomes are `usage.tool_calls` (`executed`, `denied_by_handler`, `denied_by_policy`), and the ceilings in force are in `limits` ([reference](reference.md#usage-ceilings-and-tool-call-counts)). Phase durations use saved timestamps and remain null when missing or inconsistent; execution includes finalization because the current lifecycle does not separately timestamp inference completion. Records written before a field existed do not invent its missing observations. Reports without `report_version` predate version 2; saved records remain readable.

## Approval ledger and pin identity

At settle the backend hands the approval handler's decision ledger to the run manager, which saves it as `artifacts/approvals.json` and lists it among the run's artifacts with its digest. Each record holds `callback_id`, `related_entry_id`, `turn_id`, `tool`, `path` (as the worker wrote it), `fingerprint` (the SHA-256 of the canonical input the callback showed), `decision` (`approve` or `deny`) and `reason` (null for an approval). The file is `{ schema_version: 1, run_id, truncated, records }`. It holds at most 4,096 records; `truncated` is `true` when the ledger filled (further callbacks are denied with the reason `ledger_full`) or more records existed than the file keeps. It holds the handler's own decisions, never task text, file contents or reasoning.

`runs export` adds `approvals.json` to the bundle when the saved run has one, after checking the file against the digest saved in the run record, its schema and its run id; a mismatch refuses the export (`Approval ledger does not match the saved artifact digest`). `report.json` then carries `approvals` (`file`, `source_sha256`, `records`, `truncated`). A run without a ledger, such as one that failed before a backend settled, exports without both. A coordinator checking a run for unapproved effects compares the ledger's `related_entry_id` values with the `entry_id` of every `tool_call` and `tool_denied` event (export with `--include events` for the projection).

The run record's `pin` (`vibe_version`, `manifest_sha256`, `record_sha256`) is written when the pin check passes at launch: the exact version, the SHA-256 of the manifest file that was read and the SHA-256 of the installed `mistral_vibe` `RECORD`. `report.json` carries it as `pin`, so a report names the exact manifest the run was admitted under. A record from before this field, or a run that never reached launch, has none.

## Measuring usefulness

`vibe-supervisor runs usefulness [--config <path>] [--since <YYYY-MM-DD>] [--json]` reads every saved record the way `runs list` does (the data root and its isolated sessions) and reports how often the coordinator accepted an edit. It never reads results, events or the task, and makes no model call.

- **What counts.** Only settled runs (`completed`, `failed`, `cancelled`, `closed`) created on or after `--since` (a calendar date, UTC). An edit run counts when its latest assessment is bound to its saved acceptance contract and `diff.patch` digests: `accepted` or `rejected` count toward the rate and print a row; `deferred` is counted apart; an edit with no bound assessment is counted as without a decision. An assessment whose hashes no longer match the saved contract and patch is ignored and counted in the summary.
- **Reviews are not assessable.** A review has no patch to bind an assessment to, so every settled review is counted as not assessable and never enters the rate.
- **Row.** One Markdown table row per decided edit: date, supervisor version, run id (first eight characters), shape (`edit`, the contract's check count, the changed-file count), measure (`max_turns`, stop reason, seconds, tokens, model calls and an estimated cost when the record has them), Yes or No, and the assessment's reason, flattened and cut at 300 characters. The task shape is not stored, so add it when copying a row into a log. A summary line follows (decided, accepted, rejected, deferred, without a decision, ignored assessments, reviews, unreadable records).
- **`--json`.** One JSON object per line: `kind: "row"` objects (`date`, `supervisor_version`, `run_id`, `shape`, `measure`, `accepted`, `reason`) and a final `kind: "summary"` object (`since`, `accepted`, `rejected`, `deferred`, `unassessed`, `not_assessable_review`, `unbound_assessments`, `unreadable`, `acceptance_rate`, null when nothing is decided).
- **Empty and bounded.** A data root that does not exist reports zero runs and exits 0. More than 10,000 saved runs, or more than 128 session directories, is refused with `VSUP_INVALID_STATE`; an unreadable record is counted, not fatal.

The rate measures the coordinator's decision, not whether the worker was right; assessments are reported evidence like the validations they cite.

## Execution lifecycle and reasoning observations

Closing a run is a resource lifecycle action. The run record keeps the terminal outcome (`completed`, `failed` or `cancelled`) as `execution_state` beside `state`, which becomes `closing` and `closed`; restart recovery records `failed` in both. `started_at` is written when the run is first observed running and is never moved by later callbacks or close. The report's `execution.state` takes the verification snapshot's outcome, then `execution_state`, and is `unknown` only for a closed record written without a saved outcome; `timestamps.started` is null when no start was recorded. Coordinator rejection of a completed answer is a separate assessment and must not relabel execution as failed. Inference-only duration is not estimated from total wall time.

The `reasoning_observation` diagnostic, recorded once when the turn concludes, contains only structured-entry counts: `streamed_entries`, `history_entries` (or null) and `history_audited`. Export with `--include events` to retain those fields. Content is discarded, and existing reasoning/secret filtering remains unchanged. Stream/history counts overlap and must not be summed. A count of zero means none observed, not proof that no provider reasoning was generated. Private-file word searches are not a measurement of reasoning generation.
