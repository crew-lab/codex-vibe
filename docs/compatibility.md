# Vibe compatibility and enforced local profiles

This document records behavior verified against the installed Mistral Vibe **2.25.8** package on macOS, plus the supervisor profile contract derived from that source. Vibe changes quickly; the supervisor must identify the executable version at startup and fail closed when a required check differs or cannot be observed.

## Enforced process profile

Each run must use a fresh owner-only `HOME` and a fresh owner-only `VIBE_HOME`. `VIBE_HOME` redirects Vibe's config, local `.env`, plugins, tools, skills, agents, hooks, trusted-folder records, history, and ordinary logs. A fresh `HOME` also isolates Vibe's separately resolved `~/.agents/skills` directory and the ACP message logger, whose path is hard-coded as `Path.home()/.vibe/logs/acp/messages.jsonl` rather than resolved through `VIBE_HOME`. Set `VIBE_ACP_LOGGING_ENABLED=0` explicitly. Never clone the user's full `~/.vibe` or `~/.agents` into these directories.

Vibe resolves its normal configuration in this order (low to high): schema defaults, GrowthBook experiment values, user TOML, trusted project TOML, `VIBE_*` environment, runtime overrides, active agent profile, then enforced admin config. `VIBE_*` fields use `__` for nested names; `enabled_tools` is replace-merged, whereas `mcp_servers` is union-merged by server name. An empty MCP list is therefore not a general-purpose deny override. Use a fresh `VIBE_HOME`, do not trust the project, do not provide `additionalDirectories`, and pass `mcpServers: []` in ACP. Verify the effective session and fail if any user/project MCP server or connector appears.

Vibe's ACP entrypoint always initializes both `user` and `project` harness sources. There is no `VIBE_*` switch to turn project sources off. With a fresh home, the project's trust record is absent. The installed harness manager applies project config and project hooks only for a trusted working directory; project tools, agents, plugins, and skills are discovered from the trusted roots. `session/new` reported `workspace_trust.status = "untrusted"` in the isolated probe. The supervisor must not call `trust/decide`, set trust, or pass a trusted/additional project root. If Vibe reports trusted or the effective config includes project content, the run must fail closed. Project `.env` is not loaded by the ACP entrypoint: Vibe loads only `$VIBE_HOME/.env`; however, the parent process environment is inherited unless the supervisor replaces it with an explicit allowlist.

The recommended read-only profile sets `VIBE_DEFAULT_AGENT=plan`, `VIBE_ENABLED_AGENTS=["plan"]`, and `VIBE_ENABLED_TOOLS=["read_file","grep"]`, and passes those settings as environment values or writes their equivalent into the isolated profile's known config. For each enabled file tool, set `permission = "never"` and configure the encoded literal grant `vibe-path:directory_recursive:<canonical-root>`. The pinned resolver authorizes the root and descendants at any depth; the legacy `<root>/**` form only covers immediate children. This allowlist is necessary: with no matching path-specific decision, `NEVER` is also the fallback for in-workspace paths. Put secret-file deny patterns before the allowlist, since Vibe checks denylist first; include root-level patterns (`<root>/.env`, `<root>/.env.*`, `<root>/.envrc`, `<root>/.envrc.*`) and recursive forms (`<root>/**/.env`, etc.). Do not substitute a global `always` fallback for a recursive grant. Vibe's resolver resolves symlinks before checking workspace membership and path patterns. The profile must reject every unexpected ACP permission request. The stock sensitive-file check can still produce an `ASK` request for a sensitive path inside the workspace even when the normal file permission is `ALWAYS`; never grant that request by default.

Vibe applies agent-profile overrides after environment settings. The supervisor therefore writes its own owner-only `plan.toml` or `accept-edits.toml` into the run's private `$VIBE_HOME/agents`. The pinned AgentRegistry explicitly supports shadowing built-in names through these files. The generated profile retains the environment's path grants, denylists, and exclusions, sets enabled file tools to a `never` fallback, and restricts the enabled-tool list to the run mode. It replaces Plan's private-plans-only read override and Accept Edits' global-write override without inheriting any user or project agent. Definitions are regenerated on recovery; unsafe symlink paths fail closed. Mode IDs stay `plan` and `accept-edits` for ACP compatibility.

The source names are class-derived and stable in this build: `read_file` is the file reader and `grep` is the local ripgrep/grep search. Search is read-only but still discloses matched source to the model. Do not enable `bash`, `experimental_bash`, `git_bash`, `windows_shell`, `write_file`, `edit`, `task`, `web_search`, `web_fetch`, `skill`, or MCP-provided tools in this profile. Shell tools can access process environment and the host filesystem beyond the file-tool policy. Do not treat Vibe's Plan label alone as a security control.

The run's private HOME and VIBE_HOME protect the user's configuration and logs from inheritance. Authentication is still private input to the Vibe process: Vibe can resolve `MISTRAL_API_KEY` from an inherited process variable, its own `$VIBE_HOME/.env`, or the macOS Keychain (`ai.mistral.vibe`, with legacy `vibe` fallback). In fallback mode, do not copy credential files or the user's full Vibe home. Preserve only an explicitly present, nonempty `MISTRAL_API_KEY` in the private child environment; it always wins and no Keychain lookup happens. An empty value counts as absent: the shim removes it and performs the lookup. Otherwise, on macOS only, the pinned shim looks the credential up itself, because the fresh private HOME hides the user's Keychain from Vibe. The lookup runs after the Vibe version, entrypoint, and logger-signature checks, so an unsupported Vibe never triggers it. The supervisor passes the trusted original HOME in one variable, `VIBE_SUPERVISOR_ORIGINAL_HOME`, for real runs only (`start` and `recover`); backend probes, and therefore `doctor` and `compat:probe`, never set it, so a probe cannot trigger a Keychain lookup or a macOS prompt. The shim removes it from its environment at startup and the value reaches only the `security` subprocess, whose entire environment is `HOME=<original>` and `PATH=/usr/bin:/bin`. The original HOME must be absolute, normalized, and a real (non-symlink) directory owned by the current user, or the lookup is skipped; trailing slashes are stripped first (`/Users/alice/` is accepted, `/` alone is not), while `..` segments, doubled separators, NUL, relative paths, symlinks, non-directories, and directories owned by someone else are refused. The skip diagnostic names the reason: `skipped-home:unset`, `not-absolute`, `not-normalized`, `missing`, `symlink`, `not-directory`, or `not-owner`. The exact command is `/usr/bin/security find-generic-password -a MISTRAL_API_KEY -s <service> -w` for service `ai.mistral.vibe`, then the documented legacy service `vibe` only if the first misses. It has a 5 second timeout, 8 KiB stdout cap, and discarded stderr. Output is decoded as strict UTF-8 with exactly one trailing newline removed; a non-zero exit, timeout, oversize, invalid, empty, or NUL/CR/LF-containing result yields no credential, and Vibe then proceeds and fails authentication normally with a diagnostic naming only reason codes. The `security` exit status is the low byte of the OSStatus: 44 (`errSecItemNotFound`, -25300) is `not-found`; 36 (`errSecInteractionNotAllowed`, -25308) is `locked`; 51 (`errSecAuthFailed`, -25293) and 128 (`errSecUserCanceled`, -128) are `denied`; any other non-zero status is `error-<status>`. The byte arithmetic is checked by the Python tests, but the mapping to real Keychain situations is best-effort and unverified against a real Keychain. The other reasons are `timeout`, `oversize`, `invalid-output`, and `error` (the runner itself failed). The diagnostic reports the most actionable reason across the two services (`locked`, `denied`, `timeout`, `oversize`, `invalid-output`, `error`, `not-found`, in that order) followed by every service's own reason, for example `locked (ai.mistral.vibe=locked,vibe=not-found)`; it never includes a value. A found value is set only in the shim's own `os.environ` (never in an exec'd environment, argv, file, event, or artifact), the shim's `sys.stderr` replaces the exact value with `[REDACTED]`, and the shim's native-history redaction already replaces it in persisted messages and metadata. Worker `HOME` and `VIBE_HOME` stay private. Stdout is not rewritten (it carries protocol frames), and writes that bypass Python's `sys.stderr` are not covered. The real Keychain lookup is unverified; tests use a fake or injected `security`. Never put a key in MCP arguments, ACP prompt text, supervisor events, transcripts, or error messages. A credential must not be handed to the model as prompt content. Since Vibe reads an API key to make model requests, the key is necessarily available inside the child process and to the configured provider transport. Ordinary backend close retains the private homes for retention/recovery handling; only the supervisor's retention cleanup should remove them.

The programmatic task prompt file (`task-prompt.txt`) is deleted by the shim after it is read. If the launcher never consumed it (version mismatch, failed `import vibe`, spawn failure, cancel), the supervisor removes it after the child exits or after a spawn failure, but only when it is still a regular, non-symlink file directly inside a real run directory; otherwise it is left untouched and a warning diagnostic is recorded.

Vibe 2.25.8's ACP message logger is disabled unless `VIBE_ACP_LOGGING_ENABLED` is one of `1`, `true`, or `yes`; if enabled it records the full incoming and outgoing JSON-RPC messages, including prompts, updates, and tool payloads. Vibe's session logging and histories also belong to Vibe, not the supervisor. Do not enable ACP message logging for normal runs. Treat Vibe logs, histories, transcript output, tool results, and reasoning-like content as potentially sensitive; do not claim to suppress Vibe's own logs, and do not expose hidden reasoning in the supervisor API. Retention/cleanup must cover the isolated home as well as supervisor artifacts.

### Pinned runtime shim and grep boundary

The supervisor launches both installed entrypoints through `src/backends/runtime/vibe_supervisor_launcher.py`; it does not edit Vibe's installed files. The shim accepts exactly Vibe 2.25.8, checks `SessionLogger` persistence signatures, sets `umask(077)`, forces the legacy harness, suppresses INFO logs (where this version logs the raw user prompt), and wraps append/overwrite/session-metadata disk persistence. It removes recursively named reasoning/thought fields and redacts known token/key patterns and sensitive credential-bearing field names before disk writes. A one-second watchdog kills the launcher's own detached process group when its parent disappears or the run lifetime elapses. Any version/signature drift aborts before work starts. This narrows persistent session data; it does not prevent provider transmission, redact unknown credential formats, or provide kernel isolation. ACP wire logging remains explicitly disabled; ERROR stderr output is streaming-redacted before supervisor events.

`src/backends/runtime/test_vibe_supervisor_launcher.py` is an opt-in no-prompt fixture against the installed Vibe logger. It verifies append, overwrite, and metadata storage remove reasoning and credential canaries while retaining public content and ordinary recovery fields. The Vibe Python 3.12 interpreter is required. Grep checks only its requested directory at the permission gate, then runs ripgrep/GNU grep and applies sensitive-pattern filtering after buffering process output. The profile explicitly excludes `.git/`, `.vibe/`, `.agents/`, common secret file extensions, and retains the stock generated/cache exclusions; it supplies root and nested dotenv patterns. Its configured result cap bounds returned output, not peak subprocess buffering. Symlinked `.vibeignore` is rejected. These remain Vibe application-level controls.

## ACP capabilities and version behavior

The isolated `vibe-acp` probe identified itself as `@mistralai/mistral-vibe` 2.25.8 and negotiated `protocolVersion: 1`. Initialization advertised `loadSession: true` and session `close`, `list`, and `fork`; it did not advertise a `resume` capability. ACP v1 baseline methods remain `session/new`, `session/prompt`, `session/cancel`, and `session/update`. The adapter can continue a live connected session and reconnect using `session/load` only when `loadSession` is advertised. It suppresses notifications while Vibe replays persisted session updates, does not resubmit the original task, and checks mode and workspace trust before continued work. Persisted run/home/VIBE_HOME paths must match the supervisor's trusted `dataDir/runs/<uuid>` layout; unverifiable records are not loaded. Pending permissions and elicitation are process-local and are never restored. Do not infer `session/resume` support from Vibe's internal `resume_session` implementation.

ACP 2.25.8 exposes both the legacy harness and an optional unified harness. `vibe-acp` may otherwise select unified from cached GrowthBook state; `--legacy-harness` forces legacy. These modes do not have identical permission/runtime implementations. The pinned runtime shim forces legacy for both ACP and programmatic launches, so unified is outside the supported profile. Any shim/version/signature drift aborts launch; do not fall back to whichever backend Vibe selects by default.

Vibe's default ACP mode in a fresh home is `accept-edits`. The probe showed that `VIBE_DEFAULT_AGENT=plan` plus `VIBE_ENABLED_AGENTS=["plan"]` makes `session/new` report `currentModeId: "plan"` and advertise only Plan as the available mode. This is evidence that mode selection can be constrained through Vibe's config. It is not evidence that tool names or path boundaries are enforced by themselves. Keep the exact enabled-tool filter and `NEVER` boundary rules as the actual controls, assert the requested mode and untrusted workspace after session creation, and fail if any profile other than the mode's single configured agent is active. Do not enable custom project profiles.

ACP 2.25.8's `request_permission` callback contains only a `tool_call_id` in its `toolCall` object. The action description/path is emitted separately in prior `session/update` tool-call updates. The supervisor must index and merge tool-call updates by ID, then correlate a permission request with that record before evaluating it. If the ID is unknown, incomplete, or its normalized path does not establish a safe action, offer only deny/cancel outcomes. A user or policy rejection is answered as `selected` with the offered reject option's ID (`reject_once` or `reject_always`), which lets the agent continue the turn; `cancelled` is reserved for a cancelled prompt turn, so cancelling or closing a run answers any pending permission request `cancelled` (and a pending elicitation with action `cancel`) before the process is terminated. An unknown, incomplete or overlapping permission request is refused the same way (reject_once, then reject_always, and `cancelled` only when no reject option is offered). `allow_always` is never selectable. This follows the ACP specification; real Vibe behavior after a selected reject is unverified. Do not infer a permission decision from a title or raw input fragment. A normal in-workspace read under the profile above should not request permission; sensitive files and unexpected tools still require a safe deny path.

Availability probes are cached per backend instance, keyed on the resolved executable path, its realpath and stat (mtime, size, inode) and, for ACP, the launcher interpreter's path and stat. A successful probe is reused for 10 minutes, a failed one for 30 seconds, and concurrent callers share one in-flight probe. `probe({ fresh: true })` bypasses the cache; `doctor`, `test-acp` and `compat:probe` build new instances and so always probe. A run now spawns Vibe for the probe at most once per cache window instead of twice per run.

Vibe initializes its OAuth/API-key authentication methods during ACP initialization. A fresh-home `session/new` without a key failed with `Missing API key for mistral provider`; a non-secret placeholder key allowed the local session object to be created without sending a prompt. The current compiled backend probe sends only `initialize` and needs no API key. It verifies ACP v1 and exact Vibe version; authenticated `session/new`, provider auth, and hosted inference remain untested by that command. No ACP message log was enabled.

## Revalidating a Vibe release

```sh
npm run build
npm run compat:probe -- --out compat-report.json
```

Options: `--vibe <path>`, `--vibe-acp <path>` (both default to `PATH` lookup, as the backends do), `--python <path>` (default: the interpreter named by the `vibe` entrypoint shebang, as the launcher derives it), `--out <file>`, `--help`. The JSON report (timestamp, Node/OS/arch, resolved executable paths, pinned versions, one record per check) is always printed to stdout. The exit code is non-zero if any check is `FAIL`; `MANUAL` and `SKIPPED` do not fail the run. A missing Vibe install is a `FAIL` on the first check. The script needs `dist/` and a real Vibe install, so it is not part of `verify:release`. No prompt is sent, no key is used, no Keychain lookup is made (the probes do not receive the original HOME), and ACP logging stays disabled.

| Check | Proves |
|---|---|
| `vibe_cli_version` | `vibe --version` equals the pinned version (single source: `src/backends/pinned.ts`). |
| `acp_initialize` | ACP `initialize` through the pinned launcher shim under isolated `HOME`/`VIBE_HOME` returns the exact pinned version and `protocolVersion` 1. |
| `acp_load_session_advertised` | `agentCapabilities.loadSession` is `true`, the precondition for `session/load` recovery. |
| `launcher_logger_fixture` | `src/backends/runtime/test_vibe_supervisor_launcher.py` exits 0 with the Vibe interpreter: persistence redaction still works against the installed logger. |
| `shim_pin_consistent` | `EXPECTED_VERSION` in the Python shim equals the TypeScript pin (the shim keeps its own copy because it runs inside the child). |
| `tool_path_resolver` | MANUAL. The stock `read_file`/`grep` resolver (exact-root and recursive allowlist, denylist first, `NEVER` fallback) is an internal Vibe API this repository does not document precisely enough to call without guessing. Re-run the scratch check from the results table above with the Vibe interpreter and compare against `core/tools/builtins/read_file.py`, `grep.py` and `core/tools/utils.py`. |
| `effective_tool_inventory`, `hosted_inference` | MANUAL. These need an authenticated hosted session (Handoff Phase 3). |

Dependent checks report `SKIPPED` when a prerequisite fails. To support a new Vibe release, first re-inspect the installed sources listed below, then update the pin in `src/backends/pinned.ts` and the shim, and only then run the probe. Record the outcome by keeping the JSON report with the release evidence, pasting the PASS/FAIL/MANUAL summary and the Vibe version into the results table above, and listing each MANUAL check as verified or still unverified. A green probe does not replace the manual checks.

## Installed profile regression check

With pinned Vibe installed, run `VIBE_SUPERVISOR_TEST_VIBE_PYTHON=/absolute/path/to/vibe/python npm test -- tests/unit/profile.test.ts`. The optional fixture uses the real agent registry, configuration layers, and file resolver for review and edit, with network connections disabled and no provider credential. It checks immediate/deep descendants, secret and reserved paths, sibling/outside paths, and symlinks to outside. Without this explicit interpreter, the two installed-runtime tests are skipped; ordinary profile tests still run. This fixture does not prove hosted edit, ACP continuation, or recovery.
