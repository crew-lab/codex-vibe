# The 2.0 path (2026-10-14)

Two 2.0 engines existed on 2026-10-14: `claude/app-server-design` (A) and `codex/unified-harness-v2` (B, commit `c3678cc`). Both are `vibe-app-server` clients for Vibe 2.26.1. A side-by-side review against the Vibe v2.26.1 source chose A as the base for the released 2.0.0, porting B's stronger pieces. B stays on its branch as a reference.

## Why A

Read from the Vibe source, B would fail every real start at read-back: it requires `max_turns` in `config/effective/read`, which `VibeConfigSchema` does not have, and compares MCP `args` and `env` that the server redacts (`_config_introspect.py`). It also maps `rate_limited` where the code is `rate_limit`, leaves experiments, auto-update and title generation on (network), runs with thinking `high` (reasoning on disk), and never deletes a crashed run's private directories. Its fake server mirrors its own shapes. A has the legacy engine removed, deeper tests and a fake built from the source answers.

## 2.0.0 scope

On A, before the target acceptance:

1. Handoff re-validation and usage continuity from B: on `session/compacted` or `session/contextCleared`, no unfinished effects or pending callbacks, a full audit of the old session, a fresh read-back, and usage offsets so the budget holds. Counters going backwards outside a handoff fail the run; a cost ceiling without prices fails closed.
2. Read-back additions from B: active agent, `default_agent`, MCP discovery errors, no callbacks, child sessions or background processes at start. Not B's `max_turns` or literal MCP argument checks.
3. Effect-to-callback fingerprints from B: one approval binds one effect and its exact input.
4. The bounded workspace file listing in review prompts (owner decision), as ADR 0004 says.
5. Cold review of the branch, then the target kit (step 10): manifest generation, a no-inference conformance check, readiness, one review, one edit, one MCP-client disconnect.

Release (owner decision, 2026-10-14): 1.0.1 is skipped. Once the 2.0.0 ports and the cold review land, the branch merges to main, which becomes the 2.0 line; 2.0.0 is cut once the target gates in `docs/acceptance.json` are verified. 1.0.0 stays the last 1.x release, with no `release/1.0` line.

## 2.0.1: one version, no history (owner goal, 2026-10-14)

2.0.0 is the stable major version. 2.0.1 drops support for every other version and removes everything about other versions and development history:

- **Supervisor versions.** 1.x is no longer described: no 1.0 configuration upgrade notes, no special handling of saved 1.x run records beyond refusing them, and no `historical_*` sections in `docs/acceptance.json`.
- **Vibe versions.** Only the one pinned Vibe release is described or accepted; nothing refers to the legacy harness, `vibe -p`, the Python launcher or earlier Vibe releases.
- **Development history.** `docs/history/` and `docs/reviews/` are removed from the tree (Git history keeps them), with ADR 0003 and every reference to rc candidates, the Unified Harness audit, the Codex branch and pre-2.0 decisions. `CHANGELOG.md` starts at 2.0.0. `Handoff.md` describes only the current state.

2.0.1 also carries the work below, each needing evidence 2.0.0 cannot give:

- **A shipped root of trust.** A per-release manifest derived from the published wheel (B's `vibe-2.26.1-macos-arm64.json`), so the pin no longer trusts the first manifest generated on the target. A's RECORD hashing stays for the rest of the environment. Building it downloads the wheel: owner authorization.
- **Search for reviews.** A supervisor-owned read-only search sidecar (B's `search.ts`, `search-server.ts`, `path-policy.ts`) exposed as an MCP tool, replacing the listing as the review's way to find code. Only after the 2.0.0 target runs confirm the MCP route names and tool inventory on the real server.
- **Ceilings in the run record.** Persist `max_tokens` and `max_cost_usd` per run, as B does.
- **Fixes from the 2.0.0 target evidence:** unknown history entry kinds seen on a real run, the `thinking = off` effect, the experiments fetch, nested `run_typescript` shapes.
- **The next Vibe release:** a new candidate with the conformance check, one review and one edit, per the exact-pin decision.
