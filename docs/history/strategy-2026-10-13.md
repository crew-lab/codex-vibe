# Strategy after rc.28 (2026-10-13)

What the project is for now that the runtime is verified, what the owner gets out of finishing it, and how it reaches other people. Written from the [Handoff](../../Handoff.md), the [competitive landscape](competitive-landscape-2026-10-13.md), the [ecosystem notes](ecosystem-2026-10-13.md) and the [article evidence](article/evidence.md). Numbers are the recorded ones; nothing here promises more than the evidence files hold.

## The strategy in one paragraph

Finish 1.0 on the verified rc.28 runtime and treat it as the proof, not the product. The product is a way of delegating between coding agents that can be checked: readiness on the live connection, one bounded run, a patch that is never applied, cleanup that cannot hide a lost edit, and a release gated by recorded evidence. Vibe 2.26.1 on the legacy harness is the first worker that way of working was proven on; Mistral has announced that engine's removal, so the next engineering theme is an adapter for the Unified Harness, which also makes the supervisor engine-agnostic. Meanwhile the thing to publish is the checklist, with the tool and its evidence trail as the worked example.

## The owner's wins

1. **A finished public artifact with an evidence trail.** A public MIT repository with a 1.0 tag, a machine-readable acceptance record, dated target evidence and a history of 28 candidates in eleven days. The honest parts (gates marked INCONCLUSIVE, usage marked UNKNOWN, a real review that failed acceptance) are what make it credible to an engineer who reads it. This is a portfolio piece about judgment, not volume.
2. **A transferable method.** The checklist from the article draft (a limit stop is neither success nor failure; readiness on the live connection; the worker's output is an artifact you review; process claims are counted, not believed; runs survive restart without replay; delete what no run needs) is a policy for any agent delegation, including internal ones at work. The supervisor is its reference implementation.
3. **A daily tool that costs nothing.** Every recorded hosted run fit inside the free Mistral credit (8.50 per month in euros on the owner's account; earlier edits cost about $0.02 each as Vibe reported). A second opinion from a different model family on a diff, from inside Codex, at that price, is useful in ordinary work once the task templates exist.
4. **First-mover position in a small niche.** There is no other Codex-to-Vibe path, and the two large platforms have an open request for Vibe support with nothing behind it. Being the person who documented Vibe's programmatic contract, its harness cutover and its export format has value in Mistral's community regardless of the tool's star count.
5. **A story worth telling.** Twenty-eight candidates, two machines, two agents (Claude on the preparing machine, Codex on the target) working the same repository, a cold review that found the safety check agreeing with the bug, and a product that got smaller as it got better. That is a talk, an article and a case study, each already half written.

## Benefits of the development

- **Lower correlated error.** A review from another vendor's model does not share the author model's blind spots; the recorded hosted reviews found a planted bug in a nested file and left the source untouched.
- **Bounded spend and blast radius.** Fixed turn, time and output limits, no retries, no replay, a patch instead of a commit. The worst case of a bad run is a retained worktree and a few cents.
- **A provider choice.** An EU model provider with a browser login and no API key in the supervisor; task text never in `ps`; private homes per run.
- **Reusable parts.** The launcher shim (private homes, filtered environment, prompt-file handoff, credential resolution), the private-index export and the owner lock are independent of Vibe and reusable in any CLI-agent adapter, which the Unified Harness work will show.
- **A release discipline.** Deterministic gates run by `verify:release`, hosted gates recorded with hashes, and a candidate that never becomes stable by assertion. Teams can copy `acceptance.json` and the runbook shape without the tool.

## Involving the community

In order of effort and return, after the 1.0 tag:

1. **Mistral's own channels first.** Open one issue on `mistralai/mistral-vibe` asking for the legacy harness removal timeline and whether `export.json` fills `usage` on the legacy path, citing the supervisor as a programmatic-mode consumer. Share the compatibility audit as a reference. A programmatic consumer with recorded evidence is the kind of user a CLI team listens to; the headless contract tests in their repository are a place to contribute.
2. **The open Vibe requests elsewhere.** Multica has an open issue for Vibe support and Paperclip has no adapter. One considered comment each, pointing at the launcher shim and the readiness contract as a reference for a safe adapter, not a sales pitch. Do not copy Multica code; its licence is not MIT.
3. **Registries and lists.** The official MCP registry and the curated MCP server lists, with the honest one-line description: one bounded Vibe review or edit for Codex, patch returned, never applied. Fix the GitHub repository description first; it still reads "Codex ASP client for Mistral Vibe".
4. **Good first contributions.** Label them: the Linux and Windows code paths that exist but are unclaimed, byte-reproducible builds, the clean-account install walkthrough, task templates for other languages, and the Unified Harness adapter itself once its interface is defined. Each has a test or an evidence file to produce, so a contribution is checkable.
5. **The article as the front door.** Publish the DEV article at 1.0 with the AI-assisted disclosure, then a Show HN and a LinkedIn post that lead with the checklist. Ask for one thing in each: readers who run a different coordinator or worker and would try the same contract.

## Propagation

The sequence matters: tag, then evidence, then story, then listings. A listing before the tag sends readers to a prerelease that says no platform is certified.

1. `v1.0.0` tag and release with the checksums and `acceptance.json`.
2. Article with the real numbers from the rc.28 and 1.0 sittings; `evidence.md` is the only source of numbers.
3. Show HN and a Mistral community post the same week; the Vibe issue the same day.
4. Registry and list submissions; repository description and topics.
5. Monthly: a usefulness log entry with the accepted and rejected real-project reviews, published as is. Rejected reviews are part of the story; they are what the templates improve.

## As a case study

Yes, and the frame is the method rather than the tool: "an evidence-gated 1.0 for an agent-to-agent tool, built by two agents on two machines". The sections that make it a case study are already in the tree:

- **Problem.** Let one coding agent hand work to another without the first one being lied to about what happened.
- **Constraint.** No OS sandbox, a worker that runs as the user, a provider that changes its engine mid-project, and a hosted budget of seven runs for the final sitting.
- **Approach.** Five tools, fail-closed pin, readiness receipts, patch-only edits, verified cleanup, restart without replay; everything else removed. The two-machine rule: the preparing machine never runs a real Vibe; the target machine never changes code.
- **Evidence.** `docs/acceptance.json`, the rc.28 target folder, the Node floor record, the cold reviews, and the CI history including the one red run caused by two agents fixing the same test runner.
- **Outcome.** The numbers from the sittings and the usefulness log.
- **Lessons.** The six from the article, plus two from this phase: a safety check must not share the exporter's blind spot, and two agents on one repository need a fetch-before-fix rule.
- **Risk stated plainly.** The pinned engine is scheduled for removal; the adapter is the next phase.

For a project list entry: name, one line, the tag, the article, the acceptance record, and the case-study page. Leave the star count out; the evidence is the credential.
