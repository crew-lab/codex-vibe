# Pre-1.0 cold review of the whole shipped surface

Date: 2026-10-08. Commit reviewed: 444b78c (package version 0.9.0-rc.9). The review read the committed tree (src, the Python launcher, schemas, scripts, README, CHANGELOG, Handoff, ADRs and docs) rather than a diff, because earlier reviews covered only per-release diffs from rc.1 to rc.9. Uncommitted work of other sessions in the same checkout was ignored. No Vibe process was started, and nothing under the user's Codex configuration, the Keychain or the real supervisor data directory was touched.

Verdict labels: CONFIRMED means the failure was traced through the code end to end (some also by running a small Node expression); PLAUSIBLE means the mechanism is real in the code but the trigger is narrow or depends on Vibe behavior that cannot be exercised here. Severity ranks are: blocker for 1.0, should fix before 1.0, after 1.0, doc-only.

Checks actually run: `npx vitest run tests/unit/errors-doc.test.ts tests/unit/tool-schemas.test.ts` (pass), `npm run lint`, `npm run typecheck` and `npm run secret-scan` (all pass; run in the shared checkout, whose uncommitted edits are not part of the reviewed commit). ## Summary

No code defect found that breaks a documented boundary in a way that exposes credentials, applies a patch, enables shell or network, or lets recovery replay a task or signal a stored PID. Six findings should be fixed before 1.0, nine can follow it, seven are documentation drift. The only blocker is the project's own list of unverified release gates, which is a verification matter, not a code defect.

Top items: a patch refused as "credential-bearing" for ordinary code such as `password: string` fails a whole edit run and leaves a worktree the supervisor can never remove (F1); an ACP worker that hangs during negotiation survives cancel, close and the run deadline until its own watchdog fires (F2); an edit worktree always contains the whole repository, so an allowlisted subdirectory does not bound what the worker sees (F3); `doctor` executes a project-relative `./vibe` when `paths.vibe` is a bare command name (F4).

## Findings

### Blocker for 1.0

**B1. Release gates are unverified (verification, not code). CONFIRMED.** `docs/compatibility.md:83-95`, `Handoff.md` (priority table, items 1 to 5) and `docs/acceptance.json` agree that the hosted soak has never passed (best attempt 19 of 100 runs, stopped on a driver timeout), native desktop use of any build after rc.2 is unverified, clean-account installation is unverified, the 15-minute silent worker stall is unexplained, and the release workflow is not in the tree (see D2). The docs state this honestly; the point here is only that, by the project's own definition, 1.0 cannot be tagged until these are recorded. No new work is asked of the code.

### Should fix before 1.0

**F1. A patch that merely resembles a credential makes the edit run fail and the worktree unremovable. CONFIRMED.**
Location: `src/git/worktree.ts:169-171`, `src/security/redaction.ts:7`, `src/core/run-manager.ts:1011-1017` and `:1190-1196`; documented at `docs/security.md:15`.
The export is refused whenever `redactSecrets(patch) !== patch`. The generic `key: value` pattern (`password`, `secret`, `passwd`, `api_key`, access and refresh tokens, followed by `:` or `=` and six or more non-space characters) matches ordinary code. A Node check showed that `  password: string;`, `+const secret = process.env.SECRET;` and `  secret: SecretString,` are all rewritten. The patch includes context lines, so the match does not have to be in a changed line.
Failure scenario: a coordinator asks Vibe to fix validation in an auth module whose file declares `password: string` within three lines of the edit. The turn completes, settlement tries to export, the export throws `VSUP_ARTIFACT_ERROR`, and a `completed` run becomes `failed`; no `diff.patch` is written. `vibe_close` with `cleanup_worktree` cannot succeed, because cleanup needs a verified export and finalization fails again ("No verified patch export"), and retention never removes a run that still has a worktree. The worktree stays on disk until a person deletes it by hand, and the edit result is lost to the coordinator.
Suggested fix: decide separately from the display redactor. Either scan the patch only for high-confidence shapes (PEM blocks, `sk-`/`ghp_`/AWS key prefixes, `Bearer <token>`, known sentinel values), or write the patch and report a `warnings` entry plus an `integrity`-style flag instead of failing; and let cleanup proceed when the saved export is complete. Add regression tests with `password: string` context.

**F2. An ACP worker that hangs during negotiation survives cancel, close and the run deadline. CONFIRMED.**
Location: `src/backends/acp.ts:214-272` (the process is spawned at `:227`; `launchSession` returns `state.ready.promise`, which has no timeout), `src/core/run-manager.ts:782-790` (the handle is stored only after `backend.start` returns), `:991-996` and `:1319-1324` (cancel and release do nothing without a handle), `:1252-1265` (deadline).
Failure scenario: Vibe ACP starts but stalls in `initialize` or `session/new` (provider hang, keychain prompt, slow import). The coordinator calls `vibe_close`, or the run deadline fires. Both paths call `cancelBackendSession`/`releaseSession`, find no handle and skip the kill, then settle the run (`cancelled` or `failed`) and release its slot. The worker keeps running until the shim watchdog's own deadline (`timeout_seconds`, up to 7200 s) or until `backend.start` finally returns and the launch code kills it. During that time more runs can start, so live workers can exceed `max_concurrent_runs`. The progress watchdog does not help because it is armed only in `running`. The recovery path has a 30 s load timeout (`acp.ts:549-565`); the start path has none, and no test covers a hanging `session/new` (the fake fixture hangs only on `session/load`).
Suggested fix: register the spawned process with the run (an early handle or a `terminate` hook returned before readiness), and add a start-phase timeout equal to the smaller of the deadline and a fixed negotiation limit.

**F3. An edit worktree always contains the whole repository, so an allowlisted subdirectory does not bound the worker. CONFIRMED.**
Location: `src/git/worktree.ts:136-145`, `src/core/run-manager.ts:238-243` and `:763-766`, `src/backends/profile.ts:115-118`.
`addDetachedWorktree` adds a worktree of the git root of `cwd`, and the worker workspace and file grants are the worktree root, not `cwd`'s position in it.
Failure scenario: the allowlist holds `/repo/services/api` (a subdirectory of a monorepo). `vibe_edit_start` with that `cwd` passes the root check, and the worker receives read and write grants over a checkout of the entire repository at the base commit, including `/repo/services/billing`. Everything the worker reads is sent to the provider, and the exported patch can touch paths outside the allowlist. The worker's start directory is also not the directory the coordinator named. Reviews are not affected, because they run in `cwd` itself.
Suggested fix: refuse an edit when the canonical `cwd` is not the git root, or, if subdirectory edits are wanted, start the worker in the matching subdirectory of the worktree, grant only that subtree and reject patch paths outside it. At minimum document that the whole repository is exposed.

**F4. `doctor` runs a project-relative executable when `paths.vibe` is a bare command name. CONFIRMED.**
Location: `src/diagnostics/doctor.ts:16-18`, `:72-75`, `:82-85`; accepted by `src/config/validation.ts:12`; advertised at `docs/reference.md:129-130`.
`findExecutable` returns `path.resolve(configPath)` for any configured value, so `paths.vibe = "vibe"` becomes `<current directory>/vibe`. `setup` writes absolute paths, so the exposure needs a hand-written bare name, which the reference documents as valid.
Failure scenario: a user whose config says `paths.vibe = "vibe"` runs `vibe-supervisor doctor` inside a freshly cloned repository that contains an executable file named `vibe` (or `vibe-acp`). Doctor executes it with `--version`. Without such a file doctor reports a false "found but probe failed". The run path is not affected: `resolveCommand` uses `which`.
Suggested fix: resolve bare names through `PATH` only (as `launcher.resolveCommand` does) and resolve only absolute entries directly.

**F5. Policy-violation failures and refused responses use `VSUP_PERMISSION_REQUIRED`, whose documented meaning and remedy do not apply. CONFIRMED.**
Location: `src/core/run-manager.ts:436`, `:441`, `:451-452`, `:951`; `src/contracts.ts:266` and `:281`; `scripts/errors-doc.mjs:20` and `:35`; `src/backends/acp.ts:419`.
`VSUP_PERMISSION_REQUIRED` is documented as "The run is waiting for a permission decision" with the remedy "Respond to the pending permission request". The code uses it when a run is failed because the worker asked for something outside policy (no request is pending), and when a `vibe_respond` option is refused. `VSUP_PERMISSION_DENIED` ("denied by policy") exists but is thrown only for `allow_always`. A coordinator reading the failed run's `error.remediation` is told to do something impossible, and a sibling case (`VSUP_INPUT_REQUIRED` for "not an elicitation", `run-manager.ts:445`) has the same shape.
Suggested fix: use `VSUP_PERMISSION_DENIED` for the policy-failure and refused-option cases, keep `VSUP_PERMISSION_REQUIRED` for "answer the pending request first", and regenerate `docs/errors.md`.

**F6. Input problems surface as generic codes. CONFIRMED.**
Location: `src/core/run-manager.ts:239` with `src/security/paths.ts:35-39`; `src/backends/profile.ts:19-21`, `:50-69`; `src/backends/acp.ts:209`; `src/backends/programmatic.ts:80-81`; `src/core/run-manager.ts:1523-1530`.
(a) A `context_files` entry that does not exist makes `realpath` throw a plain `ENOENT`, which the MCP layer reports as `VSUP_INTERNAL` ("The request could not be completed"), although the docs promise `VSUP_WORKSPACE_INVALID` for paths that do not exist or fall outside the allowlist. A Node check confirmed `code` is `ENOENT`, not a `VSUP_` code. (b) A workspace containing `.vibe` or `.agents`, a symlinked `.vibeignore`, or glob characters in its path is rejected inside `backend.start`, after the run was accepted (and, for edits, after the worktree was created); the plain `Error` is normalized to `VSUP_BACKEND_ERROR` with the generic message "The backend failed", and the reason is only in a `launch_failed` diagnostic event. The README and skills tell users the supervisor "refuses" such workspaces, which suggests a start-time `VSUP_WORKSPACE_INVALID`.
Suggested fix: validate `context_files` and the project-extension and glob checks synchronously in `start()` and throw `VSUP_WORKSPACE_INVALID` with a specific message.

### After 1.0

**F7. `respond()` can move a finished run back to `running`. PLAUSIBLE.** `src/core/run-manager.ts:454-458`, `src/backends/acp.ts:420`, `src/core/run-state.ts:11`. After the backend accepts the response, `respond` awaits a persist and then calls `setState(running)` unconditionally, outside the serialized queue. If the turn completes in that window, `completed -> running` is a legal transition, so the run shows `running` with no worker, the progress watchdog arms, and 600 s later fails a run that had completed. Narrow, because the profile makes Vibe ask almost nothing. Fix: make the post-respond transition conditional on the run still being `waiting_*`, or drop it (the backend callback already moves the state).

**F8. Deny-option detection is name-based in the policy engine but kind-based in the adapter. PLAUSIBLE.** `src/core/policy-engine.ts:26-29` and `:35` match `reject|deny|decline` against option id, kind and name, whereas `src/backends/acp.ts:142-145` uses `kind` equal to `reject_once` or `reject_always`. An option named, for example, "Allow once (never deny)" would be treated as the deny option for an execute-kind request. Needs an unusual Vibe option list. Fix: classify by the ACP `kind` only.

**F9. The elicitation validator is stricter than the schemas the adapter accepts. PLAUSIBLE.** `src/backends/acp.ts:102-125` admits schemas with extra keywords such as `title`, `description`, `default` and array properties; `src/core/run-manager.ts:1628-1650` rejects any root key outside `type`, `properties`, `required`, `additionalProperties` and any property key outside `type`, `enum`, `minimum`, `maximum`, `minLength`, `maxLength`. Fail-closed, but a typical form schema makes `accept` always fail with `VSUP_INVALID_ARGUMENT`, leaving only decline or cancel. Callbacks are an unverified gate, so this has never been exercised. Fix: share one validator, or allow annotation keys in both.

**F10. The allowlist accepts `/` and `~`; only `setup` and `allow` refuse them. CONFIRMED.** `src/config/validation.ts:15-16` and `docs/reference.md:113` accept `"~"` and any absolute path; `src/cli/setup.ts:46-47` refuses the filesystem root and the home directory; `doctor`'s `workspace-roots` check (`src/diagnostics/doctor.ts:109-113`) only tests that a root exists. A hand-edited `allowed_workspace_roots = ["~"]` therefore lets a coordinator review `~/.ssh` or `~/Library`. This is an operator decision, so it is hardening: make `doctor` warn, or have validation reject `/` and the home directory.

**F11. A worktree created after the run was closed is never cleaned up automatically. PLAUSIBLE.** `src/core/run-manager.ts:763-767`, `:650`. If `vibe_close` lands while `git worktree add` is still running, the run settles `cancelled` and closes, then `launch` records the worktree and returns. Retention skips any run with a worktree. The window is about the duration of the git call, and a second `vibe_close` with `cleanup_worktree` fixes it, but nothing tells the user to do that. Fix: after creating the worktree, if the run is already terminal, export and remove it or record a retained reason.

**F12. Raw child stdout is capped by the transcript limit. PLAUSIBLE.** `src/backends/acp.ts:228`, `:520`, `src/backends/programmatic.ts:113`, `src/process/managed.ts:66`. `maxStdoutBytes` is `limits.max_transcript_bytes` (10 MiB), but for ACP stdout is the whole JSON-RPC wire (tool results, thought chunks, usage) and the count is cumulative across `vibe_continue` turns and idle time. A long ACP review session can fail with `VSUP_OUTPUT_LIMIT` long before the transcript is large. `docs/functionality.md:132` mentions stdout overflow only for programmatic runs. Fix: a separate wire limit, or document the semantics.

**F13. Shutdown from stdin close, SIGINT or SIGTERM has no overall deadline. PLAUSIBLE.** `src/cli.ts:71-79`, `src/core/run-manager.ts:662-687`. `manager.shutdown()` awaits each run's serialized queue and the artifact export (`git diff` up to 30 s per edit run) with no cap; only the uncaught-exception path has a 5 s bound (`src/diagnostics/background.ts:41`). A hung step leaves the process alive after its client has gone. Workers still die through the shim's parent watchdog. Fix: bound the shutdown and exit.

**F14. Unused runtime dependency. CONFIRMED.** `package.json` lists `@modelcontextprotocol/node` under `dependencies`; nothing in `src`, `tests` or `scripts` imports it. It widens the install and the SBOM for no benefit.

**F15. Worktree cleanup trusts the persisted worktree path. PLAUSIBLE.** `src/core/run-manager.ts:1186-1198` passes `record.worktree` from `meta.json` to `removeVerifiedWorktree`, which accepts any registered worktree of the source repository. ACP recovery, by contrast, re-derives `dataDir/worktrees/<runId>` and rejects anything else (`src/backends/acp.ts:495-499`). Only someone who can already write the data directory could exploit it, but the checks should match. Fix: require the path to equal the derived location before removal. (Related: `src/core/serialization.ts:132` keeps a hand-written copy of the error-code list, currently in sync with `src/contracts.ts`; derive it from the contract so a new code cannot be silently dropped on reload.)

### Doc-only

**D1. Error documentation drift.** `scripts/errors-doc.mjs:26` says `VSUP_TIMEOUT` also covers "a session load did not answer in time", but the code and `docs/functionality.md` use `VSUP_SESSION_NOT_RESUMABLE` for that (`src/backends/acp.ts:565`); `VSUP_TIMEOUT` is thrown only by the run deadline. The remedies for `VSUP_ACP_INIT_FAILED` and `VSUP_BACKEND_CRASHED` (`src/contracts.ts:259`, `:271`) send the reader to a "stderr log" that does not exist; stderr appears as `diagnostic` events.

**D2. The release workflow is documented as shipped but is not in the tree.** `CHANGELOG.md:49` (rc.6) says a `v<version>` tag builds and attaches the tarball to a GitHub Release, and `README.md:20` installs from a release; `.github/workflows` contains only `ci.yml`. `Handoff.md` lists pushing the workflow as pending, so the changelog entry is premature.

**D3. Documents promise run-time verification the code does not perform.** `docs/compatibility.md:9` ("Verify the effective session and fail if any user/project MCP server or connector appears") and `docs/adr/0003-vibe-launcher.md` ("must verify ... tool inventory ... fails closed") describe a check of the effective tool inventory. The ACP start verifies only version, protocol, mode and workspace trust (`src/backends/acp.ts:330-351`); the programmatic start verifies none of these at run time; the tool inventory is a manual compat gate. The pinned version and the env-driven profile make this safe for 2.25.8, but the text should say "pinned" instead of "verified at start". `docs/adr/0002-protocol-security-boundary.md` also still describes the allowlist as "exact root plus `<root>/**`", superseded by the recursive grant in `src/backends/profile.ts:36`.

**D4. Tool description omits a state.** `src/mcp/tools.ts:29` says `vibe_continue` accepts "a completed or ready run"; `docs/reference.md:16` and `src/core/run-manager.ts:102` also allow `recoverable`.

**D5. One unqualified verification sentence.** `README.md:104` says desktop registration and hosted review and edit runs "are verified on macOS arm64". `docs/compatibility.md:85-95` shows that evidence comes from a locally patched rc.2 build plus scoped rc.7 runs, and that current-build desktop use is unverified. Add the build to the README sentence.

**D6. README edit example names a path the worker cannot read.** `README.md:59` asks for a fix in `/absolute/path/to/repo/src/validate.ts`, a source-checkout path, while the worker runs in a worktree under the data directory whose grants cover only that worktree (`src/core/run-manager.ts:242`, `src/backends/profile.ts:115-118`). The task text is passed through unchanged. PLAUSIBLE wasted turns; give the example as a repository-relative path.

**D7. `docs/security.md:3` says export verifies "the patch and changed-file records".** Cleanup verifies only the `diff.patch` digest and a fresh export (`src/git/worktree.ts:194-207`); `changed-files.json` is not compared. Say "the patch". Smaller drift: `schemas/config.schema.json` accepts any content under `phase1` and `security`, while the validator accepts only the six removed keys.

## What was checked and found clean

- Config validation against `schemas/config.schema.json`, `src/config/defaults.ts`, `examples/config.toml` and `docs/reference.md`: every key, default and bound matches (apart from D7).
- MCP schemas (`src/mcp/schemas.ts`) against `docs/reference.md` input tables, including strictness, `wait_seconds` and `max_events` ranges, and the seven-versus-five tool registration rule.
- `REMEDIATION` against `docs/errors.md` (the generated file is in sync and the test passes; D1 is about the source text) and the error-code set used for saved records.
- CLI (`src/cli.ts`, `src/cli/*`) against README and reference: commands, aliases, exit codes, refusal of `/` and the home directory, backup naming, Codex entry values (`startup_timeout_sec = 30`, `tool_timeout_sec = 600`).
- State machine (`src/core/run-state.ts`) and settlement: one path, slot released in `finally`, requested outcomes win over backend reports, completed runs are never moved to failed, shutdown records `recoverable` or `cancelled`. No slot leak found on cancel during start, queue cancellation, failed launch or rejected continuation.
- Timers: deadline, idle expiry, idle cap and progress watchdog arm and clear consistently with `docs/functionality.md`; the watchdog is not armed while `waiting_*`, queued or idle, and cannot fire after an outcome was requested.
- Continuation: single-slot guard is synchronous (no double-continue race), cumulative `max_turns` rules match docs, recovery requires `loadSession`, the original task is never resubmitted, pending requests are cleared on restart.
- Persistence: atomic private writes, no-follow opens, event-log retry and structural-fault handling, torn-record truncation, lazy loading, retention and the closed/terminal rules.
- Owner lock: exclusive create, recovery guard, stale and reused-PID detection, never removes a live lock, signal 0 only.
- Process handling: process groups, bounded output collectors, SIGTERM then SIGKILL with a bounded wait, degraded group termination reported rather than hidden; git helper runs with hooks, filters, external diff and global config disabled.
- Launcher shim: exact version and signature checks, prompt-file consumption (regular, owner-only, size-capped, deleted before Vibe starts), Keychain lookup argv, timeout and output cap, original-HOME validation, watchdog reading a validated deadline file, parent-death detection, 48-hour cap, diagnostics sidecar safety.
- Review integrity: snapshot and compare logic, manifest persistence and digest check, touch-versus-change handling, `unverified` rather than `changed` when the manifest is missing.
- Documentation: `security.md`, `README.md`, `SECURITY.md` and the skills consistently call the policy an application-level boundary and never a sandbox; `docs/compatibility.md` lists the unverified gates once and the README and security pages link to it rather than restating them.
