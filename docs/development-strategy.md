# Development strategy

How vibe-supervisor is developed, verified and released from 2.0 on: the picture, the plan and the rules. [Handoff.md](../Handoff.md) holds the current status (what is done, what remains, who acts, what is open) and is not repeated here.

## Vision and scope

vibe-supervisor is one thing: a local MCP server that lets a coding agent delegate one bounded review or one isolated edit to Mistral Vibe, as a client of Vibe's `vibe-app-server` protocol ([ADR 0004](adr/0004-app-server-client.md)). The five MCP tools and the boundaries in [AGENTS.md](../AGENTS.md) are fixed. Work goes into making that one path correct, observable and verified, not into new surfaces.

- **One engine.** No second backend, selector or fallback. A future Vibe engine is supported by moving this client, not by adding another.
- **One Vibe version.** Each release pins exactly one Vibe release: the server's reported version plus the installed files hashed against a per-candidate manifest. A new Vibe release is a new supervisor candidate with its own manifest and conformance check.
- **One supported line.** Only the latest 2.x release is supported. 1.0.0 was the last 1.x release, 1.0.1 was never released, and there is no 1.x maintenance line. 2.0.0 is the stable major version; 2.0.1 removes every other version and the development history from the tree.
- **Enforcement the supervisor owns.** The client decides every approval, reads the effective configuration back before the first turn, audits every effect, and fails closed on anything it cannot account for. It never imports or patches Vibe. This is application policy, not an OS sandbox, and is never described as one.
- **Client-agnostic by protocol, verified per client.** Nothing on the MCP side is written for Codex; Codex is simply the only client with recorded evidence. Another client earns a support claim through its own gates on the target machine (readiness, one hosted review and one edit, a disconnect), never through runtime code written for it first. Google Antigravity is the candidate, as a client only ([research](../research/antigravity-2026-10-14.md)): no surface of it offers supervisor-owned approvals, a configuration read-back or an engine that can be pinned, so it is never a worker.
- **Evidence or "unverified".** A claim about hosted behaviour, a native client or a platform is made only when `docs/acceptance.json` records it. Until then the gate stays open and the documentation says so.

## Where 2.0.0 stands

**Built.** Branch `claude/app-server-design` replaces the 1.x engine wholesale: the legacy harness path, the Python launcher, the `backend` key, the programmatic backend, the worker diagnostics file and the `grep` tool are gone. In their place: a JSON-RPC client of `vibe-app-server` with a typed protocol subset, session configuration and read-back, an approval handler, an event validator, usage and outcome mapping, a pin check with its `pin-manifest` command, the credential lookup in Node, a reaper process, and a bounded workspace file listing in the prompt. A side-by-side review against the parallel Codex branch `codex/unified-harness-v2` chose this branch as the base and ported three of its pieces: handoff re-validation with usage continuity, more read-back checks and effect-to-callback fingerprints. The version is 2.0.0 in `package.json`, `package-lock.json` and `.codex-plugin/plugin.json`, with the changelog entry and release wording in place.

**Fixed by the cold review.** A reader with no design context reviewed the branch after a green suite and found eleven findings; ten are fixed with regression tests: a reaper stopped when a failed start could not confirm the worker's exit; a configuration without `paths.vibe_pin_manifest` blocking the command that writes it; a budget or deadline stop skipping the final history audit yet reporting `completed`; executed-then-cancelled effects unchecked against the approval ledger; approvals still granted after a stop; a protocol fault hidden by a later cancel; the watermark advancing past queued notifications; worker stdout held twice with quadratic copying; the pin verified on the resolved path but the worker spawned from the unresolved one; restart cleanup racing a dying worker. Also fixed: a missing `hooksCount` in `config/read` read as zero, a completed turn with a running effect not failed, and a worker without stdio unguarded.

**Documented limits.** The eleventh finding is accepted and written down: the pin covers only the installed `mistral_vibe` distribution's `RECORD`, not dependencies, `.pth` files, the interpreter or `__pycache__`, and it runs before the process starts, so it detects drift, not a malicious original ([security](security.md#process-configuration-and-persistence)). Other limits 2.0.0 states rather than closes: the model-visible catalogue cannot be narrowed, so `write_file`, `edit`, the shell tool and `run_typescript` are listed and refused, never hidden; reviews have no search tool; the event validator is detective, so it can stop a run and record a breach but not undo it; token and cost ceilings can overshoot by one model call; cost is an estimate; and all of it has run against the scripted fake only, never against a real Vibe.

## Architecture and enforcement points

One run is one `vibe-app-server` process, driven over newline-delimited JSON-RPC on stdio. The run manager (admission, slot, snapshot or worktree, settlement, retention) is the 1.x frame, unchanged; the engine adds the points below. Preventive points stop a call before it runs; detective points notice it afterwards and interrupt. [Security](security.md#enforcement-points) is the normative text.

| Point | What happens | Fails closed on |
|---|---|---|
| Launch | Pin check and credential lookup (`MISTRAL_API_KEY`, or the macOS Keychain through `/usr/bin/security`) before any process exists; then `vibe-app-server` from the real path the pin hashed, no arguments, own process group, filtered environment, private `HOME`, `VIBE_HOME` and `TMPDIR` in the run directory. The task travels in `turn/start`, never in arguments. | Pin or credential failure, before spawn |
| Pin | Installed files match the manifest `pin-manifest` wrote on the Vibe machine; `serverInfo.version` equals 2.26.1 after `initialize`. | Any version, `RECORD`, file or unsafe-file mismatch (`VSUP_VIBE_VERSION_UNSUPPORTED`) |
| Session configuration | `agentConfig` with the worker workspace as `cwd`, a supervisor-written profile (`permission = "ask"` plus the reserved-directory and secret-file denylist per tool), `enabledTools`, `disabledTools`, `maxTurns`, no auto-approve, no workspace trust, no roots, no MCP servers; `VIBE_*` settings turn off subagents, shell, connectors, skills, MCP, telemetry, updates, experiments and session logging; thinking off through `config/model/write` before the first turn. | Preventive by construction |
| Read-back | `runtime/read`, `config/effective/read` and `config/read` must show exactly the profile tools, no skills, MCP, connectors, hooks or issues, bypass off, the unified harness, the expected `cwd`, every setting above, `ask` and the exact denylist per tool, thinking off; repeated after thinking is written and after every handoff. | Any difference or missing field (`readback_mismatch`), before the first turn |
| Approvals | The supervisor answers every `callback/call`: approve only the profile's tool (`file_system.read_file`; for an edit also `file_system.write_file` and `file_system.search_replace`) with the matching effect kind on an in-workspace path that names no reserved directory or secret file; deny everything else within 5 seconds; never a session or permanent approval; each approval bound to one effect by a fingerprint of the shown input. | Deadline, repeated id, malformed callback, wrong session, revoked handler: deny |
| Event validation | Every history entry is classified; reasoning is dropped on receipt. A denied effect is recorded as `tool_denied` and the run continues. An allowed or executed effect is approved only with decision `execute`, type `ask`, source `user`, linked to the handler's approval for the same effect, tool and turn, with an equal fingerprint; null metadata is unapproved. | `turn/interrupt`, then `VSUP_BACKEND_ERROR` with `details.reason` (`unapproved_effect`, `unknown_entry_kind`, `watermark_gap`, `unfinished_effect`, a malformed notification) |
| Handoffs | `session/compacted` and `session/contextCleared` are accepted only from the active session, with a watermark, no open gap, no unfinished effect, no open callback; the new session's history is paged and every settled effect compared with its fingerprint; the read-back repeats; usage totals carry across. | `session_handoff_unsafe`, `historical_effect_changed`; a failed re-validation revokes the handler |
| Usage and budgets | No run export exists, so tokens, model calls and cost are rebuilt from `session/statsUpdated` and `runtime/read` with Vibe's pricing formula; `maxTurns` is Vibe's iteration limit, backstopped by the model-call count; `limits.max_tokens` and `limits.max_cost_usd` interrupt the turn when crossed. | `usage_counter_regressed`; `price_unavailable` when a cost ceiling has no price |
| Outcome | Turn status, stop reason and error code, supervisor-detected limits first: `end_turn`, `turn_limit`, `token_limit`, `price_limit`, `refusal` (completed with a warning), `cancelled`; the error-code mapping settled by the owner (`VSUP_AUTH_REQUIRED`, `VSUP_BACKEND_ERROR`, `VSUP_OUTPUT_LIMIT`, `VSUP_RATE_LIMITED`) is in [functionality](functionality.md#settlement-and-close). An earlier protocol failure outranks a later cancel or deadline. | A limit stop whose final audit could not run (`audit_unavailable`) |
| Reaper | A small Node process in its own group kills the worker's group when the supervisor's PID disappears or the deadline plus a 15-second margin passes; it stays running when a stop cannot be verified, a failed start included. | Nothing; it is the backstop |
| Cleanup | Every stop revokes the handler first, sends `turn/interrupt`, closes stdin (Vibe's clean path, which removes its throwaway store), waits, kills the group if needed, verifies termination, then deletes `child-home`, `vibe-home` and `tmp`; a review's snapshot comparison and an edit's export and verified worktree cleanup are the 1.x checks. | Unverified termination keeps handle, slot, worktree and lock (`worker_termination_unverified`); undeletable state is a `private_state_retained` warning |
| Restart | Interrupted runs are marked failed; recovery waits for the old reaper (at most 6 seconds), then deletes the private directories before the server accepts work. Nothing is launched, resumed, replayed, restored or signalled from saved data. | Nothing is trusted from saved state |

Around this sit the 1.x controls: strict schemas and exactly five tools; the owner-controlled allowlist reread before every readiness check and start; boot-bound settings that demand a restart; readiness receipts (HMAC, 10 minutes, bound to instance, policy revision, operation, workspace and edit base); one active slot per instance with an owner lock; `--isolated` storage per connection; bounded, redacted, atomically written persistence.

## Verification model

Four layers, each honest about what it cannot show.

1. **Source-read facts with hashes.** Every wire fact the client relies on was read from Vibe's tagged source (`v2.26.1`, commit `4ae5c5955da8e761318916bdb1a7f46f0b50c7d0`) without running it, and recorded with the SHA-256 of each file read. The protocol audit, the source answers and the design note stay in the source repository under `docs/history/`; [compatibility](compatibility.md#wire-facts-the-client-relies-on) carries the facts the code depends on.
2. **The scripted fake.** `tests/fixtures/fake-vibe-app-server.mjs` speaks the audited subset from scenario files, written from the source answers independently of the client's types. It checks inbound parameters strictly, as the real server's models do, and refuses snake_case effect inputs and unknown keys. It proves the client against the source facts, not against Vibe.
3. **Cold reviews and local release checks.** A reviewer with no design context reads the diff before every merge. `npm run verify:release` (lint, typecheck, build, tests, acceptance, secret scan, SBOM) runs locally on every change; there is no GitHub CI, because the owner skipped the push token's `workflow` scope. For 2.0.0 the run on exactly Node 20.19.0 passed with 83 test files and 1244 tests and is recorded as gate `node-floor-20.19.0` (`PASSED_LOCALLY`). `npm run package:rc` adds the offline installed-package smoke test with its exact five-tool catalogue.
4. **Target gates with owner authorizations.** Every claim about a running Vibe, a native client or a platform is a named gate in `docs/acceptance.json`, `UNVERIFIED` until the target machine records its evidence; each needs the owner's separate authorization and, for hosted runs, a budget, and the target changes no code. The 2.0.0 gates are listed in [compatibility](compatibility.md#unverified-gates): the no-inference conformance check (`scripts/v2-conformance-check.mjs`), native readiness, one hosted review and edit, an MCP-client disconnect, `permission = "ask"` visible and reaching the handler, thinking off, the experiments fetch, nested `run_typescript` gating, and the clean-account installation. The target brief in `docs/history/` orders them and stops at the first failure.

**Open protocol questions that fail closed.** Only a real server can settle these, and in each case the client refuses rather than guesses: whether a callback's `relatedEntryId` is filled at the entry or only in `detail` (if only `detail`, every approval is refused); whether handler-approved effects carry `approvalType` `ask` and `approvalSource` `user` (if not, every approved call fails the run); whether `agentConfig.maxTurns` is enforced (it is not read back, and the model-call backstop turns off when Vibe reports no count); how long Vibe keeps a callback open (the handler answers within 5 seconds regardless); whether a large legitimate `write_file` fits the 8 MiB line cap. Whether thinking off stops reasoning generation, which the throwaway store would hold until cleanup, is an observation gate. The target brief records which way each goes.

## Lessons from building 2.0

**About Vibe's protocol.** Each of these was a guess that would have broken every real run, caught only by reading the tagged source:
- Wire fields are camelCase (`filePath`), because app-server models serialize by alias. The Python attribute name is not the wire name.
- Callbacks and effects name tools `file_system.read_file`, `file_system.write_file` and `file_system.search_replace`; `enabledTools` takes the config names `read_file`, `write_file`, `edit`.
- `read_file` defaults to `always`, and a path allowlist resolves to `always`: both skip the approval callback. The agent profile sets `permission = "ask"` and carries only the denylist.
- Vibe can allow a call without asking (scratchpad paths, session grants, the bypass gate). Only an `execute` / `ask` / `user` effect linked to the handler's own approval counts as approved.
- `vibe-app-server` writes no run export, so usage is rebuilt from events, and counters reset at a context handoff.
- `config/effective/read` has no `max_turns`, and the server redacts MCP `args` and `env`. A read-back that expects either fails every start.
- After a handoff, the new session id is `sessionId`; the old one is `oldSessionId`.

**About verification.**
- A fake server encodes what we believe. It proves the client against those beliefs, not against Vibe. Write the fake from source answers with file hashes, and reject anything the source contradicts.
- An independent implementation is a strong check. The parallel Codex branch and this one each caught errors the other made.
- A cold review before every merge pays for itself. The 2.0 branch review found a reaper dropped on a failed start, approvals still granted after a stop, and protocol faults hidden by a later cancel, all after a full green test suite.
- Grep-based audits miss behaviour; read the tagged source and record its hashes.

**About working with agents.**
- An agent must never stage, move or remove files in Git. One agent's staged removals once went into an unrelated docs commit and published a half-removed engine. The coordinator commits by path.
- Chain every check and the commit with `&&`, so a failed check stops it. A secret-scan failure was once committed because the command continued.
- Fake credentials must not look like keys: `/\bsk-[A-Za-z0-9_-]{24,}\b/` fails the secret scan.
- Agents write files with the Write tool, never with heredocs that wait on stdin, and avoid aliased `ls`; both left hung shells. After an agent finishes, check for its leftover processes.
- Give each agent named files, the wire facts it must use, and what it must not touch; forward any fact one agent finds that another depends on.
- A test that passes alone and fails under full parallel load is a timing issue to fix, not to retry until green.

## Working rules

- **Verification is local.** There is no GitHub CI: the token's `workflow` scope was skipped. Every change ends with `npm run verify:release`; a release adds `VIBE_SUPERVISOR_TEST_NPM_CACHE=<populated cache> npm run package:rc` and a run on Node 20.19.0.
- **Two machines.** Vibe is never installed, run or tested on the preparing machine, the installed-Vibe fixture included; questions about Vibe are answered from its tagged source, checked against the recorded hashes. Behaviour is proven only on the target machine, with the owner's authorization and budget; the target records evidence and changes no code. Version numbers and runtime code change on main.
- **Fakes prove the client, not Vibe.** A gate is verified only by target evidence; missing evidence stays "unverified", never a guess.
- **Evidence uses placeholders from the start** (`docs/reviews/REDACTION.md`), because the repository is public. No credential or private session history reaches any committed file, prompt, transcript or report.
- **Agents work in parallel on disjoint files.** Each agent owns named files, commits nothing, and reports what it could not verify. The coordinator runs the full checks before every commit, and nothing is committed while a check fails.
- **Branches.** Work happens on a branch and reaches main by merge after the full checks and a cold review. Push with `make push` (main) or `make push-branch BRANCH=<name>`.
- **Owner decisions are explicit.** Pushes, hosted runs, releases, scope readings, vendor downloads and every public post need the owner's separate yes, recorded in [Handoff.md](../Handoff.md).
