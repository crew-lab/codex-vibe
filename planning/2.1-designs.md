# 2.1 design sketches

Companion to the [development plan](development-plan.md), section 5. One sketch per item: what the user sees, the data shapes, the files, the boundary check against [AGENTS.md](../AGENTS.md), the tests, the gate entry, size and dependencies. Written 2026-10-15 against main at `b7ac223` (2.0.1); every path was checked in the tree. Not shipped.

**Status after the workflow line was integrated (2026-10-15).** 2.0.1 already delivers part of items 1, 2 and 6: prompt, completion and cached tokens, model calls, the cost source and model observations in every run record; an append-only `assessment` on `vibe_close` bound to the patch and contract hashes (item 2 keeps only `runs usefulness`, built on assessments instead of a separate `accepted` field); and `runs verify` and `runs export` as a sanitized bundle directory with optional patch and projected events (item 6 keeps the approval ledger). The preparation kit is not item 7. The [plan](development-plan.md#6-21-observable-and-measurable), section 6, has the narrowed list; where a sketch below conflicts with the delivered shape, the delivered shape wins. The search sidecar's ADR is 0007, because 0005 and 0006 are taken.

Conventions used throughout:
- **Absent versus null.** A wire field that is absent was never measured (the run ended first); `null` means the source reported no value. "An explicitly unavailable field is preferable to a zero" (Vibe issue 1161, quoted in the [features research](../research/features-2026-10-14.md)).
- **Wire names** are snake_case in `meta.json`, `result.json` and tool replies; TypeScript names are camelCase in `src/contracts.ts`. `src/core/serialization.ts` (`runToWire`, `runFromWire`) is the only translation point; `usageToWire` in `src/core/run-manager.ts` duplicates part of it and is removed in wave 0.
- **Compatibility of saved records.** Every new record field is optional, so a 2.0 record still loads (`runFromWire` ignores what it does not know today and must keep doing so).
- **Gate entries** follow `docs/acceptance.json`: deterministic entries carry `RUN_BY_focused-tests`; hosted observations start `UNVERIFIED` with `evidence_required` and move per the plan's section 3.3.
- **One 2.1 target sitting** covers items 1, 2, 3, 4 and 6 with one hosted review and one hosted edit; item 7 rides on the conformance check; items 5 and 8 add their own runs.

## 1. Usage, ceilings and tool-call counts in every run record

**Behaviour.** Every run record and result carries the numbers the supervisor already computes: prompt, completion and cached tokens, model calls, the cost estimate, and how many tool calls ran or were denied. The ceilings in force are saved beside the limits. `runs list` keeps printing full records, now including these fields, and lists runs from isolated sessions too: today it reads only `<data root>/runs` (`src/cli.ts`, `runsCommand`) and misses `<data root>/mcp-sessions/session-*/runs`, where the default isolated registration stores every run (`src/config/isolated-home.ts`).

**Data shapes.**

```ts
export interface ToolCallCounts { executed: number; deniedByHandler: number; deniedByPolicy: number }
export interface UsageState {
  tokensUsed?: number;
  promptTokens?: number;
  completionTokens?: number;
  cachedTokens?: number | null;
  modelCalls?: number | null;
  contextSize?: number;
  cost?: { amount: number; currency: string; authoritative: false };
  toolCalls?: ToolCallCounts;
}
export interface RunLimits {
  timeoutSeconds: number; maxTurns: number; maxEventBytes: number; maxTranscriptBytes: number; maxArtifactBytes: number;
  maxTokens?: number; maxCostUsd?: number; maxModelCalls?: number;
}
```

```json
"usage": { "tokens_used": 41200, "prompt_tokens": 39800, "completion_tokens": 1400, "cached_tokens": null, "model_calls": 9, "context_size": 128000,
           "cost": { "amount": 0.031, "currency": "USD", "authoritative": false },
           "tool_calls": { "executed": 7, "denied_by_handler": 1, "denied_by_policy": 0 } },
"limits": { "timeout_seconds": 180, "max_turns": 12, "max_event_bytes": 52428800, "max_transcript_bytes": 10485760, "max_artifact_bytes": 104857600,
            "max_tokens": 200000, "max_cost_usd": 0.5, "max_model_calls": 17 }
```

- `max_model_calls` is the backstop the supervisor enforces, `turnBackstop(maxTurns)` from `src/backends/app-server/usage.ts` (turns plus 5); `max_tokens` and `max_cost_usd` appear only when configured.
- `tool_calls` counts the supervisor's own audited outcomes, the same ones that become `tool_call` and `tool_denied` events in `emitEffect` (`src/backends/app-server.ts`), not Vibe's `toolCalls*` statistics, which are the worker's claims and are not parsed today.
- `runFromWire` ends with a check that every value of `run.limits` is a positive safe integer. `max_cost_usd` is a decimal, so that check must name the five integer limits and validate the ceilings separately (positive integers for tokens and model calls, a positive finite number up to 1,000,000 for cost); otherwise every record with a cost ceiling becomes unloadable. A 2.0 supervisor reading a 2.1 record picks only the limits it knows and is unaffected.
- `schemas/run.schema.json`: `limits` gains the three optional numbers (it is closed today, so this is required); `usage` becomes a closed object listing the eight properties. `schemas/result.schema.json` `usage` gets the same definition. Neither schema is loaded by code or tests today; they document the wire format.

**Files.**
- Wave 0: `src/contracts.ts` (types), `src/core/serialization.ts` (both directions), `src/core/run-manager.ts` (the `limits` object built in `start`, about line 284, gains the ceilings from `this.config.limits` and `turnBackstop`; the local `usageToWire` goes), `schemas/run.schema.json`, `schemas/result.schema.json`, new `src/cli/runs.ts` with a bounded run-directory enumerator (the data root's `runs/` plus at most 128 `mcp-sessions/session-*` directories, the router's limit in `src/core/isolated-run-router.ts`; symlinks and foreign owners refused as there).
- Wave 1: `src/backends/app-server/usage.ts` (`toUsageState` carries prompt, completion, cached tokens and model calls, keeping `null`), `src/backends/app-server.ts` (counters incremented in `emitEffect`, merged into the usage handed to `onState` in `conclude`).
- Wave 3: `docs/reference.md` ("Results and artifacts", "CLI"), `docs/functionality.md`.

**Boundary check.** Reads numbers the supervisor already has; cost stays an estimate marked `authoritative: false`; persistence stays bounded (eight numbers). No enforcement point changes. No ADR.

**Tests.**
- `tests/unit/app-server-usage.test.ts`: `toUsageState` keeps `modelCalls: null`; a handoff carries prompt, completion and model calls across segments.
- New `tests/integration/usage-record.test.ts` with new scenario `tests/fixtures/app-server-scenarios/usage-tool-counts.json` (three approved reads, one handler denial, one policy denial): `meta.json` and `result.json` carry `tool_calls` 3/1/1 and token totals equal to the statistics delta; with `limits.max_tokens` configured the record carries it.

## 2. `accepted` and `reason` on `vibe_close`; `runs usefulness`

**Behaviour.** After verifying a result, the coordinator closes the run with `accepted: true|false` and an optional `reason`. The decision is stored once: a repeated close with the same values is a no-op, a different value is refused with `VSUP_INVALID_STATE` ("acceptance already recorded"), and a close on an already closed run may add a decision that was never recorded. The close reply echoes it. `vibe-supervisor runs usefulness [--config <path>] [--since <YYYY-MM-DD>] [--json]` prints one row per run with a decision, in the usefulness log's columns (commit `d360f28`, `docs/history/usefulness-log.md`), then a summary line; `--json` prints one JSON object per line instead.

**Data shapes.**

```ts
export interface CloseToolInput { run_id: string; cleanup_worktree?: boolean; accepted?: boolean; reason?: string }
export interface AcceptanceRecord { accepted: boolean; reason?: string; recordedAt: string }
// RunRecord gains: acceptance?: AcceptanceRecord
```

```ts
export const closeSchema = z.object({
  run_id: runId,
  cleanup_worktree: z.boolean().default(false),
  accepted: z.boolean().optional(),
  reason: z.string().min(1).max(500).optional()
}).strict().refine((input) => input.reason === undefined || input.accepted !== undefined, "reason requires accepted");
```

```json
"acceptance": { "accepted": true, "reason": "11 parser cases checked independently", "recorded_at": "2026-11-03T10:12:44.120Z" }
```

The reason is stored after control characters are replaced and `redactSecrets` runs with the environment's secrets, never longer than 500 characters. An `acceptance_recorded` event (severity `info`, data `{ accepted, reason_chars }`) marks when it happened; the reason text stays in the record only.

Output of `runs usefulness`:

```text
| 2026-11-03 | 2.1.0 | `1284e7c0` | review, 2 context files | max_turns 12, end_turn, 64 s, 41,200 tokens, 9 model calls, about 0.03 USD | Yes | 11 parser cases checked independently |
Accepted 3 of 5 runs with a decision since 2026-11-01; 2 closed runs have no decision.
```

The "operation and task shape" column carries only what the record knows (mode, context-file count); the owner adds the task shape when copying the row, since the task text is never stored.

**Files.**
- Wave 0: `src/mcp/schemas.ts` (`closeSchema`), `src/contracts.ts`, `src/core/run-manager.ts` (`close`, `closeRun`, `closeOutcome`), `src/core/serialization.ts`, `schemas/run.schema.json`, `src/mcp/tools.ts` (the `vibe_close` description: "after verifying, pass accepted and a short reason").
- Wave 1: new `src/cli/runs/usefulness.ts` (uses wave 0's enumerator); `skills/vibe-supervisor/SKILL.md` ("Record whether the answer was accepted" becomes "close with `accepted` and `reason`").
- Wave 3: `docs/reference.md` (the close row in the field table, the CLI list), `docs/functionality.md`.

**Boundary check.** An optional field on an existing tool; the catalogue stays exactly five tools; strict schemas still reject unknown fields. Nothing changes for a client that never sends it. No ADR.

**Tests.**
- `tests/unit/tool-schemas.test.ts`: `accepted` boolean; `reason` 1–500 characters; `reason` without `accepted` rejected.
- New `tests/integration/close-acceptance.test.ts`: decision persisted in `meta.json`; same values twice is idempotent; a different value is `VSUP_INVALID_STATE` and leaves the record unchanged; a close on a closed run without a decision records it; a reason containing an environment secret is stored redacted.
- New `tests/unit/runs-usefulness.test.ts`: golden Markdown row and summary; `--since` filter; runs under isolated sessions; runs without a decision counted but not listed; `--json` lines parse.

**Gate entries.**

```json
{ "name": "close-acceptance-recorded-and-usefulness-row", "status": "RUN_BY_focused-tests" }
{ "name": "hosted-close-acceptance-recorded", "status": "UNVERIFIED",
  "evidence_required": "The 2.1 hosted review is closed from the client with accepted and a reason; meta.json carries them and runs usefulness prints the row with the run's usage." }
```

**Size and dependencies.** S. Mostly wave 0; the CLI in wave 1. Its row is better with item 1's numbers. Unlocks the monthly usefulness rate in the marketing strategy.

## 3. `excluded_globs` per allowed root

**Behaviour.** The owner adds paths that no run may read or write beyond the fixed reserved and secret patterns: fixtures with real data, dumps, `*.tfvars`. Exclusions apply to every run admitted under that root, relative to the run's workspace (a review's `cwd`, an edit's repository root and therefore its worktree). They are merged into the profile denylist that Vibe enforces, judged again by the approval handler, dropped from the review's file listing, and read back before the first turn. Like the allowlist, they are live: a change applies at the next readiness check or start without a restart, and changes the policy revision.

**Configuration.**

```toml
allowed_workspace_roots = ["~/src/project"]

[excluded_globs]
"~/src/project" = ["*.tfvars", "fixtures/private/**", "dumps/*.sql"]
```

```ts
// SupervisorConfig gains (optional, so nothing else has to change to compile; absent means none):
excludedGlobs?: Record<string, string[]>;
```

Validation (`src/config/validation.ts`, `VSUP_CONFIG_INVALID` with the field path on failure):
- Each key equals an entry of `allowed_workspace_roots`, as written; any other key is an error.
- At most 100 globs per root; each 1–256 characters, at most 16 segments separated by `/`.
- Allowed in a segment: letters, digits, `.`, `_`, `-`, `@`, `+`, `=`, `,` and `*`; `**` only as a whole segment. No leading `/`, no `~`, no empty, `.` or `..` segment, no `?`, `[`, `]` or braces: the handler's matcher and Vibe's must agree, and the fixed patterns already use only `*`.
- Duplicates are dropped; order is kept.

**Merging.** `workspaceDenylist(workspace, excluded)` in `src/backends/app-server/session-config.ts` returns the fixed list unchanged, then for each glob `g` the entry `${workspace}/${g}` and, when `g` has no `/`, also `${workspace}/**/${g}`, the rule the secret patterns follow. The fixed list is never shortened. `buildExpectation` receives the merged list, so the read-back compares it per tool.

**Handler and listing.** `judgeWorkspacePath(workspace, rawPath, excluded)` in `src/backends/app-server/approvals.ts` gains the deny reason `path_excluded` (added to `DenyReason` and `PathJudgement`), matched on the workspace-relative path: a one-segment glob against every segment, as `restrictedSegment` does for secrets; a multi-segment glob segment by segment, `*` within a segment, `**` across any number. `eligibleListingPaths` in `src/backends/app-server/workspace-listing.ts` drops the same paths.

**Record.** `RunRecord.excludedGlobs?: string[]` (wire `excluded_globs`), the list applied to that run.

**Files.**
- Wave 0: the optional `SupervisorConfig.excludedGlobs`, `excludedGlobs: string[]` on `StartRunInput` and `RunRecord` in `src/contracts.ts`, set in `run-manager.ts` from the admitted root's entry (empty when none).
- Wave 1: `src/config/validation.ts`, `src/config/config.ts` (`configFingerprint` includes the exclusions, so receipts and records bind to them), `src/config/policy.ts` (not boot-bound; nothing to add to `BOOT_BOUND_SETTINGS`, and a test says so), `src/backends/app-server/session-config.ts`, `src/backends/app-server/approvals.ts`, `src/backends/app-server/workspace-listing.ts`, `schemas/config.schema.json`, `examples/config.toml`, `scripts/v2-conformance-check.mjs` (a repeatable `--excluded-glob <glob>` so the target can observe the merged read-back).
- Wave 2: `src/backends/app-server.ts` passes the list to `buildSessionConfig`, the approval handler and `buildWorkspaceListing`.
- Wave 3: `docs/reference.md` (configuration table, policy authority), `docs/security.md` (enforcement points), `docs/functionality.md`.

**Boundary check.** Narrows access only: the fixed denylist cannot be reduced, the handler denies by default as before, and the read-back point now covers the merged list. AGENTS.md's "reject invalid, unsafe, or out-of-root paths rather than broadening access" holds. A key that is not an allowed root is an error, so an exclusion can never imply access. No ADR.

**Tests.**
- `tests/unit/config.test.ts`: each validation rule; the fingerprint changes with an exclusion; an unknown root key fails.
- `tests/unit/app-server-session-config.test.ts`: merged denylist order and the two forms; the fixed entries always present.
- `tests/unit/app-server-approvals.test.ts`: `path_excluded` for a basename glob at depth, an anchored glob, `**`; a path that only looks similar is approved.
- `tests/unit/app-server-workspace-listing.test.ts`: excluded files are not listed and not counted as eligible.
- `tests/unit/app-server-readback.test.ts`: an effective configuration missing one merged entry is `readback_mismatch`.
- `tests/unit/policy-readiness.test.ts`: changing an exclusion changes `policy_revision` without `restart_required`.
- Wave 2, `tests/integration/app-server-backend.test.ts` with a new scenario: a read of an excluded file is recorded as `tool_denied` and the run completes.

**Gate entries.**

```json
{ "name": "excluded-globs-merged-denied-and-read-back", "status": "RUN_BY_focused-tests" }
{ "name": "hosted-excluded-glob-readback-and-denial", "status": "UNVERIFIED",
  "evidence_required": "With one exclusion for the fixture: the conformance check run with --excluded-glob shows denylist_matches_expected true for every profile tool, and the 2.1 hosted review, asked to read the excluded file, records tool_denied (outcome permission_denied_by_policy, or reason path_excluded) and completes." }
```

**Size and dependencies.** S. Wave 1 (modules) and wave 2 (wiring). The sidecar (item 5) applies the same judgement to search results.

## 4. Findings for reviews: `findings.json` and SARIF

**Behaviour.** `vibe_review_start` accepts `output: "findings"`. The supervisor then appends a fixed output contract to the prompt; when the run completes it takes the last fenced `json` block of the final message, validates it, checks every location against the launch snapshot, and writes `artifacts/findings.json`. Malformed or missing output is a warning, never a failed run: the summary is still the answer. `vibe-supervisor runs sarif <run-id> [--config <path>] [--output <absolute file>]` converts the file to SARIF 2.1.0 for reviewdog or code scanning.

**The contract appended to the prompt** (a constant in `src/core/findings.ts`, recorded as `output: "findings"` in the run record):

```text
End your final answer with one fenced block tagged json and nothing after it:
{"conclusion": "<one paragraph>", "findings": [{"severity": "error" | "warning" | "note", "path": "<path relative to the workspace root>", "line": <integer or null>, "end_line": <integer or null>, "trigger": "<the input or condition>", "requirement": "<what the contract requires>", "observed": "<the wrong behaviour>"}]}
Use an empty findings array when nothing is wrong. Do not invent a finding.
```

**`findings.json`** (`schemas/findings.schema.json`):

```json
{
  "schema_version": 1,
  "run_id": "<uuid>",
  "supervisor_version": "2.1.0",
  "workspace_snapshot_sha256": "<64 hex>",
  "format_valid": true,
  "conclusion": "<≤ 2000 characters>",
  "findings": [
    { "id": "F1", "severity": "error", "path": "src/limit.mjs", "line": 7, "end_line": 9,
      "trigger": "<≤ 500>", "requirement": "<≤ 500>", "observed": "<≤ 1000>",
      "location_check": "verified" }
  ],
  "rejected": [ { "index": 4, "reason": "path_outside_workspace" } ],
  "claims_note": "Findings are the worker's claims; locations are checked against the launch snapshot, behaviour is not."
}
```

- At most 200 findings; the block itself at most 256 KiB; the file at most `limits.max_artifact_bytes`.
- `location_check`: `verified` (a regular file in the launch snapshot, unchanged since launch, line within its line count), `file_changed`, `line_out_of_range`, `path_unknown` (not in the snapshot), or `not_checked` (the snapshot was `unverified`). A path that is outside the workspace, reserved, secret or excluded is moved to `rejected` with the judgement's reason; its file is never opened.
- `ResultSummary` gains `findings?: { formatValid: boolean; count: number; verifiedLocations: number }`, shown in the compact result; the artifact is listed with its digest like the patch.

**SARIF mapping** (`runs sarif`): `version` `2.1.0` with the official `$schema`; one run with `tool.driver` `{ name: "vibe-supervisor", version, informationUri }` and one rule `vibe-supervisor/review-finding`; `automationDetails.id` `vibe-supervisor/<run-id>`; each `verified` finding becomes a result with `level` from severity, `message.text` "observed (trigger: …; requirement: …)", `locations[0].physicalLocation.artifactLocation` `{ uri: <relative path>, uriBaseId: "%SRCROOT%" }` and `region` `{ startLine, endLine }`, and `partialFingerprints["vibeSupervisorFinding/v1"]` = SHA-256 of path, trigger and requirement joined by newlines. Findings without a verified location are counted in `runs[0].properties.unlocated`, not emitted, because code scanning needs a location. No absolute path is written.

**Files.**
- Wave 0: `src/mcp/schemas.ts` (`output: z.enum(["text", "findings"]).default("text")` on the review schema only), `src/contracts.ts` (`ReviewStartToolInput.output`, `StartRunInput.output`, `RunRecord.output`, `ResultSummary.findings`), `src/core/run-manager.ts` (passes `output`; in `writeArtifacts`, for a completed review with `output: "findings"`, calls `buildFindingsArtifact` from `src/core/findings.ts` and records the artifact), stub `src/core/findings.ts`, `schemas/findings.schema.json`, `schemas/result.schema.json`.
- Wave 1: `src/core/findings.ts` (parse, validate, locate, SARIF conversion), new `src/cli/runs/sarif.ts`.
- Wave 2: `src/backends/app-server.ts` (`promptFor` appends the contract when `input.output` is `findings`).
- Wave 1 templates agent: the review template in `skills/vibe-supervisor/SKILL.md` mentions `output: "findings"` and keeps its "No defect found" line.
- Wave 3: `docs/reference.md`, `docs/functionality.md`.

**Boundary check.** No new tool and no new worker capability: the review stays `read_file` only and read-only; parsing is supervisor-side after the worker has exited; result content stays untrusted data and the file says so; the prompt addition is fixed text recorded in the record. No ADR.

**Tests.**
- New `tests/unit/findings.test.ts`: a valid block; invalid JSON, no block, a second block earlier in the text, over 200 findings, an over-long field (each `format_valid: false` with one warning); every `location_check` value; `../`, absolute, `.git`, `.env` and excluded paths rejected without being opened.
- New `tests/unit/sarif.test.ts`: golden SARIF for a fixed `findings.json`; fingerprints stable across runs; unlocated findings counted, not emitted; no absolute path in the output.
- `tests/unit/tool-schemas.test.ts`: `output` on review only; edit rejects it.
- Wave 2, a scenario whose final message carries a block: artifact written, compact result shows the counts; a scenario with a broken block: run `completed` with the warning.

**Gate entries.**

```json
{ "name": "findings-parse-locate-and-sarif", "status": "RUN_BY_focused-tests" }
{ "name": "hosted-review-findings-file", "status": "UNVERIFIED",
  "evidence_required": "The 2.1 hosted review started with output findings writes findings.json with format_valid true (or records the model's non-compliance as the finding), every location checked against the launch snapshot, and runs sarif produces a SARIF 2.1.0 document whose results match the verified findings." }
```

**Size and dependencies.** M. Wave 0, 1, 2. Uses item 3's judgement for rejected paths. The reviewdog outreach row waits for it.

## 5. Search tool for reviews

**Status.** Proposed on 2026-10-28 from a source reading of Vibe 3.0.2, for the owner's decision; no product code yet. It replaces this section's earlier 2.26.1-era sketch.

Reviews read one file at a time and cannot search, which is the main reason review answers miss code that a search would have found. This design adds two read-only tools, `list_files` and `grep`, to reviews. A supervisor-owned stdio MCP server, `supervisor_search`, serves them, and the model reaches them through `run_typescript`. Edits are unchanged.

Every Vibe fact below was read from the v3.0.2 tag source. The paths and SHA-256 values are in [Search tool facts](../docs/compatibility-v3.md#search-tool-facts). None of these facts has been observed on a hosted run.

#### Decision

1. **Server.** A review session declares exactly one MCP source on the session wire. Vibe 3.0.2 accepts the session option `agentConfig.mcpServers`, a list of `SessionMCPStdioServer` (`transport`, `name`, `command`, `args`, `env`, `cwd`):

   ```json
   { "transport": "stdio", "name": "supervisor_search", "command": "<node executable>",
     "args": ["<dist>/backends/app-server/search-server.js", "--workspace", "<workspace>", "--excluded", "<json list>", "--lifetime", "<run lifetime directory>"],
     "env": {} }
   ```

   `env` stays empty. Vibe's stdio client then gives the server only `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM` and `USER`, taken from the worker's already-filtered environment. `MISTRAL_API_KEY` never reaches the server. `cwd` is omitted.

2. **Tools.** `list_files { path = ".", cursor?, limit 1–1000 = 200 }` and `grep { pattern 1–1024 chars, path = ".", case_sensitive = true, max_matches 1–500 = 100 }`. Vibe registers every MCP tool for use inside `run_typescript` only and never as a direct tool. The model therefore calls `tools.mcp_supervisor_search.grep(...)` and `tools.mcp_supervisor_search.list_files(...)`. The namespace is `mcp_` plus the server name, and the member is the remote tool name.

3. **Review profile.** `enabledTools` becomes `["read_file", "run_typescript", "supervisor_search_grep", "supervisor_search_list_files"]`. Vibe filters MCP tools by their `{server}_{tool}` display names against the same `enabled_tools` globs, so a profile without those two names publishes neither tool. The edit profile does not change.

4. **Approval.** Each sidecar call reaches the supervisor as a `callback/call` approval. Vibe's resolver treats any name that is not a builtin as a provided-tool route, and with no configured permission it answers `ask`. The handler approves only when all of the following hold:
   - the effect is `kind: "tool"`;
   - `toolName` is `mcp_supervisor_search.grep` or `mcp_supervisor_search.list_files`;
   - the input parses against that tool's schema;
   - the `path` argument passes the judgement below.

   `inputFingerprint` covers `{ tool, input }` as it already does for unknown tools. A session or permanent approval is still never offered, and the 5-second deny is unchanged.

5. **Per-file judgement.** Each judgement goes through `judgeWorkspacePath` in `src/backends/app-server/approvals.ts` with the run's `excluded_globs`. There is no second policy: the parallel branch's `path-policy.ts` merges into it. There are two layers:
   - The handler judges the call's directory argument. The workspace root itself (`.`) is allowed as a search scope. `judgeWorkspacePath` rejects the root (`relative === ''`), so the root needs an explicit scope case. Every other directory goes through `judgeWorkspacePath` unchanged.
   - The sidecar runs `judgeWorkspacePath` on every file it lists or opens, with the same workspace and `excluded_globs` passed in `args`. Reserved, secret, excluded, symlinked and out-of-root files are skipped silently. They are left out of `list_files` results and never read by `grep`. A skipped directory is not descended into.

   This per-file layer is what built-in `grep` lacks.

6. **Bounds.** Each call returns at most 64 KiB of result and at most 500 matches. `grep` reads at most 64 MiB of file content per call and has a 10-second call deadline, below Vibe's default 60-second MCP tool timeout. Each file's regular expression runs in a worker thread that is terminated after 2 seconds; that call then returns an error instead of hanging. The server serves one request at a time and refuses a concurrent one. `list_files` cursors are HMAC-signed with a per-process key, and `list_files` stops at 1000 entries per page. The bounds are the parallel branch's `search.ts` values (`c3678cc`).

7. **Lifetime.** The sidecar does not share the worker's process group. Vibe starts it through the `mcp` Python SDK's `stdio_client`, which spawns with `start_new_session=True` on Unix. The supervisor's process-group kill therefore does not reach it, and AGENTS.md forbids signalling a PID read from saved data. The sidecar ends itself in three ways:
   - when stdin closes;
   - when its parent PID changes;
   - when the run's deadline passes (passed in `args`).

   At start it writes a private lifetime record of its pid and start time. Close waits up to 5 seconds and checks, with a read-only `ps` start-time comparison, that every recorded sidecar is gone. If one is still alive, close fails as termination unverified. Restart recovery treats a leftover record as evidence only and never signals it. This is the parallel branch's `search-lifetime.ts`.

8. **Fallback.** If the sidecar fails to start, the read-back fails closed and the run fails. There is no silent fallback to a review without search. The file listing in the prompt stays as it is.

#### Rejected alternatives

- **Client-provided tools.** `vibe/app_server/_client_provided_tools.py` declares them internal: nothing on the app-server wire declares them. The supervisor cannot register a tool that way.
- **Vibe's built-in `grep`.** `GrepTool.resolve_permission` (`vibe/core/tools/builtins/grep.py`) judges only `args.path`, the directory searched. It has no per-file check against the supervisor's reserved, secret or `excluded_globs` patterns. Its ignore handling is `.gitignore`/`.vibeignore` plus a model-settable `use_default_ignore`. Its matches would expose `.env` lines or excluded files to the model.
- **Shell search (`rg`/`grep` through `bash`).** Shell tools stay disabled, and `allow_shell: true` stays rejected. A command line cannot be judged per file either.
- **Prompt-only listing (status quo).** It does not scale past the listing budget and gives no content search.

#### Boundary changes in AGENTS.md

Three lines change, all under "Boundaries that must remain intact":

- "Review profiles enable `read_file` only (there is no `grep`); edits add `write_file` and `edit`." becomes: "Review profiles enable `read_file`, `run_typescript` and the two `supervisor_search` tools (this design); edits add `write_file` and `edit` and do not get search."
- "Do not inherit user/project tools, hooks, agents, skills, MCP servers, or trust records." stays. A new sentence follows it: "The one MCP exception is this design's supervisor-owned `supervisor_search` stdio server on reviews; the read-back expects exactly that source and no other."
- The app-server enforcement list gains "the supervisor-owned search sidecar with per-file `judgeWorkspacePath` and its bounds". #### Read-back

The read-back expects exactly this one source, in each of these places:

- **`runtime/read`**: `runtime.mcp.sources` is a single entry: `name: "supervisor_search"`, `kind: "server"`, `transport: "stdio"`, `status: "connected"`, `error: null`, `pluginName: null`, with `tools` named `grep` and `list_files`, both `enabled: true`. Tool descriptions are not compared. `runtime.mcp.discoveryErrors` stays `{}`, and `runtime.connectors` stays zero.
- **`config/effective/read`**: `config.mcp_servers` is a single entry with `name: "supervisor_search"`, `transport: "stdio"`, `command: ["<node executable>"]`, `args` as the expected count of `"<redacted>"` strings (Vibe redacts every argument), `env: {}`, `disabled: false` and `disabled_tools: []`. `sampling_enabled` reads `true`, Vibe's default, which the session wire cannot change. The sidecar sends no server-to-client request, and a fixture test asserts this. `config.enabled_tools` equals the review profile above. `config.tools` has no `supervisor_search_*` entry, so its permission stays Vibe's default `ask`.
- **`config/read`**: `mcpServersTotal` and `mcpServersEnabled` are both `1`. `skillsCount` stays `0`.

A second source, a missing source, a source that is not connected, or any discovery error fails the run before the first turn. The edit read-back is unchanged and still expects no sources.

#### Prerequisites

- Gate `nested-run-typescript-shape-and-gating` in [docs/acceptance.json](../docs/acceptance.json) must be VERIFIED first. Vibe's Rust acceptance tests show that a call made inside `run_typescript` goes through the same approval as a direct call: they expect `tool_id` `file_system.read_file` or the provided route `github.create_issue`, and a rejection reaches the program. The source does not show which of `tool_id` or `display_name` (`tools.file_system.write_file`) the app-server effect's `toolName` carries for a nested call. If a nested `write_file` does not arrive as a `file_system.*` effect that is denied, enabling `run_typescript` is unsafe and this design stops.
- Enabling `run_typescript` makes the program's other members reachable, for example `tools.self.sleep` and nested `tools.file_system.*`. Each one still has to pass the handler. One that runs without an approval is an unapproved allowed effect, which the event validator already fails closed on. The hosted gate must show this.
- Item 3 (`excluded_globs` per root) is merged before this, so the sidecar receives the same exclusions as `read_file`.

#### Gates

Fixture gate `search-sidecar-routes-approved-and-bounded` (focused tests):

- Session start carries exactly one `supervisor_search` source and the four-tool review profile. Edit sessions carry none.
- Read-back: one connected source passes. Zero sources, two sources, a disconnected source or a discovery error fails.
- Approval: the two `mcp_supervisor_search.*` routes with in-workspace paths are approved. Out-of-workspace, reserved, secret, excluded or symlinked paths are denied, as are an unknown `mcp_*` route and a `kind` other than `tool`.
- Sidecar: `grep` never returns a line from `.env`, a reserved directory or an `excluded_globs` match, even under an allowed directory. `list_files` never lists them.
- Bounds: results stop at 64 KiB and 500 matches. A catastrophic regular expression returns an error within its limit. A concurrent call is refused.
- Lifetime: the sidecar exits on stdin EOF and when its parent dies. Close fails while a recorded sidecar is still alive.
- A nested `write_file` from `run_typescript` in a review is denied. This is the fixture half of the prerequisite gate.

Hosted gate `hosted-review-search-sidecar`, one hosted review on the candidate archive:

- the read-back shows exactly the `supervisor_search` source;
- the history shows a sidecar call that the handler approved, with its actual `toolName` and `kind` recorded;
- the probe's nested write is denied;
- results stay within their bounds;
- no sidecar process remains after close.

#### Open items

- The exact `toolName` string on the live approval effect for an MCP call. Source reading gives the route `mcp_supervisor_search.grep`; the handler should accept only what the hosted gate records.
- Whether `runtime.tools` lists the MCP tools, `run_typescript` or neither. The fixture's read-back expectation is set from the hosted gate's recorded `runtime/read`.
- Whether the source has reached `status: "connected"` when the startup read-back runs, or whether the read-back must wait for discovery.

## 6. `runs export` audit bundles

**Behaviour.** `vibe-supervisor runs export <run-id> [--config <path>] [--output <absolute file>] [--redact-paths]` writes one self-contained JSON file for a settled run: the record, the result, the pin identity, the policy it was admitted under, the approval ledger, every event and the artifact digests, each digest re-checked.
