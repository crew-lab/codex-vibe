# Development strategy

How vibe-supervisor is developed, verified and released: the picture, the direction, the release line and the rules. [Handoff.md](../Handoff.md) holds the current status (what is done, what remains, who acts); the live sequence is the Direction below, and the sequenced plan that led to 2.2.0 is in Git history ([development-plan.md](development-plan.md) says where). Operators follow [the local operating procedure](../docs/local-operation.md).

## Direction — 2026-10-28

**Where the product is.** The stabilization goal set on 2026-10-17 ("working ASAP") is met: v2.2.0 was qualified on the target with one accepted native edit and one accepted native review and is published as a pre-release, the supported line. The default engine is exactly Vibe 3.0.2 over its app-server protocol; every start needs a single-use grant from `task authorize`. A source review on 2026-10-27 found no more stable integration surface (ACP runs the same app-server with fewer controls, `vibe -p` denies every approval itself, the agent socket and `run-server` are hidden), and Codex can reach another agent only through an MCP server. The enforcement points have held on every target sitting since 2.0.1.

**What limits the product today.** Not the boundary; the use. Four things, in order of weight:

1. It has not been used on real work. Two bounded fixture trials prove the supervisor, not that Codex gets better answers by delegating. Every priority below is a guess until the owner has run it ten times on real tasks and the usefulness log says what came back.
2. Starting is hard. A grant is a hand-assembled command that must name the server's install, Node and configuration; one wrong field is `VSUP_AUTHORIZATION_INVALID`. The per-field diagnostics in 2.2.0 explain the refusal; nothing yet prevents it.
3. Reviews cannot search, and the worker's answers are mixed. This is the quality lever, and the search sidecar is one route to it, not the only one.
4. Every change costs a two-machine sitting, and the gate ledger has fallen behind: `docs/acceptance.json` names 2.1.0 as the candidate, holds no 2.2.0 build and lists the hosted gates as unverified while the 2.2.0 trials were accepted. A ledger that lags two releases protects nobody. Protection comes from the fail-closed code, which CI and the preparation PASS exercise on every build; the ledger records observations, so it must be cheap enough to keep true.

The experimental Antigravity backend is a second vendor with weekly releases whose only tool gate is a hook that needs `--dangerously-skip-permissions` to pass its probes, for a product whose one user delegates to Vibe. It is a cost, not a limit, and it stops growing (step 8).

**Next steps, in order.** Steps marked **D** need an owner decision; the recommendation stands beside each. Size: S is under a day of agent work, M a few days, L a week or more plus a hosted sitting.

**Owner decisions.** The owner accepted D1–D6 as recommended on 2026-10-28; standing authorization stays declined until after the ten starts.

- **D1, simplify the ledger: yes.** It is two releases behind, so today it informs nobody; a per-build observed list that stays true is worth more than eighteen gates that do not. It changes the "Verification and reporting" text in AGENTS.md, not a boundary.
- **D2, mark 2.2.0 latest without the clean account: yes.** The gate cannot be met with the accounts available, and the only user has already installed the archive into a fresh prefix.
- **D3, a hosted allowance of about ten real starts: yes.** The trials proved the boundary, not the usefulness; nothing else on this list can be ordered without real use.
- **D4, the search sidecar: not yet.** It widens the model's reach through `run_typescript` on a gate that is still unverified; decide after steps 5 and 6.
- **D5, freeze Antigravity: freeze, not drop.** The code is opt-in and tested, so keeping it costs nothing until the next agy release; following those releases is what costs. Drop it at the next minor if unused.
- **D6, re-pin on trigger with a lighter qualification: yes.** A candidate per Vibe release is unaffordable at a four-day cadence, and 3.0.3 fixes nothing seen on 3.0.2.
- **A standing authorization: no, for now.** The per-start approval the owner gives through Codex's command permission is the one human check per start; the friction is the hand-assembled command, which step 4 removes. Revisit after the ten starts if the click itself turns out to be the cost.

Feature expansion beyond these needs the owner's decision. Decisions and new ideas are recorded in this document and the Handoff; no new ADRs are written, and the existing ones stay as the record of past decisions (owner, 2026-10-28). Dated checkpoints and superseded runbooks live in the Handoff's history and in Git, not here.

## Ideas under consideration — 2026-10-28

Each is a candidate for the owner's decision, with what is known so far. None is authorized.

- **A generated `task authorize` command (step 4).** The server already knows the runtime executable, configuration path and candidate it will bind; returning the command from `vibe_status`, or a `task authorize --from-status <json>` that reads them, makes the hand-assembled fields disappear. Replay prevention, expiry and private storage are untouched.
- **Search context through `context_files` (step 6).** Codex has `grep`; the review request already takes `context_files`. Before a sidecar is built, measure whether a searched-and-handed context closes the quality gap.
- **Search sidecar (step 7).** Two read-only tools, `list_files` and `grep`, from a supervisor-owned stdio MCP server declared in `agentConfig.mcpServers` with an empty environment; the model reaches them only inside `run_typescript`, so reviews would enable it. Every call is an approval judged by route, schema and path, and the server judges every file it lists or reads with `judgeWorkspacePath` and `excluded_globs`, which Vibe's own `grep` lacks. Bounds: 64 KiB and 500 matches per call, a 2-second regex limit per file, a 10-second deadline; the server is outside the worker's process group and carries its own lifetime check ([design](2.1-designs.md#5-search-tool-for-reviews), [source facts](../docs/compatibility-v3.md#search-tool-facts)). Open: the live `toolName` of an MCP approval, whether `runtime/read` lists MCP tools, and the nested-write gate. Downgraded from "next feature" to "on evidence" because it loosens the model's reach for a gain step 6 may deliver without it.
- **A per-build observed list instead of per-gate entries (step 1).** One entry per archive: identity, runtime, what was run, what was seen, what was not. Gates that only a hosted run can settle are listed as observations with a date or "not observed".
- **A per-version wire table (step 9).** Today the edit tool's wire name, the written settings and the version constant are spread over six source files; a re-pin to 3.0.3 would touch them all. One table keyed by the pinned version keeps the pin exact and makes the next move a row.
- **A standing authorization.** An owner-configured budget per root (N starts a day within fixed limits) would let Codex start Vibe without a per-start command, at the cost of the one-registration-per-task rule and the owner's per-start click. It would change the dispatch contract and ADR 0010's line in AGENTS.md. Recommendation above: not now.
- **Dropping Antigravity (step 8).** If the owner has not opted in by the next minor, the backend, its probes, its gates and ADR 0008's boundary lines are removed in one change, with the ADR kept as history.

**Rejected on 2026-10-28, with the reason.** Vibe 3.0.3 as the next pin: it renames the edit tool on the approval wire and fixes nothing seen on 3.0.2 ([assessment](../research/vibe-3.0.3-assessment-2026-10-28.md)); step 9 replaces a per-release re-pin with a trigger. ACP, `vibe -p`, the agent socket and `run-server` as integration surfaces: fewer controls or no supported contract; revisit only if Mistral publishes a versioned one. Linux, MCPB and Codex plugin packaging, the `runs` watch view and reviewed dependency-preparation profiles: off the list until a second user asks.

## Vision and scope

vibe-supervisor is a local MCP server that lets a coding agent delegate one bounded review or one isolated edit to a supervised worker—by default Mistral Vibe through its `vibe-app-server` protocol ([ADR 0004](../docs/adr/0004-app-server-client.md)), or, experimentally and only on explicit opt-in, Google Antigravity CLI (`agy`). The five MCP tools and the isolation boundaries in [AGENTS.md](../AGENTS.md) are fixed across both backends.

- **Two supervised execution backends, one MCP contract.** `backend = "app-server"` (default) drives Mistral Vibe 3.0.2 over JSON-RPC. `backend = "antigravity"` drives `agy` 1.4.0, 1.4.3, 1.4.4, 1.4.7 or 1.4.8 headless (`-p`, `--output-format stream-json`, `--mode accept-edits` for edits, `--sandbox`, `--disable-slash-commands`, `--print-timeout`) with a supervisor-written `settings.json` and `PreToolUse` hook in a private per-run `antigravity-home` ([ADR 0008](../docs/adr/0008-antigravity-execution-backend.md)). By the owner's 2026-10-19 decision it is experimental and off by default: it needs `experimental.antigravity = true`, and it is not for production until its [target probes](../docs/target-acceptance.md#antigravity-backend-probes) pass. Changing `backend` or `paths.antigravity` updates the policy fingerprint and is boot-bound (`restart_required: true`).
- **One Vibe version.** Each release pins exactly one Vibe release: the server's reported version plus the installed files hashed against a per-candidate manifest. A new Vibe release is a new supervisor candidate with its own manifest and conformance check.
- **One supported line.** Only the latest release is supported, and there is no maintenance line for an earlier one. The tree describes and accepts no other supervisor or Vibe version.
- **Enforcement the supervisor owns.** For `app-server`, the client decides every approval, reads the effective configuration back before the first turn, audits every effect, and fails closed on anything it cannot account for. For `antigravity` there is no such protocol: the supervisor blocks untrusted workspace `.gemini` and `.agents` extensions, writes a strict per-run `settings.json` and a `PreToolUse` hook that decides each tool call, matches agy's `stream-json` events against the hook ledger after the run, and cleans up `antigravity-home` and `antigravity-tmp`. That gate holds only if agy loads the hook, runs it before every call, honours its deny and denies when it fails, and none of that has been observed through agy yet ([security](../docs/security.md#antigravity-backend-experimental)). This is application policy (plus `agy --sandbox` for Antigravity terminal restrictions), not an OS kernel sandbox over the supervisor itself, and is never described as one.
- **One authorized attempt per start.** Every review or edit start carries a single-use grant from `vibe-supervisor task authorize`, bound to the exact request, the supervisor install, the Node runtime and the policy; a refused start names the fields that differ ([ADR 0010](../docs/adr/0010-dispatch-attempt-authorization.md)). Nothing is retried or replayed.
- **The coordinator decides from bytes, not summaries.** The main chat coordinates and verifies; the worker implements one bounded task; acceptance is decided on the exact exported patch against a contract frozen before dispatch, with execution, automated verification and the coordinator's assessment kept apart. A fallback implementer is used only after a verified rejection; it does not authorize another hosted start.
- **Antigravity, frozen.** Antigravity is an experimental, opt-in execution backend (`backend = "antigravity"`) and was a candidate verified MCP client ([research](../research/antigravity-2026-10-14.md)). Both roles are frozen at agy 1.4.9 pending the owner's decision D5 (Direction, step 8). As a client, nothing on the MCP side is written for Codex; any other client earns a support claim only through its own gates on the target machine.
- **Evidence or "unverified".** A claim about hosted behaviour, a native client or a platform is made only when `docs/acceptance.json` records it for the exact build. Until then the gate stays open and the documentation says so.

## Where things stand

**Delivered.** A JSON-RPC client of `vibe-app-server` with a typed protocol subset, session configuration and read-back, an approval handler, an event validator, usage and outcome mapping, the pin check, a reaper, and a bounded workspace listing in review prompts; the coordinator workflow (frozen acceptance contracts on exported patches, append-only assessments, sanitized `runs verify` and `runs export`, a version-matched preparation kit whose pass gates dispatch, owned validation copies); the 2.1 waves (tool-call counts and ceilings, cross-session `runs list/show/tail`, per-root `excluded_globs`, `runs usefulness`, the approval ledger and pin in exports, review findings with SARIF, the daily cost ledger with per-root budgets); single-use dispatch grants; and in 2.2.0 `allowed_write_paths` on edits and per-field authorization diagnostics. The experimental Antigravity backend sits beside it with its own hook, private home and probes.

**Proven on the target.** 2.0.1 and 2.0.2: conformance, native readiness and the MCP-client disconnect; their hosted review and edit were rejected on worker answer quality, a limit the owner documented on 2026-10-16. 2.1.0: preparation, native readiness and one accepted fixture edit. 2.2.0: one accepted native edit and one accepted native review on archive `6b0a120d…`, runtime Node 24.21.0 with an isolated Vibe 3.0.2 ([evidence](../research/evidence/v2.2.0-local-workflow-20261027/README.md)). Supervisor isolation, permissions, events, cleanup and no-replay held every time.

**Found along the way.** The target's first checks found beliefs the fake had encoded wrongly (a null harness provenance, a remote managed-configuration refresh, Vibe's packaged skills), repaired by [ADR 0005](../docs/adr/0005-target-conformance-repairs.md) and [ADR 0006](../docs/adr/0006-bundled-vibe-skills.md). Cold reviews found lifecycle and audit defects in the engine, sixteen Antigravity issues, and in 2.1.0 a finalization race and timestamp-bound grants; each is fixed with regression tests or recorded as a gate. Packaging was made to hash the exact archive it ships after a kit once named other bytes.

**Documented limits.** The eleventh cold-review finding is accepted and written down: the pin covers only the installed `mistral_vibe` distribution's `RECORD`, not dependencies, `.pth` files, the interpreter or `__pycache__`, and it runs before the process starts, so it detects drift, not a malicious original ([security](../docs/security.md#process-configuration-and-persistence)). Other limits stated rather than closed: the model-visible catalogue cannot be narrowed, so `write_file`, `edit`, the shell tool and `run_typescript` are listed and refused, never hidden; reviews have no search tool; the event validator is detective, so it can stop a run and record a breach but not undo it; token and cost ceilings can overshoot by one model call; cost is an estimate; a host-only proxy observation cannot attribute a request to experiments; and the validation helper blocks project manager configuration, local dependencies and required build scripts. The supervisor makes no claim about the worker's answer quality: it can report what the worker did, not whether the answer is right.

## Architecture and enforcement points

One run is one worker process (`vibe-app-server` driven over newline-delimited JSON-RPC on stdio when `backend = "app-server"`, or `agy` driven in headless `--output-format stream-json` mode when `backend = "antigravity"`). The run manager (admission, slot, snapshot or worktree, settlement, retention) is the frame both backends plug into; the engine adds the points below, and the coordinator layers sit around both. Preventive points stop a call before it runs; detective points notice it afterwards and interrupt. [Security](../docs/security.md#enforcement-points) is the normative text.

| Point | What happens | Fails closed on |
|---|---|---|
| Preparation | `prepare check` verifies the version-matched kit against the installed candidate, runs the no-inference conformance check once with a fixed fake key and the refusing network observer, and saves a private receipt bound to the candidate bytes, pin manifest, Node, platform and policy (allowed roots excepted). Starting a check invalidates the earlier pass. Readiness reports workspace eligibility, candidate, preparation and an optional expected candidate separately ([preparation](../docs/preparation.md)). | Missing, failed, stale or changed evidence blocks ordinary dispatch; a wrong `expected_candidate` blocks readiness |
| Launch | Pin check and credential lookup (`MISTRAL_API_KEY`, or the macOS Keychain through `/usr/bin/security`) before any process exists; then `vibe-app-server` from the real path the pin hashed, no arguments, own process group, filtered environment, private `HOME`, `VIBE_HOME` and `TMPDIR` in the run directory, and a per-worker loopback managed-config endpoint bound before spawn. The task travels in `turn/start`, never in arguments. | Pin, credential or endpoint failure, before spawn |
| Antigravity launch & policy (`backend = "antigravity"`, experimental, needs `experimental.antigravity = true`) | Probes `agy --version`, verifies `assertNoProjectVibeExtensions` and `assertNoProjectAntigravityExtensions` (rejecting any `.gemini`, `.agent`, `.agents`, `GEMINI.md` or `AGENTS.md` at the workspace root or an ancestor, so this repository itself is not eligible for the Antigravity backend), creates private `antigravity-home` and `antigravity-tmp`, writes `$HOME/.gemini/antigravity-cli/settings.json` (`toolPermission = "strict"`, `enableTerminalSandbox = true`, `allowNonWorkspaceAccess = false`, mode-specific `permissions.allow` and `permissions.deny`), spawns `agy -p <prompt> --mode <plan\|accept-edits> --output-format stream-json --disable-slash-commands --sandbox --print-timeout <N>s` in `workerWorkspace`, parses `status`, `usage`, `num_turns` and `denied_actions`, and removes `antigravity-home` and `antigravity-tmp` on completion/close and restart recovery. The child gets only the selected Google key, `BROWSER=false` and `open`/`xdg-open` shims on `PATH`; preparation accepts only ADR 0008's pinned built-in skills with `builtin: true` and exact global permissions. | Missing `agy` or API key, untrusted workspace extensions, `status: "ERROR" \| "INVALID"`, output limit or timeout |
| Pin | Installed files match the manifest `pin-manifest` wrote on the Vibe machine; `serverInfo.version` equals 3.0.2 after `initialize`. | Any version, `RECORD`, file or unsafe-file mismatch (`VSUP_VIBE_VERSION_UNSUPPORTED`) |

| Read-back | `runtime/read`, `config/effective/read` and `config/read` must show exactly the profile tools, only the bundled skills ADR 0006 permits (with their provenance) and a root skill count of 0, no MCP, connectors, hooks or issues, bypass off, the unified harness (a null selection source accepted), the expected `cwd`, the owned managed-config URL, every setting above, `ask` and the exact denylist per tool, thinking off; repeated after thinking is written and after every handoff. | Any difference or missing field (`readback_mismatch`), before the first turn |
| Approvals | The supervisor answers every `callback/call`: approve only the profile's tool (`file_system.read_file`; for an edit also `file_system.write_file` and `file_system.search_replace`) with the matching effect kind on an in-workspace path that names no reserved directory or secret file; deny everything else within 5 seconds; never a session or permanent approval; each approval bound to one effect by a fingerprint of the shown input. | Deadline, repeated id, malformed callback, wrong session, revoked handler: deny |
| Event validation | Every history entry is classified; reasoning is dropped on receipt. A denied effect is recorded as `tool_denied` and the run continues. An allowed or executed effect is approved only with decision `execute`, type `ask`, source `user`, linked to the handler's approval for the same effect, tool and turn, with an equal fingerprint; null metadata is unapproved. | `turn/interrupt`, then `VSUP_BACKEND_ERROR` with `details.reason` (`unapproved_effect`, `unknown_entry_kind`, `watermark_gap`, `unfinished_effect`, a malformed notification) |

| Patch acceptance | An optional contract (exact allowed and required paths, text and hash assertions, required validation IDs) is normalized, hashed and frozen before launch, and evaluated on the committed base plus the exported patch in a private index; bounded saved inputs allow re-verification after cleanup ([workflow acceptance](../docs/workflow-acceptance.md)). Project code never runs. | Missing, unsafe or changed inputs give `incomplete`, never a pass |
| Coordinator decision | `vibe_close` takes an assessment bound to the patch and contract hashes and the coordinator's validations; acceptance needs a fresh automated pass and every required validation passed. Assessments append; a correction keeps the earlier decision. | A hash mismatch or missing validation refuses acceptance |
| Validation | `validation prepare` builds independent baseline and candidate copies from the immutable base and exact patch, with hooks, global Git configuration, lifecycle scripts and fetches off, from a private copy of a populated offline cache; `validation clean` removes only an owned copy whose content still matches ([validation workspaces](../docs/validation-workspace.md)). | Export | `runs verify` and `runs export` write sanitized reports with hashes, optionally the exact patch and projected events; no transcript, reasoning, receipt, history or credential, and private paths replaced. | A patch that trips the credential check is refused, not rewritten |

Around this sit the run controls: strict schemas and exactly five tools; a single-use dispatch grant per start, registered with `task authorize`, bound to the request's digest and checked again just before launch ([ADR 0010](../docs/adr/0010-dispatch-attempt-authorization.md)); the owner-controlled allowlist reread before every readiness check and start; boot-bound settings (`backend`, `paths.*`, `limits.*`, `retention.days`, `version`) that demand a restart; readiness receipts (HMAC, 10 minutes, bound to instance, policy revision, operation, workspace and edit base); one active slot per instance with an owner lock; `--isolated` storage per connection; bounded, redacted, atomically written persistence.

## Verification model

Five layers, each honest about what it cannot show. Evidence is recorded against an exact source, archive and installed distribution in [acceptance.json](../docs/acceptance.json) and never transfers to other bytes; partial observations stay partial.

| Layer | Proves | Does not prove |
|---|---|---|
| Tagged source audit | Wire and configuration assumptions, with file hashes | The behaviour of a running build or another release |
| Scripted fake and fixtures | Contract, lifecycle, permission, recovery, Git, acceptance and reporting regressions against defined observations | Vibe's behaviour, the provider, another platform |
| Cold review and local release checks | Lint, strict types, build, tests, acceptance, secret scan, SBOM, offline installed catalogue | Hosted inference, desktop registration, clean-account installation, another Node floor |
| No-inference conformance on the target | Pin, handshake, initialization, configuration read-back and cleanup for identified bytes and runtime | Hosted tool behaviour, thinking generation, experiments attribution from a host name |
| Target gates with owner authorizations | Native readiness, bounded hosted runs with independent acceptance, a disconnect, a clean account, each on the named archive | Unlimited reliability, changed artifacts, unsupported clients or platforms |

1. **Source-read facts with hashes.** Every wire fact the client relies on is read from Vibe's tagged source without running it, and recorded with the SHA-256 of each file read. For 3.0.2 that is tag `v3.0.2`, commit `36f7b3a4e10440e90f98080492530b8f4d46960d`, in [the 3.0.2 assessment](../docs/compatibility-v3.md); [compatibility](../docs/compatibility.md#source-basis) keeps the earlier release's basis and [its wire facts](../docs/compatibility.md#wire-facts-the-client-relies-on).
2. **The scripted fake.** `tests/fixtures/fake-vibe-app-server.mjs` speaks the audited subset from scenario files, written from the source answers independently of the client's types. It checks inbound parameters strictly, as the real server's models do, and refuses snake_case effect inputs and unknown keys. It proves the client against the source facts, not against Vibe: the target found two beliefs it encoded wrongly (the harness provenance and the skill catalogue). Fixture tests inject their own preparation evidence; there is no production bypass.
3. **Cold reviews and local release checks.** A reviewer with no design context reads the diff before every merge. `npm run verify:release` (lint, typecheck, build, tests, acceptance, secret scan, SBOM) runs locally on every change, and GitHub Actions CI runs it again on Node 20.19.0 and 24.21.0 for every push. Each qualified archive records its own run on exactly Node 20.19.0 (2.2.0: 109 files, 1,567 tests); `main` after the Antigravity 1.4.7/1.4.8 merge passes 110 files and 1,583 tests. The 2.2.0 hosted trials ran under Node 24.21.0, so both runtimes are exercised. `npm run package:rc` adds the offline installed-package smoke test with its exact five-tool catalogue, writes the preparation kit, and then installs the packed archive offline to prove the kit names the bytes it ships with.
4. **No-inference conformance on the target.** `prepare check` runs `scripts/v2-conformance-check.mjs` from the kit against the installed candidate: no turn, a fixed fake key, a refusing network observer with a telemetry-and-experiments control. Its pass is the receipt dispatch requires and the evidence for gate `target-no-inference-conformance-check`, nothing more.
5. **Target gates with owner authorizations.** Every claim about a running Vibe, a native client or a platform is a named gate in `docs/acceptance.json`, `UNVERIFIED` until the target machine records its evidence; hosted runs need the owner's allowance, and a code fix found on the target goes through a reviewed branch and becomes a new candidate. The gates are listed in [compatibility](../docs/compatibility.md#unverified-gates): the no-inference conformance check, native readiness, one hosted review and edit, an MCP-client disconnect, `permission = "ask"` visible and reaching the handler, thinking off, the experiments fetch, nested `run_typescript` gating, the Node floor, populated pnpm validation, and the clean-account installation. For the Antigravity backend they add the five agy probe gates (hook invoked and deny honoured, hook failures deny, stream tool shape, proxy honoured, project configuration not loaded). The [target acceptance procedure](../docs/target-acceptance.md) orders them and stops at the first failure.

**Open protocol questions that fail closed.** Only a real server can settle these, and in each case the client refuses rather than guesses: whether a callback's `relatedEntryId` is filled at the entry or only in `detail` (if only `detail`, every approval is refused); whether handler-approved effects carry `approvalType` `ask` and `approvalSource` `user` (if not, every approved call fails the run); whether `agentConfig.maxTurns` is enforced (it is not read back, and the model-call backstop turns off when Vibe reports no count); how long Vibe keeps a callback open (the handler answers within 5 seconds regardless); whether a large legitimate `write_file` fits the 8 MiB line cap. Whether thinking off stops reasoning generation, which the throwaway store would hold until cleanup, is an observation gate. The target acceptance procedure records which way each goes.

## Lessons

**About Vibe's protocol.** Each of these was a guess that would have broken every real run, caught by reading the tagged source or by the first target check:
- Wire fields are camelCase (`filePath`), because app-server models serialize by alias. The Python attribute name is not the wire name.
- Callbacks and effects name tools `file_system.read_file`, `file_system.write_file` and `file_system.search_replace`; `enabledTools` takes the config names `read_file`, `write_file`, `edit`.
- `read_file` defaults to `always`, and a path allowlist resolves to `always`: both skip the approval callback. The agent profile sets `permission = "ask"` and carries only the denylist.
- Vibe can allow a call without asking (scratchpad paths, session grants, the bypass gate). Only an `execute` / `ask` / `user` effect linked to the handler's own approval counts as approved.
- `vibe-app-server` writes no run export, so usage is rebuilt from events, and counters reset at a context handoff.
- `config/effective/read` has no `max_turns`, and the server redacts MCP `args` and `env`. A read-back that expects either fails every start.
- After a handoff, the new session id is `sessionId`; the old one is `oldSessionId`.
- `config/read.harnessSelectionSource` is null on the unified implementation, the packaged plugin skills are listed even with every skill disabled, and a managed-configuration refresh runs whenever a provider key is present. The source read did not settle these; the installed server did.

**About verification.**
- A fake server encodes what we believe. It proves the client against those beliefs, not against Vibe. Write the fake from source answers with file hashes, reject anything the source contradicts, and expect the target to find what both missed.
- An independent implementation is a strong check. The parallel Codex line and this one each caught errors the other made, and each built pieces the other lacked.
- A cold review before every merge pays for itself. The engine review found a reaper dropped on a failed start, approvals still granted after a stop, and protocol faults hidden by a later cancel, all after a full green test suite.
- Grep-based audits miss behaviour; read the tagged source and record its hashes.
- Evidence belongs to bytes. A packet that says it does not certify a later package means exactly that; integrating it changes the bytes, so the gates reopen.

- A real gate finds what tests do not. The first populated-pnpm run found that the lockfile check matched `file:` inside `excludeLinksFromLockfile`, so every pnpm 9 project was blocked, after the whole suite had passed.
- Verify the packaged archive itself, not the tree. The target packet passed release verification, the smoke and every test, and its kit still named other bytes; only an independent inspection of the archive caught it, so packaging now installs the exact archive and compares identities before it reports success.
- Package early and on the machine that will test. `npm pack` runs `prepare` even with `--ignore-scripts`; a cache filled by `npm ci` lacks the metadata an offline tarball install needs, so fill a dedicated cache with `npm cache add` per locked version; and the SBOM's time and namespace make archives differ across machines, so test and publish the same bytes.

**About coordinating.**
- A worker's final summary is not the work. On `<site-project>`, the exact patch contained the required disclosure while the summary abbreviated it, and the coordinator first rejected a correct patch. The answer is deterministic acceptance on exported bytes, append-only correction history and accurate attribution; no allowance or fallback is spent until the bytes show a real failure.
- Worker answer quality is a separate axis from supervisor correctness. The hosted review stayed inside every boundary and still reversed two of five cases; the edit is reported to have stayed inside them too and missed its contract. Record the run's execution, the automated verification and the coordinator's decision apart, and decide what to spend on answer quality as its own question.
- A model's report of a tool error is not an event. The review answer said `writeFile` is not a function; with no denied event the probe is NOT EXERCISED, and the member name should have been checked against the pinned source before a start was spent. Ask for labeled rows, so a wrong answer is visibly wrong per case.
- Measure the thing itself. A word count over private files could not tell reasoning from configuration text, and closing a run erased `completed` from its export; both are now structured fields. A source fix after the sitting is a new candidate: the frozen archive does not contain it.
- A report on an unmerged branch is a report. The edit result stays "reported" until its sanitized packet reaches main.
- Preparation should be version-matched, bounded and observable. A missing installed script, a dependency link outside a build copy, ambiguous readiness or an accidental model-role assignment is workflow evidence to repair, never a reason to broaden permissions or replay a task.

- Integrate parallel lines before deciding a release. The v2.0.0 draft looked ready while the other line had already shown it could not start on the real Vibe.
- Before deleting a superseded branch, record it with an `ours` merge, so its commits stay reachable from main and nothing is lost.
- A gate ledger that is not updated with the evidence misleads more than no ledger. The 2.2.0 trials were accepted and recorded under `research/evidence/`, while `docs/acceptance.json` kept 2.1.0 as the candidate and the hosted gates unverified; the two then disagreed for a release.

**About the 2.1 and Antigravity cold reviews.**
- A hook-based gate needs per-run proof that it ran. A hook file on disk and a read-back of it say nothing about whether the vendor's process called it for a tool call; prove it through the vendor binary, and treat a run whose hook ledger cannot account for its tool calls as failed.
- Denylist filters leak. Dropping reasoning or secrets by a list of known field names misses the next field name; keep what is known safe (an allowlist) and drop the rest.
- Resolve a binary once and execute exactly what was hashed. Looking it up again on `PATH`, or probing its version with the full environment, means what runs need not be what was checked.
- Key budgets by canonical paths. A budget or exclusion keyed by the path as written can be sidestepped by another spelling of the same directory.
- A check that the supervisor runs on its own script is not evidence about the vendor. The first Antigravity no-inference check ran the hook directly; it showed the script works, not that agy uses it.

**About 2.1 and 2.2.**
- Ship no unreachable code on a live path. The deferred correction mode was off everywhere, yet its edits to turn completion and deadline handling broke every one-shot run's finalization; deferring a feature means removing its code from shared paths, not just its entry point.
- Bind what matters, not what is cheap to read. A review grant bound to file timestamps was spent by any editor or build touching the tree; content of the files Git can see is what the review reads.
- An authorization needs diagnostics from the start. A single "invalid or unavailable" hid a Node-runtime mismatch between `task authorize` and the server; per-field hashes name the cause without exposing values.
- Read the vendor's spawn path before trusting a process boundary. Vibe's MCP SDK starts stdio servers in a new session, so a sidecar escapes the worker's process group and the reaper and needs its own lifetime check.
- A source review can retire a design. Vibe 3.0.2's client-provided tools looked like a simpler search route; its own source marks them internal to embedding hosts, so the MCP route stands.

**About working with agents.**
- An agent must never stage, move or remove files in Git. One agent's staged removals once went into an unrelated commit and published a half-removed change. The coordinator commits by path.
- Chain every check and the commit with `&&`, so a failed check stops it. A secret-scan failure was once committed because the command continued. A check gates on its exit code (`cmd; echo exit=$?`), never on a `grep` of test output, which hides failures.
- A long-running agent writes a usable first version early, so an interruption leaves something; the coordinator checks for its leftover processes afterwards.
- Fake credentials must not look like keys: `/\bsk-[A-Za-z0-9_-]{24,}\b/` fails the secret scan.
- Agents write files with the Write tool, never with heredocs that wait on stdin, and avoid aliased `ls`; both left hung shells.
- Give each agent named files, the wire facts it must use, and what it must not touch; forward any fact one agent finds that another depends on.
- A test that passes alone and fails under full parallel load is a timing issue to fix, not to retry until green.
- Give the owner runnable commands, never placeholders: a command is run as written.
- Environment guards are not obstacles. A hook that blocks writes to another worktree and a classifier that blocks credential use are answered by handing the owner the exact command, never by a workaround.
- A session goal that needs the owner's hands keeps a stop hook looping; set goals the session can meet.

## Working rules

- **The main chat coordinates.** It sets scope, the immutable base, the contract and the hosted budget, verifies independently, and records execution, verification and its own decision separately. A fallback implementer is used only after a verified rejection of the exported bytes, within the user's scope, with Vibe's and the fallback's changes attributed separately.
- **Task-scoped preparation is authorized by the task.** A Vibe implementation request covers installing or switching the candidate, the no-inference check and adding only the named root, with settings and rollback kept; no separate approvals for those. Hosted starts still need their explicit budget; broader roots, publication, deployment and unrelated global changes stay outside.
- **Diagnose, do not retry.** Deterministic failures stop the step; repair, then check the changed artifact. Nothing is replayed.
- **Verification.** Every change ends with `npm run verify:release`, and CI repeats it on every push; a release adds `VIBE_SUPERVISOR_TEST_NPM_CACHE=<populated cache> npm run package:rc` and a run on Node 20.19.0. Documentation-only changes need links, JSON and `git diff --check`. Report only checks actually run.
- **Two machines.** Vibe is never installed, run or tested on the preparing machine, the installed-Vibe fixture included; questions about Vibe are answered from its tagged source, checked against the recorded hashes. Behaviour is proven only on the target machine, with the owner's authorization and budget; the target records evidence. The target may fix code it finds broken, on a branch from main that it pushes for review; it never pushes to main or publishes, a code fix makes a new candidate whose earlier evidence does not transfer, and the coordinator reviews the branch (private-path scan, `npm run verify:release`) and merges it. Version numbers and runtime code change on main.
- **Fakes prove the client, not Vibe.** A gate is verified only by target evidence for the exact archive; missing evidence stays "unverified", never a guess.
- **Evidence uses placeholders from the start** ([target acceptance](../docs/target-acceptance.md#recording-evidence)), because the repository is public. No credential, receipt, reasoning or private session history reaches any committed file, prompt, transcript or report.
- **Agents work in parallel on disjoint files.** Each agent owns named files, commits nothing, and reports what it could not verify. The coordinator runs the full checks before every commit, and nothing is committed while a check fails.
- **Branches.** Work happens on a branch, in an isolated worktree that leaves the primary checkout alone, and reaches main by merge after the full checks and a cold review. Push with `make push` (main) or `make push-branch BRANCH=<name>`. A branch is deleted only after an ancestry check.
- **Evidence reaches the repository first.** A gate, changelog line or Handoff row claims a target result only after the sanitized evidence and its `docs/acceptance.json` entry are committed.
- **Owner decisions are explicit.** Pushes, hosted runs, releases, scope readings, vendor downloads and every public post need the owner's separate yes, recorded in [Handoff.md](../Handoff.md).
