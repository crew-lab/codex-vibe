# Feature candidates after 2.0 (2026-10-14)

Read-only research on 2026-10-14. Nothing was installed, run, posted or filed. External facts come from pages fetched that day and are listed in section 7 with their URLs; GitHub numbers (reactions, states, dates) were read from the public API at that moment and move. Protocol facts come from the Vibe v2.26.1 source already extracted for the [audit](../docs/history/app-server-protocol-audit-2026-10-14.md), read again for this note. This directory is outside the package `files`; nothing here ships.

Tags: **[V]** read on the owner's own page or API (vendor docs, the repository's issue tracker, the Vibe source); **[T]** third party; **[I]** our inference; **[U]** not established. Fit is judged against the fixed boundaries in [AGENTS.md](../AGENTS.md): *keep* needs no boundary change, *ADR* touches one in a reviewable way, *rejected* breaks one.

## 1. Demand evidence

### 1a. External, by theme

**Delegation to subagents, and isolating them.** Codex's "Subagent Support" request drew 413 reactions before closing (#2604, 2025-08-23) and "cannot specify subagent models" 206 (#31814, 2026-07-09) [V, S1]. Paperclip's first RFC was "adapter-level git worktree isolation for parallel agent execution" (#175, 2026-03-07) [V, S5]. Claude Code's subagent worktree isolation was patched four times in a month (2.1.203, .210, .216, .222) for reaching the parent checkout through shell and `git -C`/`GIT_DIR` [T, S28, 2026-08-06]; the author's advice is to verify isolation against a disposable repository. Codex users asked for `--worktree` startup (#12862, 129, closed) and Codex 0.162.0 shipped managed worktrees [V, S13, 2026-10-08]. [I] Isolation that returns a patch and never applies it is what these threads converge on; the Claude Code patches show how hard "the subagent cannot touch the checkout" is to keep when the subagent has a shell, which our worker does not.

**Review as a product.** Claude Code Review posts severity-tagged inline findings (Important, Nit, Pre-existing), a machine-readable severity count in the check run, collects 👍/👎 on each finding "to tune the reviewer", reviews fork PRs only on an explicit comment, and prices at "$15-25" per review [V, S17]. Cursor Bugbot claims "70%+ of flags get resolved before merge" and "$1.00–$1.50" per review [V, S20]; a third party estimates CodeRabbit at $40M ARR in April 2026 [T, S21]. Codex has `/review` ("prioritized, actionable findings without changing your working tree") and `@codex review` on GitHub [V, S14]; the Linux Foundation's Sashiko reviews every LKML submission with Google-funded tokens [V, S30; 111 HN points, S25]. "Show HN: Stage – Putting humans back in control of code review" got 130 points and 111 comments (2026-04-16) [V, S25]. In Vibe's own tracker, a user found the bundled `code-review` skill inconsistent, closed not planned (#301, 2026-02-03) [V, S3].

**Cost and usage.** The loudest threads in every tracker are about spend: Codex #28879 (561 reactions), #14593 (308, 630 comments), #23794 (253, a removed usage indicator) [V, S1]; Claude Code #38335 (545) [V, S2]; Vibe #275 "rate limits unclear" (22), #740 (9), a `/cost` command (#108, shipped) and a read-only usage surface for orchestrators, "an explicitly unavailable field is preferable to a zero" (#1161, open 2026-09-29) [V, S3]. Paperclip users want token-denominated budgets (#1756) and cost estimates for subscription runs (#339) [V, S5]; Multica had to document that headless `claude -p` bills from a separate pool (#2563) [V, S6]; ACP contributors asked for normative usage semantics (#1860, #890) [V, S7]. Claude Code ships `--max-budget-usd` with explicit headroom caveats [V, S18]; Codex has a token "rollout budget" marked under development [V, S12]; Codex 0.162.0 "Preserve native USD amounts in thread usage responses" [V, S13].

**Safety.** "A way to exclude sensitive files" is one of Codex's most-reacted requests (#2847, 470) [V, S1]. AI Now's "Friendly Fire" (2026-07-08) showed Claude Code 2.1.116–2.1.199 and Codex CLI 0.142.4 in autonomous modes running attacker code while reviewing an untrusted repository, with "no hooks, plugins, MCP servers, or configuration files" needed [T, S27]. Sandbox products launched on HN all year (Freestyle 322 points, Agent37 160, Pi pod 121, Runtime 103) [V, S25]; Claude Code added `--restricted` for harnesses on shared machines [V, S18]; Vibe's Ideas board has "Sandbox Support" (3 votes, 2025-12-10) and a privacy complaint about telemetry defaults (#679, 7) [V, S3, S4].

**Auditability.** Codex #28058, "encrypted MultiAgentV2 messages remove readable task audit trail" (150 reactions, open since 2026-06-13), asks that "Codex should preserve a human-readable, structured audit copy" [V, S1]. A controlled study of delegation contracts (arXiv 2606.17099, 2026-06-14) found they "bought reviewability rather than correctness" [V, S26]. Hooks, the audit primitive users reach for, are Codex's #2109 (688) and the top Vibe idea (20 votes) [V, S1, S4].

**Structured output.** Codex `exec --output-schema` is wired into the official GitHub Action [V, S16]; Claude Code has `--json-schema` and a `ReportFindings` tool for hosts [V, S18, S17]. GitHub accepts SARIF 2.1.0 only, 25,000 results per run, 20 runs per file, 10 MB gzipped, and generates `partialFingerprints` when absent [V, S22]; reviewdog ingests `-f=sarif` and `-f=rdjson` and posts to `github-pr-review` or `github-pr-check` [V, S23].

**MCP direction.** Revision 2026-07-28: stateless, `server/discover`, Tasks moved to the extension `io.modelcontextprotocol/tasks` with `tasks/get` polling and `tasks/update`, server-initiated elicitation and sampling replaced by multi round-trip `input_required` results, Roots/Sampling/Logging deprecated, deterministic `tools/list` with `ttlMs` [V, S8]. The 2026-08-22 roadmap names five areas; under agentic messaging it says "there is a clear need to steer work mid-flight" and plans to mature Tasks into the specification; it also wants "one clear contract" for tool results and progressive tool discovery [V, S9]. The community client matrix has no Tasks column at all and does not list Codex [V, S11]. Codex's config knows `default_tools_approval_mode` (`auto|prompt|writes|approve`), a 60 s `tool_timeout_sec`, a 10 s `startup_timeout_sec`, and lists `tool_search` among "retired switches" [V, S12]; 0.162.0 mentions "Guardian MCP elicitation reviews" and "opt-in ranked tool search in Code Mode" [V, S13].

**Packaging.** Codex plugins "can include skills and MCP servers" plus hooks, installed from marketplaces with `/plugins` [V, S15]; the `.codex-plugin/plugin.json` format could not be read from the docs (two 404s) [U]. MCPB is a zip with `manifest.json`, built with `mcpb init` and `mcpb pack`; Claude for macOS and Windows installs it [V, S24]; the registry accepts it on GitHub releases ([outreach draft](../docs/history/outreach-drafts.md#3-mcp-registry-entry-post-after-stable-101)).

**Platforms and cadence.** Linux desktop requests: Codex #11023 (1,464) and Claude Code #65697 (655), both closed [V, S1, S2]; Vibe has a nixpkgs build (#975) and a container login bug (#941) [V, S3]. Vibe released 2.25.8, 2.26.0 and 2.26.1 between 2026-09-23 and 2026-10-09 [V, S29]: three candidates in sixteen days at our one-pin-per-release rule.

**Images and steering.** Vibe users asked for image attachment in the CLI (8 votes, 2026-01-04; a drag-and-drop variant closed) [V, S4]. Mid-run steering exists in Multica ([landscape](../docs/history/competitive-landscape-2026-10-13.md)) and in the MCP roadmap quote above. Page 1 of 8 of Vibe's Ideas board carries nothing on headless mode, the app-server, third-party clients, read-only review or structured output [V, S4]; the other pages were not read [U].

### 1b. Internal

- [Usefulness log](../docs/history/usefulness-log.md): six real runs, three accepted. Every accepted run was narrow with enumerated inputs; the rejected edit missed an edge that was not named; the rc.28 real-project review "executed and closed safely but failed answer acceptance" and the record says nothing more about why [V, rc.28 STATUS.md; U]. The run that returned an empty patch claiming "tools were unavailable" has no recorded tool attempt, so its cause is unknown. Usage is UNKNOWN in every row: the cheapest missing evidence is a number the supervisor already computes.
- Open protocol questions only the target can answer ([Handoff](../Handoff.md#open-questions)): `relatedEntryId` placement, the `ask`/`user` approval triple, whether `maxTurns` is enforced, callback expiry, the 8 MiB frame, the throwaway store. Each fails closed; each is a gate, not a feature.
- The parallel Codex branch built a read-only search sidecar (`search.ts`, `search-server.ts`, `path-policy.ts`) that was not ported, held "only after the 2.0.0 target runs confirm the MCP route names and tool inventory on the real server" ([2.0 path](../docs/history/v2-path-2026-10-14.md)). The audit's question 3 to Mistral is a search builtin. Reviews today "depend on a prompt-supplied listing" ([design note](../docs/history/app-server-client-design.md#9-risks-and-open-questions)).
- The audit's questions 1, 4 and 5 (catalogue narrowing, omitting reasoning, honouring budgets) remain unanswered; a yes removes work from candidates 1, 4 and 16.

## 3. Candidates

Each entry: what it is, who it serves, demand, fit, protocol basis, effort (S under a day of agent work, M a few days, L a release), risk, gate.

1. **Review search sidecar.** A supervisor-owned MCP server offering bounded `grep`/`glob` over the allowlisted workspace, passed in `mcpServers`, called by the model through `run_typescript`, every call approved only when the route is the sidecar's and the path passes the same judgement as `read_file`. Serves every review user; the listing is a stopgap. Demand: internal (1b), the Codex branch built it, Mistral question 3; no external thread asks Vibe for it [U]. Fit: keep (planned). Protocol: audit §5; read-back must then show exactly one MCP source. Effort M. Risk: MCP child environment, timeouts and result limits [U, audit 9.4]; `run_typescript` must stay listed, which it does. Gate: a hosted review whose history shows a sidecar call approved and a nested write denied.

2. **Structured review output and SARIF export.** The review template asks for a fixed JSON findings object (severity, path, line, trigger, requirement); the supervisor validates the final message, records `format_valid`, checks each path against the launch snapshot and the line against the file length, and exports `findings.json` and an optional SARIF 2.1.0 file (`ruleId`, `level`, `physicalLocation.region.startLine`, `partialFingerprints`) under `limits.max_artifact_bytes`. Serves coordinators and CI consumers (reviewdog, GitHub code scanning). Demand: S16, S17, S18, S22, S23. Fit: keep (an artifact, no new tool; an optional `output: "findings"` field on `vibe_review_start` is a schema addition). Protocol: none native, `turn/start` carries text only; the supervisor parses. Effort M. Risk: model non-compliance, so an invalid object is a warning not a failure; a line number is still the worker's claim, which the snapshot can bound but not prove. Gate: fixture for valid and invalid output; one hosted review producing a valid file.

   *Review-to-patch handoff.* A skill template that turns one finding into an edit task with "Must reject or preserve" filled from the finding's trigger. Keep, S, no protocol. Gate: one hosted pair, recorded in the usefulness log.

3. **Edit scope declaration (`allowed_write_paths`).** The edit start lists the files the worker may create or change; the approval handler denies writes elsewhere and the run continues. This is the non-interactive part of "per-file approval": the plan is approved before the run, not during it. Serves edit users who want the blast radius stated. Demand: Codex Plan Mode (#2101, 506) and Vibe's diff-preview requests (#23, #746) [V]; the usefulness log's accepted edits all named their files. Fit: keep (narrows the handler). Protocol: `effect.input.filePath` already judged per call. Effort S. Risk: none new. Gate: fixture (out-of-scope write denied, run continues); one hosted edit.

4. **Usage in the record, ceilings persisted, per-workspace ledger.** Save `usage`, the ceilings in force and `tool_calls_*` counts in every run record and show them in `runs list`; later, a per-root ledger (`budgets.<root>.max_cost_usd_per_day`) that readiness reports as a blocker. Serves everyone paying for runs and the usefulness log. Demand: the strongest external signal (1a). Fit: keep (bounded budgets are already a boundary). Protocol: `AgentStatsSnapshot`, Vibe's pricing formula. Effort S for the record, M for the ledger (retention interplay, cost is "not authoritative"). Risk: `price_unavailable` fails closed when a ceiling is set; a ledger must not become a second policy source. Gate: hosted run with usage recorded; ledger tests.

5. **Explain-the-diff (dry run).** After an edit, a second bounded review whose only input is the exported patch (`context_files`) and the base files, asked to say what changed, what could break, and what the tests do not cover. Serves the coordinator before integration. Demand: Stage HN thread, Claude's "Why this was flagged" [V]. Fit: keep. Protocol: none; Vibe's `review/turnDiff` is an idle-only UI API for Vibe's own edits and `narration/summarize` is a second provider call, neither needed. Effort S (skill template). Gate: one hosted pair.

6. **Steering a running turn.** `turn/steer` injects a user message into the active turn. Demand: MCP roadmap, Multica. Fit: ADR. It is a pending-input protocol by another name: the task is no longer the one the receipt and record admitted, the steer text would need its own redaction and bounds, and the "no continuation" line in AGENTS.md covers it. Effort M. Placement later, only with an owner decision.

7. **Image or screenshot context.** `ImageContentBlock` lets a review carry a screenshot. Fit: keep with constraints, because turn input bypasses the approval handler: only inline data from a validated `context_files` entry inside the workspace, size-capped, never a file path handed to Vibe. Demand: 8 votes on Vibe's board; for code review, low [I]. Protocol: `_vision.py` may add a provider call to describe the image for a blind model; `images_supported` is read back. Effort M. Risk: the describer's cost and failure path; which models see images [U]. Gate: hosted review with one image. Placement later.

8. **Continuation inside one bounded run.** A second `turn/start` on the same idle session, under the same budgets and approvals, for exactly one purpose: a repair turn when candidate 2's output is invalid. Not a client-facing continuation. Fit: ADR, because "no continuation" is fixed and the audit, handoff and usage logic assume one turn per run. Effort M. Placement later; first measure how often the repair would fire.

9. **Resume, replay, queue.** Vibe offers `session/resume` and a 32-item turn queue. Rejected: AGENTS.md says a restart never reloads a session or replays a task; a replayed turn would re-execute effects without their approvals, and a queue hides a second run behind the one-slot rule and outlives a receipt's policy revision. Demand exists (Vibe #249, Paperclip and Multica resume) and is out of scope.

10. **Concurrent runs.** Rejected per instance: the slot is the capacity guarantee. The documented pattern stays "one isolated connection per concurrent delegation"; a Codex subagent inheriting the MCP server hits the second-start rejection by design ([Antigravity research](antigravity-2026-10-14.md#3a-antigravity-as-the-mcp-client)). Demand: Paperclip #332, Codex subagents. Effort S (docs). Gate: two isolated connections running side by side on the target, never observed.

11. **Linux.** Code paths exist (XDG data root); what is missing is the credential path (the Keychain lookup is macOS-only, `MISTRAL_API_KEY` is the Linux route), process-group semantics for the reaper, a pin manifest generated on Linux, and evidence. Demand: 1a. Fit: keep, evidence-gated; the marketing strategy already lists it as an unclaimed contribution area. Effort M. Gate: conformance check, one hosted review and edit, one disconnect, all on Linux. Placement 2.2 or contributor-driven.

12. **Vibe candidate tooling.** A script that, for a new Vibe tag, diffs the hashes of the audited files, lists changed protocol models, reruns the fake-server scenarios and writes the candidate's `supported-vibe.ts` and manifest skeleton; plus the planned wheel-derived shipped manifest. Serves the maintainer at three Vibe releases per fortnight [V, S29]. Fit: keep. Effort M. Risk: no protocol version field, so a silent wire change passes the hash diff only if the audited file list is complete. Gate: the next Vibe release. Placement 2.1.

13. **MCP Tasks extension.** Our start/status/result is the Tasks shape (`tasks/get` polling, server-directed task handles) [V, S10]. Fit: keep, later: no client in the matrix declares Tasks, Codex's config has no key for it, and the SDK 2.3.0's support is [U]. Effort M. Gate: a client that sends the extension capability.

14. **Elicitation for owner approvals.** Rejected: a human approving a worker's file write mid-run is the interactive grant the boundary removed; the handler's 5-second deadline and deny-by-default are the design. The 2026-07-28 revision also replaced server-initiated elicitation with `input_required` results, so the shape would be a retry of `vibe_edit_start`. Codex's Guardian reviews elicitations [V, S13], behaviour [U].

15. **Runs dashboard.** `runs list|show|tail|cleanup` exists; a watch view adds little until candidate 4 gives it numbers. Demand low (Codex status line #17827 is for Codex's TUI). Keep, S, later.

16. **Audit bundle export.** `runs export <run_id>` writes one self-contained JSON: policy revision, admitted root, pin manifest digest, server version, every event with entry ids, the approval ledger with fingerprints, integrity, usage, artifact digests. Serves compliance and the article's "count process claims" rule. Demand: Codex #28058, arXiv 2606.17099 [V]. Fit: keep (reads what is already saved, redacted). Effort S–M. Gate: schema test; one hosted run exported. Placement 2.1.

17. **GitHub Action / CI mode.** A headless review of a PR needs Linux runners, Vibe installed and pinned on the runner, the key as a secret, and a non-MCP entry point, which is a new surface. Fit: ADR, after candidate 11. Safety: the Friendly Fire result is a shell-and-auto-approve failure our worker cannot reproduce (no shell, no network), which is the argument for it; the answer is still untrusted data ([security](../docs/security.md#what-is-not-isolated)), fork PRs withhold secrets [V, S19], and the two-machine rule has no runner equivalent. Effort L. Placement later.

18. **Usefulness feedback loop.** `vibe_close` gains optional `accepted` and `reason`; the record stores them; `runs usefulness` prints the log row with usage from candidate 4. Serves the owner's monthly entry and the skill's "record whether the answer was accepted". Demand: Claude collects per-finding reactions to tune its reviewer, Bugbot reports resolution rate [V]; "Ask HN: Do you have any evidence that agentic coding works?" drew 461 points [V, S25]. Fit: keep (an optional field on an existing tool). Effort S. Gate: fixture; one hosted close with acceptance. Placement 2.1.

19. **Project-level prompt templates.** Per-language review and edit templates. Keep when they ship in the skill or a plugin; ADR if the supervisor reads them from the workspace, because that is project state steering the worker's prompt. Demand: `REVIEW.md`, Bugbot Rules, Codex `AGENTS.md` review guidance [V]. Effort S. Placement 2.1 (skill).

20. **Codex plugin and MCPB bundle.** Both bundle the server and the skill, neither can install Vibe. Keep. Effort M. Risk: the plugin manifest is an unverified scaffold ([compatibility](../docs/compatibility.md#unverified-gates)) and the Codex format docs were unreachable [U]. Gate: `mcp-publisher validate`; one plugin install on the target. Placement 2.1–2.2.

21. **Antigravity client gates.** As researched: four gates, docs only, no runtime change unless the wrapper blocks the flow. Keep. Placement 2.1.

22. **Extra exclusions per workspace.** `excluded_globs` in the policy file, added to the fixed denylist (never removing from it), written into the profile's per-tool `denylist` and read back. Serves anyone with secrets outside the fixed patterns (fixtures, dumps, `*.tfvars`). Demand: Codex #2847 (470) [V]. Fit: keep. Protocol: `tools.<name>.denylist` in `config/effective/read`. Effort S. Gate: read-back shows the merged list; fixture denial. Placement 2.1.

Behind them: 20 packaging (2.1–2.2, marketing-driven), 5 and 19 skill templates (2.1, S), 15 dashboard (later), 13 Tasks (later, client-gated), 7 images (later), 6 steering and 8 repair turn (ADR only), 17 CI mode (later, after 11 and an ADR). 2.0.1 takes none of this: it is cleanup by the owner's rule.

**Non-features**, with demand acknowledged: resume, replay and queueing (9); interactive approvals of any form, per-file prompts or elicitation (3's interactive half, 14); more than one run per instance (10); search through the shell tool (audit §5, violates no-shell); any worker other than Vibe, Antigravity included ([research](antigravity-2026-10-14.md#6-recommended-path-and-non-goals)); applying, committing or merging a patch, including in a CI mode; a Vibe version range instead of a pin. Each is rejected by a line in AGENTS.md, not by lack of demand.

## 5. Suggested text for the strategies

**For `docs/development-strategy.md`, replacing the "After 2.0.1" list with a release line:**

> **2.1 (observable and measurable).** Usage, ceilings and tool-call counts saved in every run record and shown by `runs list`; `accepted` and `reason` on `vibe_close`, with `runs usefulness` printing the log row; `excluded_globs` in the policy file, merged into the profile denylist and read back; a findings schema for reviews with `findings.json` and optional SARIF export; `runs export` audit bundles; the Vibe candidate script and the wheel-derived shipped manifest; the search sidecar once the 2.0.0 target runs confirm the MCP route names and inventory; Antigravity as a verified client (four gates, docs only); per-language task templates in the skill. Gate: every item has a fixture test, and the ones that touch a run have one hosted observation.
>
> **2.2 (wider, still one path).** `allowed_write_paths` on edits; a per-root cost ledger surfaced as a readiness blocker; Linux, claimed only after a Linux pin manifest, conformance check, one review, one edit and one disconnect are recorded; MCPB and Codex plugin packaging; the `runs` watch view.
>
> **Later, each behind its own trigger.** MCP Tasks when a client declares the extension; images with inline-only, size-capped input; a single internal repair turn and `turn/steer`, each only through an ADR against the no-continuation line; a CI mode after Linux and an ADR for a non-MCP entry point.
>
> **Never.** Resume, replay or queueing; interactive or elicitation-based approvals; more than one active run per instance; shell-based search; a worker other than Vibe; automatic patch application; a Vibe version range.

**For `marketing/strategy.md`:** add to section 1 "What is genuinely distinctive" a fifth point once 2.1 ships, "Every run has a price, a stop reason and an acceptance record", and to the landscape table a row for review products (Claude Code Review at $15–25 per review with severity tags and 👍/👎 collection; Bugbot at $1–1.50 with a 70 %+ resolution claim; Codex `/review`), with the difference "they review for you; we let your agent delegate a bounded review to another vendor's model and give you the audit bundle and the findings file". In section 2, give the SARIF/reviewdog output its own channel row (reviewdog and code-scanning users; message "pipe a Mistral second opinion into the PR check you already have"; after 2.1). In section 5 add the guardrail that the Friendly Fire result is cited only as "a class of failure our worker cannot reproduce because it has no shell and no network", never as "immune". In the metrics table add "usefulness rate published monthly from `runs usefulness`" once 2.1 exists; the number replaces "three of six".
