## What the candidates are

The three candidates are named identically in `marketing/strategy.md` (section 6, step 1) and `marketing/interest.md` (rung 1): a client that omits `approval` from `callbackKinds` crashes the server on its first approval; untrusted `workspaceRoots` still load project state; `self.sleep` and `subagent.*` run without a callback. `docs/compatibility.md` records only the first (wire facts, "Framing and handshake"); `docs/security.md` and `marketing/sources.md` do not name them. Their 2.26.1 evidence lives in the deleted audit, quoted below from the commit that added it.

## Draft note text

Both drafts are integration feedback, not vulnerability reports: in Vibe's model the app-server client is trusted, and in each case the failure is fail-closed or a documented opt-in. The owner sends; the text is the whole message.

### Candidate 2, for `security@mistral.ai`

> Subject: app-server `workspaceRoots` and `trustWorkspace` precedence (3.0.2, source reading)
>
> We build a headless client for `vibe-app-server` and read the 3.0.2 source (tag `v3.0.2`, `36f7b3a4`) to confirm our session settings. One finding may deserve your judgement on whether it belongs in a public issue, so we are sending it here first.
>
> In `session/start`, `AgentConfig.workspaceRoots` is passed unchanged to `HarnessFilesManager.for_session` (`vibe/app_server/_runtime.py` 1794-1808). `project_roots` returns every listed root whatever the trust store says (`vibe/core/config/harness_files/_harness_manager.py` 111-126), and hooks, tools, skills, plugins, agents and `AGENTS.md` are collected from `project_roots`. The docstring states that add-dirs are implicitly trusted, which is a reasonable CLI contract; the wire field carries no such statement (`vibe/app_server/protocol.py` 374-394). A client that lists its own `cwd` in `workspaceRoots` while sending `trustWorkspace: false` therefore loads that untrusted tree's `.vibe` hooks and `AGENTS.md`: `for_session` keeps the listed cwd as `_session_root` (45-62), which `_listed_roots` includes (75-85). The comment at `_runtime.py` 1798-1804 already names this and the fix ("`for_session` itself ignoring a listed root equal to the cwd").
>
> What we do: we send `workspaceRoots: []`, `trustWorkspace: false`, and read `config/effective/read` back before the first turn. Suggested changes: document on `workspaceRoots` that a listed root is trusted as `--add-dir` is, and have `for_session` drop a listed root equal to an untrusted cwd, or refuse the request with `invalid_params` when `trustWorkspace` is false and the cwd is listed. Happy to open a public issue with this text if you prefer.

### Candidate 1, for the public Bug Report form

> `initialize` accepts `capabilities.callbackKinds: []` (`vibe/app_server/_connection_protocol.py` 38-45). Under an agent with `permission = "ask"`, the first approval then raises `RuntimeError("Client does not support approval callbacks")` in `_deliver_callback` (`vibe/app_server/server.py` 1609-1615); `_backend_event_finished` cancels the serve task and the server closes (411-422, 486-493). The new `_validate_open_callback_capabilities` (1654-1670) covers only an attach to a session that already has open callbacks. Suggested change: run the same check at `initialize` or `session/start` and answer `invalid_params` with `missingCallbackKinds`, or fail the tool call with `tool_denied` instead of tearing the process down. Read from tag `v3.0.2`; not reproduced on a running build.

Candidate 3 gets no note. The one open question from the 2.26.1 audit that survives ("is the default-allow for `agents.*` a stable contract?") is a documentation question for a public Ideas or Q&A post, if at all.

## New candidates of the same kind

Read at the same commit. None is a vulnerability; each is listed so the owner can see it was looked at.

- **Approval scopes.** `ApprovalCallbackDetail.choices` defaults to all five decision types, including `approve_for_session` and `approve_permanently`, and a permanent grant is written to the user's config (`vibe/app_server/models.py` 311-331 `180257cbfc7ccb18de366f42100abe01fddbc95273ac7183ea5bf2816cf9365a`; `_unified_permissions.py` 719-772, 782-826). The client chooses; a headless client must never send either. Ordinary design.
- **Managed-configuration refresh.** `fetch_managed_config` sends `Authorization: Bearer <provider key>` to `vibe_base_url` + `/api/v1/code/managed-config` (`vibe/core/config/admin_config.py` 13-15, 77-91 `af6fe5a1ab007c4a8f497df7261d39aa53e74bc9d9833597f87e7e586b1a6e94`); `vibe_base_url` is an ordinary config field settable from the user TOML, a trusted project TOML or the environment (`vibe_schema.py` 929) and is not among the GrowthBook-mapped fields. The supervisor relies on exactly this path for its loopback endpoint. Ordinary design.
- **Remote experiments.** `GrowthbookLayer` maps remote variants to `smart_approve_available`, `smart_approve_default`, `managed_shell_tools_enabled`, `experimental_enable_registry_skills`, system-prompt and model-routing fields, and sits above defaults and below the user TOML (`vibe/core/config/layers/growthbook.py` 88-116, 134-163 `60eec5e5bbc60f3f64f530bce01e1379ab3a456c9ebd9b5496e1582fef516045`; `default_orchestrator.py` 72 `f7e3f5750634e367203239e65b3256c008c10c723acad2b734e0bd04b3f2f620`). `smart_approve_default` "Make[s] smart-approve the default mode" (`vibe_schema.py` 680-685), so a remote flag can change the approval mode for a session that names no agent; no eval runs when `enable_telemetry` or `experiments.enable` is false (`vibe/core/experiments/session.py` 128-148 `10ab62c8a020f3a10513efb15612b40e2fdc9263ebf549094abd63d08a3e252d`; `ExperimentsConfig` in `vibe/core/config/models.py` 64-69 `4cd2c5b19039dc6721324a6c6af1fb97af281045992db64a6f62f3210d4d7b13`; experiment names in `vibe/core/experiments/active.py` 14-21 `2981cb66250c157ed076b8d8e155c97509bbc281d89257a1e4baaa0d2b522fce`). A headless client should name its agent and set `experiments.enable = false`, then read both back; the supervisor does. A feature-flag design, not a vulnerability; at most a public question whether `smart_approve_default` is meant to reach app-server sessions.
- **Reasoning persistence.** Unchanged from the [3.0.2 assessment](../docs/compatibility-v3.md#findings-and-qualification-stop): `_persists_to_disk` is false with logging disabled (`_unified_harness_backend_adapter.py` 4307-4310 `2b63dfc160aa1b6877be15dd7d9e946e192ef68c4820861b543535731081473b`), reasoning remains a history entry the client must filter. Not new.
- **MCP stdio servers.** Unchanged from the [search tool facts](../docs/compatibility-v3.md#search-tool-facts): the `mcp` SDK starts stdio servers with `start_new_session=True` and Vibe's own close uses `killpg`. A client that kills Vibe with SIGKILL can orphan a server's process group. A cleanup concern for clients that add servers, not a security finding.

## Recommendation

Send one short private note, on candidate 2 only, as drafted. It is the only item where a plausible reading of the wire contract (`workspaceRoots` as the repository roots to review) loads untrusted hooks and agents, Vibe's own comment acknowledges the gap, and `SECURITY.md` asks for anything possibly security-related to come privately first. Expected outcome: "file it publicly", which the note offers. File candidate 1 directly as a public Bug Report; it is a crash on the client's own misdeclaration and fails closed, so a private round would only cost time. Drop candidate 3 from the security track and record it in Handoff as re-read and reclassified. If the owner would rather skip the private rung entirely, candidate 2 as a public issue is defensible too; the private note is the cheaper first step, not a requirement.
